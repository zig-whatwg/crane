How it is measured

Every engine opens the same pages from tests/perf/, served from loopback with cross-origin isolation (so every engine’s clock is at its finest), each launch a fresh process with a fresh profile, the engines in alternating order on one quiet host. A page times each workload itself (performance.now() around a fixed number of operations, after warm-up runs) and reports through the benchmark server, which reads the engine’s whole process set when each mark arrives: CPU time and instructions between a workload’s first and last mark, phys_footprint (Activity Monitor’s Memory) at each, and the peak a 50 ms sampler saw between them. Start-up - from launch to the first page’s load - is its own row, so no other row includes it. Crane is its release build: ReleaseSafe throughout, libc malloc, V8 linked statically; rendering and layout are not Crane’s, so no workload measures them. The full method is in docs/performance.md.

Crane ReleaseFast is that build with only the optimize mode changed (-Dwpt-runner-release-fast: ReleaseFast throughout, no C sanitizer, the same V8 and snapshot), launched the same way and alternating with the other engines in the same runs.

Every Crane build is compiled for one fixed CPU, apple_m1-fuse_aes (-Dcpu), never its build host’s: two builds of one source for two CPUs are two code layouts, and a sub-microsecond row can move about 15% between them. The browsers ship one build for every Apple Silicon Mac. The build records its target, every row carries it, and the runner refuses to compare Crane builds made for different CPUs.
