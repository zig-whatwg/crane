# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Stack

Static HTML/CSS/vanilla JS plus JSON data files, generated by a Zig tool in tools/ (the repository's rule:
new tools are Zig), with no Node build step. Published by GitHub Pages from the repository's `gh-pages`
branch. Chosen by the user, 2026-09-30.

## Users

Evaluators: embedders, companies and engineers deciding whether Crane fits what they need. They arrive
wanting the honest shape of what works, quickly, and then drill down into a suite, a test file and its
subtests to judge a specific area. Contributors use the same pages to find failures, but they are not the
primary audience.

## Product Purpose

Crane's own public rendering of its web-platform-tests (WPT) results, with an informational breakdown like
wpt.fyi's, for Crane only:
- a browsable directory tree of test suites with per-directory pass counts;
- a page per test file listing each subtest's status and failure message;
- a historical graph of Crane's pass/fail over time, one point per regeneration (83 generations since
  2026-09-19).
Success: an evaluator can see what Crane passes, what it does not, and how that is moving, without being
misled about scope.

## Positioning

Crane is a headless web platform engine written in Zig ("the browser, minus the pixels"). The site shows
Crane's results only, measured by Crane's own WPT runner, against a pinned upstream WPT revision - after the
2026-09-30 snapshot move, the same revision wpt.fyi's aligned Chrome/Firefox/Safari runs use. It is not a
browser comparison.

## Operating Context

- Data: the WPT runner's journals (one record per test file: status, passed/failed/timed-out/not-run counts,
  timings) and its wptreport JSON (per-subtest names, statuses, messages; per-file streams since the
  wptupload merge). History: wpt-results/progress-history.json. The local progress report
  (`zig build wpt-progress`, tools/wpt_progress.py) regenerates on every update; the site regenerates with
  it, updates the `gh-pages` branch, and is pushed to origin with main.
- Scope of a run: the 0.1 worklist (4,319 testharness files; 4,712 after the snapshot move) and, later,
  full-corpus runs (~31,411 files).
- The 0.1 gate: a file blocks when it times out, errors, crashes, or finishes with none of its subtests
  passing (NONE-PASSED).

## Capabilities and Constraints

- Testharness tests only: Crane has no rendering or layout, so reftests are not run and tests that need
  rendering or layout (html/rendering/, canvas, scrolling, focus traversal) are excluded from the worklist
  by design. The site must say so plainly wherever totals appear.
- No single headline pass percentage that invites comparison with full browsers (the user's instruction
  for the wpt.fyi registration issue, 2026-09-30); per-suite and per-file figures carry their scope.
  encoding/ holds most subtests, so subtest totals are always shown with that context.
- Static hosting only: no server, no database. Per-subtest data (about 1.3 million subtests) is sharded
  per test file and loaded on demand; GitHub Pages limits (1 GB site, 100 MB per file) apply.
- The `gh-pages` branch is never force-pushed, so its history accumulates: generated files must be
  deterministic, so an unchanged test file produces an unchanged data file.
- Public. Every figure must trace to a run: Crane commit, WPT revision, date.

## Brand Commitments

- Name: Crane. Tagline already in the README: "A web platform engine written in Zig: the browser, minus the
  pixels."
- No logo exists yet (one is needed for the wpt.fyi browser-list PR). Do not invent a mark silently.

## Evidence on Hand

Real results only: journals under wpt-results/, frozen baselines on the build machine, the progress
history. No testimonials, customers, benchmarks or endorsements exist; none may be invented.

## Product Principles

1. Scope before numbers: what was run, and what was deliberately not, sits beside every total.
2. Every number traces to a run - commit, WPT revision, date.
3. Drill-down is the product: suite, then file, then subtest, each with a stable, shareable URL.
4. Honest status: blocking files (TIMEOUT, ERROR, CRASH, NONE-PASSED) are named as such, never hidden in
   an average.
