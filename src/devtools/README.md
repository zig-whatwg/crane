# src/devtools - the Chrome DevTools Protocol remote end

CDP part 1 (roadmap `cdp`; design tmp/plans/cdp-part1-design.md). This file is the interface the
domain handlers are written against; the design's sections are cited as "design N.N".

## The compile flag

`-Dcdp` (default true). Off, the `devtools` module's root is `unavailable.zig` - `enabled = false`
and `unavailable_message`, nothing else of this directory is reachable - `build_options.cdp` is
false for code outside it that exists only for CDP (the engine adapter's inspector bridge), and the
platform's `devtools_transport` capability is compiled out. Users check at compile time:

```zig
const devtools = @import("devtools");
if (comptime !devtools.enabled) return fail(devtools.unavailable_message);
```

## Threads (design 2.2)

- **The devtools thread** (one per Server) owns the listener, the connections' parsing, the target
  registry, and the browser target's domains: `Browser.*` and `Target.*` are always handled there,
  whatever session sends them (browser_target.zig). It never touches a DOM or an engine.
- **Each Browser's thread** runs its page sessions (`PageSession`): the devtools thread posts a
  session's attach, every message for it and its detach to the Browser through the host's command
  queue (`BrowserHost.post`), in that order; handlers run between tasks, like any task.
- Responses and events are produced on the session's thread and appended to the connection's
  outbound FIFO (outbound.zig), so per-session order is production order.
- Waiting is never a spin in a handler: an async handler keeps its `Reply` and answers from a later
  callback (a navigation milestone, the inspector).

## Generated protocol types

`devtools.protocol` is generated by `tools/devtools_protocol_gen.zig` from
`specs/devtools-protocol/` (pinned at devtools-protocol 0.0.1717327; never edit
`protocol/` by hand: `zig build codegen` regenerates, `zig build codegen-check` checks).

- `protocol.<Domain>.<command>` = `struct { method, Params, Result }`, e.g. `protocol.Page.navigate`.
- `protocol.<Domain>.<event>` = `struct { method, Params }`, e.g. `protocol.Page.frameNavigated`.
- `protocol.<Domain>.<Type>` for the protocol's types. Optional fields are `?T = null`; string enums
  are Zig enums; `any` and property-less objects are `std.json.Value`; a type that contains itself
  holds it through `*const T`.
- Whole domains: Audits, Browser, DOM, Emulation, Fetch, IO, Input, Inspector, Log, Network, Page,
  Performance, Runtime, Security, Target (`full_domains` in the generator); other domains only the
  types those use. `protocol.findMethod(name)` knows every command of both files, and
  `Domain.origin()` says whether V8's inspector implements it (js_protocol).

## A domain handler (domains/<domain>.zig)

Listed in `domains/page_domains.zig` (`Handlers`, and its `State` in `States`). A module declares:

```zig
const PageSession = @import("../page_session.zig").PageSession;
const protocol = @import("../protocol/root.zig");
const Reply = @import("../dispatch.zig").Reply;
const P = protocol.Page;

/// Per-session state, default-initialised: `session.states.Page`.
pub const State = struct { enabled: bool = false };

// One function per command, named as the command.
// sync: return the result (or an error)
pub fn enable(session: *PageSession, params: P.enable.Params) !P.enable.Result {
    _ = params;
    session.states.Page.enabled = true;
    return .{};
}
// async: answer through `reply` now or later; keep it to answer later
pub fn navigate(session: *PageSession, params: P.navigate.Params, reply: Reply(P.navigate)) !void { ... }

// Optional hooks:
pub fn sessionStarted(session: *PageSession) void {}   // attached
pub fn sessionEnded(session: *PageSession) void {}     // detaching: clear overrides, drop kept replies
pub fn onNavigation(session: *PageSession, milestone: *const host_bridge.Milestone) void {}
                                                       // every milestone of the Browser, in order:
                                                       // compare its navigable with session.tab
pub fn dispatchRaw(session: *PageSession, method: []const u8, raw: []const u8) bool {}
                                                       // methods with no function (V8's inspector)
```

What the dispatcher answers (dispatch.zig): no function for the command and no `dispatchRaw`
taking it - -32601 "'Page.foo' wasn't found" (Chrome's text); params that do not parse - -32602
"Invalid parameters" with the reason; `return session.fail("No frame with given id found")` -
-32000 with that message (`session.failWithCode` for another code); any other error - -32000 with
its name. Params slices point into the message's arena: copy what you keep.

`Reply(C)`: `ok(result)`, `okRaw(json)`, `fail(code, message)`, `failWithData`, `drop()` (never
answered: the session ended). It is a copyable value holding a reference to the session's link; an
answer after the session ended is dropped. An async handler that returns an error must not have
answered or kept its reply.

## PageSession (page_session.zig)

On the Browser thread. `browser`, `tab` (the top-level BrowsingContext id), `target_id` (= the
tab's main frame id), `states`, `emit(E, params)`, `sendRaw(message)` (a message V8's inspector
made: the session id is appended), `fail` / `failWithCode`, `frameId(navigable_id)` /
`navigableOf(frame_id)`, `runIfWaitingForDebugger()` (releases the tab's start hold: life1's
`hold_first_navigation`), `side.sessionsOn(tab, buffer)` for events every session of a tab gets.

## Ids (ids.zig)

32 uppercase hex digits, as Chrome's UnguessableToken. A frame id is the Browser's token (16 digits)
and the navigable's BrowsingContext id (16 digits); a page target's id is its main frame's id.
Session, tab-target and browser-context ids are fresh tokens.

## The host API (host_bridge.zig)

Every use of lane cdph's BrowserHost and the Browser's tab operations goes through host_bridge.zig,
which falls back to a stub (`error.HostApiMissing`) until they are on the branch.
