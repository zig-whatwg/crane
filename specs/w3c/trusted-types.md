## [1. ]{.secno}[Introduction]{.content}[](#introduction){.self-link} {#introduction .heading .settled level="1"}

*This section is not normative.*

Certain classes of vulnerabilities occur when a web application takes a
value from an attacker-controlled source (e.g. the document URL
parameter, or postMessage channel) and passes that value, without
appropriate sanitization to one of the [injection
sinks](#injection-sinks) - various Web API functions with powerful
capabilities.

These types of issues are traditionally difficult to prevent.
Applications commonly call those injection sinks with
attacker-controlled values without authors realizing it, since it's not
clear if the input was attacker-controlled when invoking the injection
sink. Due to the dynamic nature of JavaScript it's also difficult to
ascertain that such pattern is not present in a given program. It is
often missed during manual code reviews, and automated code analysis. As
an example, if `aString` contains untrusted data, `foo[bar] = aString`
is a statement that potentially can trigger a vulnerability, depending
on a value of `foo` and `bar`.

This document focuses on preventing DOM-Based Cross-Site Scripting that
occurs when attacker-controlled data reaches [§ 2.1.1 DOM XSS injection
sinks](#dom-xss-injection-sinks), as that eventually causes execution of
the script payload controlled by the attacker. DOM XSS is prevalent in
the web applications as there are over 60 different injection sinks
(e.g. `Element.innerHTML`, or `Location.href` setters).

This document defines [Trusted Types](#trusted-types) - an API that
allows applications to lock down [injection
sinks](#injection-sink){#ref-for-injection-sink link-type="dfn"} to only
accept non-spoofable, typed values in place of strings. These values can
in turn only be created from application-defined
[policies](#policies){#ref-for-policies link-type="dfn"}, allowing the
authors to define rules guarding dangerous APIs, reducing the attack
surface to small, isolated parts of the web application codebase, which
are substantially easier to safeguard, monitor and review.

### [1.1. ]{.secno}[Goals]{.content}[](#goals){.self-link} {#goals .heading .settled level="1.1"}

- Minimize the likelihood of client-side vulnerabilities that occur when
  calling powerful Web APIs with untrusted data - for example, minimize
  the likelihood of DOM XSS.

- Encourage a design in which security decisions are encapsulated within
  a small part of the application.

- Reduce security review surface for complex web application codebases.

- Allow the usability-preserving detection of vulnerabilities similar to
  how regular programming errors are detected and surfaced to the
  developers, with the assist of dynamic and static analysis tools.

### [1.2. ]{.secno}[Non-goals]{.content}[](#non-goals){.self-link} {#non-goals .heading .settled level="1.2"}

- Prevent, or mitigate the result of injections into server-side
  generated markup, in specific reflections into the body of the scripts
  running in a document. To address server-side XSS vectors, we
  recommend existing solutions like templating systems or
  [CSP](#biblio-csp3 "Content Security Policy Level 3"){link-type="biblio"}
  [script-src](https://www.w3.org/TR/CSP3/#script-src){#ref-for-script-src
  link-type="dfn"}.

- Address resource confinement, e.g. to prevent data exfiltration, or
  connecting to external sources via
  [\[Fetch\]](#biblio-fetch "Fetch Standard"){link-type="biblio"}.

- Control subresource loading. Trusted Types aim to allow the authors to
  control loading resources that can script the current document, but
  not other subresources.

- Prevent *cross-origin* JavaScript execution (for example, Trusted
  Types don't guard loading new documents with JavaScript code via
  `data:` URLs).

- Prevent malicious authors of the web application's JavaScript code
  from being able to bypass the restrictions; attempting to protect
  against malicious authors would result in an overly complex and
  not-practical design.

### [1.3. ]{.secno}[Use cases]{.content}[](#use-cases){.self-link} {#use-cases .heading .settled level="1.3"}

- An author maintains a complex web application written in a framework
  that uses a secure templating system to generate the UI components.
  The application also depends on 3rd party client-side libraries that
  perform auxiliary tasks (e.g. analytics, performance monitoring). To
  ensure that none of these components introduce DOM XSS
  vulnerabilities, author defines a Trusted Type policy in the
  templating library and enables the enforcement for the [§ 2.1.1 DOM
  XSS injection sinks](#dom-xss-injection-sinks).

- A website uses [§ 2.1.1 DOM XSS injection
  sinks](#dom-xss-injection-sinks). The website-developer adds trusted
  types to it and monitors violations by using the
  [Content-Security-Policy-Report-Only](https://www.w3.org/TR/CSP3/#header-content-security-policy-report-only){#ref-for-header-content-security-policy-report-only
  link-type="http-header"} header field. Violations are iteratively
  fixed by refactoring the code to use only safe methods. Afterwards, no
  [§ 2.1.1 DOM XSS injection sinks](#dom-xss-injection-sinks) are called
  anymore. Hence, no trusted types are required anymore. The developer
  switches the report-only mode off and disables trusted type policies
  with the
  [trusted-types](#trusted-types-directive){#ref-for-trusted-types-directive
  link-type="dfn"} and the
  [require-trusted-types-for](#require-trusted-types-for-directive){#ref-for-require-trusted-types-for-directive
  link-type="dfn"} directives. The website's functionality was never
  impaired during the refactorings.

- A large team maintains a complex client-side application. They create
  a number of Trusted Types policies that satisfy the security
  requirements for the application. The team consolidates the policy
  implementations and the safe abstractions that use them in a small
  number of heavily reviewed files and requires extra approval for
  commits that affect these files.

  The need to create trusted values to affect [injection
  sinks](#injection-sink){#ref-for-injection-sink① link-type="dfn"},
  combined with additional scrutiny on changes that affect policy code,
  incents developers to use safe abstractions instead of writing ad-hoc
  string composition code when interacting with [§ 2.1.1 DOM XSS
  injection sinks](#dom-xss-injection-sinks).

  When considering the risk of DOM XSS, security auditors find a small
  attack surface; they focus on the small amount of code that crafts the
  CSP header and provides the safe abstractions, and ignore the bulk of
  client-side application code.

- An existing web application interacts with the DOM mostly using
  XSS-safe patterns (i.e. without using [§ 2.1.1 DOM XSS injection
  sinks](#dom-xss-injection-sinks)). In a few places, however, it
  resorts to using risky patterns like loading additional script using
  JSONP, calling into `innerHTML` or `eval`.

  Review finds that those places do not cause XSS (e.g. because
  user-controlled data is not part of the input to those sinks), but
  it's hard to migrate the application off using these patterns.

  As such, CSP cannot be enforced on this application (without resorting
  to an unsafe version using `'unsafe-eval' 'unsafe-inline'`).
  Additionally, it's possible some codebase with DOM XSS flaws was not
  included in a review, or will be introduced in the future.

  To address this risk, the author converts the reviewed parts to using
  Trusted Types, and enables Trusted Type
  [enforcement](#enforcement){#ref-for-enforcement link-type="dfn"}.
  Additional places using the injection sinks, should they exist in the
  future, are correctly blocked and reported.

- A security team is tasked with assuring that the client-side heavy
  application code does not contain XSS vulnerabilities. Since the
  server side code is homogeneous (it's mostly an API backend), and the
  application enforces Trusted Types, the review only focuses on the
  Trusted Type [policies](#policies){#ref-for-policies① link-type="dfn"}
  and their rules. Later on the reviewed policy names are allowed in the
  \'trusted-types\' CSP directive, safe for the developers to use.

  Any additional code, including the code of often-changing
  dependencies, can be excluded from the review, unless it creates a
  Trusted Type policy. Without it, the code cannot cause a DOM XSS.

## [2. ]{.secno}[Framework]{.content}[](#framework){.self-link} {#framework .heading .settled level="2"}

### [2.1. ]{.secno}[Injection sinks]{.content}[](#injection-sinks){.self-link} {#injection-sinks .heading .settled level="2.1"}

*This section is not normative.*

An [injection sink]{#injection-sink .dfn .dfn-paneled dfn-type="dfn"
noexport=""} is a powerful Web API function that should only be called
with trusted, validated or appropriately sanitized input. Calling the
injection sink with attacker-controlled (i.e. injected) inputs has
undesired consequences and is considered a security vulnerability.

[Note:]{.marker} The exact list of injection sinks covered by this
document is defined in [§ 4 Integrations](#integrations).

It's difficult to determine if a given application contains such a
vulnerability (e.g. if it is vulnerable to DOM XSS) only by analyzing
the invocations of [injection
sinks](#injection-sink){#ref-for-injection-sink② link-type="dfn"}, as
their inputs (usually strings) do not carry the information about their
provenance. For example, while the application might intentionally call
`eval()` with dynamically created inputs (e.g. for code obfuscation
purposes), calling `eval()` on strings supplied by the attacker is
definitely a security vulnerability - but it's not easy to distinguish
one from the other.

This document organizes the injection sinks into groups, based on the
capabilities that sinks in a given group have.
[Enforcement](#enforcement){#ref-for-enforcement① link-type="dfn"} for
groups is controlled via
[trusted-types-sink-group](#trusted-types-sink-group){#ref-for-trusted-types-sink-group
link-type="dfn"} values.

#### [2.1.1. ]{.secno}[DOM XSS injection sinks]{.content}[](#dom-xss-injection-sinks){.self-link} {#dom-xss-injection-sinks .heading .settled level="2.1.1"}

*This section is not normative.*

DOM XSS [injection sinks](#injection-sink){#ref-for-injection-sink③
link-type="dfn"} evaluate an input string value in a way that could
result in DOM XSS if that value is untrusted.

Examples include:

- Setters for
  [`Element`{.idl}](https://dom.spec.whatwg.org/#element){#ref-for-element
  link-type="idl"} attributes that accept a URL of the code to load like
  [`HTMLScriptElement.src`{.idl}](#dom-htmlscriptelement-src){#ref-for-dom-htmlscriptelement-src
  .idl-code link-type="attribute"},

- Setters for
  [`Element`{.idl}](https://dom.spec.whatwg.org/#element){#ref-for-element①
  link-type="idl"} attributes that accept a code to execute like
  [`HTMLScriptElement.text`{.idl}](#dom-htmlscriptelement-text){#ref-for-dom-htmlscriptelement-text
  .idl-code link-type="attribute"},

- Functions that execute code directly like `eval`,

- Navigation to \'javascript:\' URLs.

Since HTML parsers can create arbitrary elements, including scripts, and
set arbitrary attributes, DOM XSS [injection
sinks](#injection-sink){#ref-for-injection-sink④ link-type="dfn"} also
include HTML parsing sinks:

- Functions that parse & insert HTML strings into the document like
  [`Element.innerHTML`{.idl}](https://html.spec.whatwg.org/multipage/dynamic-markup-insertion.html#dom-element-innerhtml){#ref-for-dom-element-innerhtml
  link-type="idl"},
  [`ShadowRoot.innerHTML`{.idl}](https://html.spec.whatwg.org/multipage/dynamic-markup-insertion.html#dom-shadowroot-innerhtml){#ref-for-dom-shadowroot-innerhtml
  link-type="idl"}, and
  [`Element.outerHTML`{.idl}](https://html.spec.whatwg.org/multipage/dynamic-markup-insertion.html#dom-element-outerhtml){#ref-for-dom-element-outerhtml
  link-type="idl"} setters, or Document.write.

- Functions that create a new same-origin
  [`Document`{.idl}](https://dom.spec.whatwg.org/#document){#ref-for-document
  link-type="idl"} with caller-controlled markup like
  [`parseFromString()`{.idl}](https://html.spec.whatwg.org/multipage/dynamic-markup-insertion.html#dom-domparser-parsefromstring){#ref-for-dom-domparser-parsefromstring
  link-type="idl"}.

Guarding DOM XSS injection sinks is controlled by the
[trusted-types-sink-group](#trusted-types-sink-group){#ref-for-trusted-types-sink-group①
link-type="dfn"} named \'script\'.

### [2.2. ]{.secno}[Trusted Types]{.content}[](#trusted-types){.self-link} {#trusted-types .heading .settled level="2.2"}

To allow the authors to control values reaching injection sinks, we
introduce [§ 2.2 Trusted Types](#trusted-types). The following list of
[Trusted Type]{#trusted-type .dfn .dfn-paneled dfn-type="dfn"
noexport=""}s indicating that a given value is trusted by the authors to
be used with an [injection
sink](#injection-sink){#ref-for-injection-sink⑤ link-type="dfn"} in a
certain context.

[Note:]{.marker} **Trusted** in this context signifies the fact that the
application author is confident that a given value can be safely used
with an injection sink - she *trusts* it does not introduce a
vulnerability. That does not imply that the value is indeed *safe*.

[Note:]{.marker} This allows the authors to specify the intention when
creating a given value, and the user agents to introduce checks based on
the type of such value to preserve the authors\' intent. For example, if
authors intend a value to be used as an HTML snippet, an attempt to load
a script from that value would fail.

[Note:]{.marker} All Trusted Types wrap over an immutable string,
specified when the objects are created. These objects are unforgeable in
a sense that there is no JavaScript-exposed way to replace the inner
string value of a given object - it's stored in an internal slot with no
setter exposed.

[Note:]{.marker} All Trusted Types stringifiers return the inner string
value. This makes it easy to incrementally migrate the application code
into using Trusted Types in place of DOM strings (it's possible to start
producing types in parts of the application, while still using and
accepting strings in other parts of the codebase). In that sense,
Trusted Types are backwards-compatible with the regular DOM APIs.

#### [2.2.1. ]{.secno}[[`TrustedHTML`]{#trustedhtml .dfn .dfn-paneled .idl-code dfn-type="interface" export=""}]{.content}[](#trusted-html){.self-link} {#trusted-html .heading .settled level="2.2.1"}

The TrustedHTML interface represents a string that a developer can
confidently insert into an [injection
sink](#injection-sink){#ref-for-injection-sink⑥ link-type="dfn"} that
will render it as HTML. These objects are immutable wrappers around a
string, constructed via a
[`TrustedTypePolicy`{.idl}](#trustedtypepolicy){#ref-for-trustedtypepolicy
link-type="idl"}'s
[`createHTML`{.idl}](#dom-trustedtypepolicy-createhtml){#ref-for-dom-trustedtypepolicy-createhtml
link-type="idl"} method.

``` {.idl .highlight .def}
[Exposed=(Window,Worker)]
interface TrustedHTML {
  stringifier;
  DOMString toJSON();
};
```

TrustedHTML objects have an associated string [data]{#trustedhtml-data
.dfn .dfn-paneled dfn-for="TrustedHTML" dfn-type="dfn" export=""}. The
value is set when the object is created, and will never change during
its lifetime.

[`toJSON()`]{#dom-trustedhtml-tojson .dfn .dfn-paneled .idl-code
dfn-for="TrustedHTML" dfn-type="method" export=""} method steps and the
[stringification behavior]{#trustedhtml-stringification-behavior .dfn
.dfn-paneled dfn-for="TrustedHTML" dfn-type="dfn"
lt="stringificationbehavior" noexport=""} steps of a TrustedHTML object
are to return the associated
[data](#trustedhtml-data){#ref-for-trustedhtml-data link-type="dfn"}
value.

### [2.3. ]{.secno}[[Policies]{#policies .dfn .dfn-paneled dfn-type="dfn" noexport=""}]{.content}[](#policies-hdr){.self-link} {#policies-hdr .heading .settled level="2.3"}

Trusted Types can only be created via user-defined and immutable
policies that define rules for converting a string into a given Trusted
Type object. Policies allows the authors to specify custom, programmatic
rules that Trusted Types must adhere to.

::: {#sanitizing-policy .example}
[](#sanitizing-policy){.self-link} Authors may define a policy that will
sanitize an HTML string, allowing only a subset of tags and attributes
that are known not to cause JavaScript execution. Any
[`TrustedHTML`{.idl}](#trustedhtml){#ref-for-trustedhtml①
link-type="idl"} object created through this policy can then be safely
used in the application, and e.g. passed to `innerHTML` setter - even if
the input value was controlled by the attacker, the policy rules
neutralized it to adhere to policy-specific contract.

``` highlight
const sanitizingPolicy = trustedTypes.createPolicy('sanitize-html', {
  createHTML: (input) => myTrustedSanitizer(input, { superSafe: 'ok'}),
});

myDiv.innerHTML = sanitizingPolicy.createHTML(untrustedValue);
```
:::

[Note:]{.marker} [Trusted Type](#trusted-type){#ref-for-trusted-type
link-type="dfn"} objects wrap values that are explicitly trusted by the
author. As such, creating a Trusted Type object instance becomes a de
facto [injection sink](#injection-sink){#ref-for-injection-sink⑨
link-type="dfn"}, and hence code that creates a Trusted Type instances
is security-critical. To allow for strict control over Trusted Type
object creation we don't expose the constructors of those directly, but
require authors to create them via
[policies](#policies){#ref-for-policies② link-type="dfn"}.

Multiple policies can be created in a given
[Realm](https://html.spec.whatwg.org/multipage/webappapis.html#concept-global-object-realm){#ref-for-concept-global-object-realm
link-type="dfn"}, allowing the applications to define different rules
for different parts of the codebase.

::: {#policy-reference .example}
[](#policy-reference){.self-link} Library initialized with a policy
allowing it to load additional scripts from a given host.

``` highlight

const cdnScriptsPolicy = trustedTypes.createPolicy('cdn-scripts', {
  createScriptURL(url) {
    const parsed = new URL(url, document.baseURI);
    if (parsed.origin == 'https://mycdn.example') {
      return url;
    }
    throw new TypeError('invalid URL');
  },
});

myLibrary.init({policy: cdnScriptsPolicy});
```
:::

[Note:]{.marker} Trusted Type objects can only be created via policies.
If [enforcement](#enforcement){#ref-for-enforcement② link-type="dfn"} is
enabled, only the policy code can trigger an action of an [injection
sink](#injection-sink){#ref-for-injection-sink①⓪ link-type="dfn"} and
hence call-sites of the policies\' `create*` functions are the *only*
security-sensitive code in the entire program with regards to the
actions of the [injection
sinks](#injection-sink){#ref-for-injection-sink①① link-type="dfn"}. Only
this typically small subset of the entire code base needs to be
security-reviewed - there's no need to monitor or review the [injection
sinks](#injection-sink){#ref-for-injection-sink①② link-type="dfn"}
themselves, as User Agents [enforce](#enforcement){#ref-for-enforcement③
link-type="dfn"} that those sinks will only accept matching Trusted Type
objects, and these in turn can only be created via policies.

The
[`createPolicy`{.idl}](#dom-trustedtypepolicyfactory-createpolicy){#ref-for-dom-trustedtypepolicyfactory-createpolicy
link-type="idl"} function returns a policy object which `create*`
functions will create Trusted Type objects after applying the policy
rules.

[Note:]{.marker} While it's safe to freely use a policy that sanitizes
its input anywhere in the application, there might be a need to create
lax policies to be used internally, and only to be called with
author-controlled input. For example, a client-side HTML templating
library, an HTML sanitizer library, or a JS asynchronous code plugin
loading subsystem each will likely need full control over HTML or URLs.
The API design facilitates that - each policy may only be used if the
callsite can obtain a reference to the policy (a return value from
[`createPolicy()`{.idl}](#dom-trustedtypepolicyfactory-createpolicy){#ref-for-dom-trustedtypepolicyfactory-createpolicy①
link-type="idl"}). As such, policy references can be treated as
[capabilities](https://en.wikipedia.org/wiki/Object-capability_model),
access to which can be controlled using JavaScript techniques (e.g. via
closures, internal function variables, or modules).

::: {#policy-capability .example}
[](#policy-capability){.self-link} Unsafe no-op policy reachable only
from within a single code block to ascertain that it's called only with
no attacker-controlled values.

``` highlight
(function renderFootnote() {
  const unsafePolicy = trustedTypes.createPolicy('html', {
    createHTML: input => input,
  });
  const footnote = await fetch('/footnote.html').then(r => r.text());
  footNote.innerHTML = unsafePolicy.createHTML(footnote);
})();
```
:::

#### [2.3.2. ]{.secno}[[`TrustedTypePolicy`]{#trustedtypepolicy .dfn .dfn-paneled .idl-code dfn-type="interface" export=""}]{.content}[](#trusted-type-policy){.self-link} {#trusted-type-policy .heading .settled level="2.3.2"}

Policy objects implement a TrustedTypePolicy interface and define a
group of functions creating Trusted Type objects. Each of the `create*`
functions converts a string value to a given Trusted Type variant, or
throws a TypeError if a conversion of a given value is disallowed.


#### [2.3.4. ]{.secno}[[Default policy]{#default-policy-explanation .dfn .dfn-paneled dfn-type="dfn" lt="default-policy-explanation" noexport=""}]{.content}[](#default-policy-hdr){.self-link} {#default-policy-hdr .heading .settled level="2.3.4"}

*This section is not normative.*

One of the policies, the policy with a
[name](#trustedtypepolicy-name){#ref-for-trustedtypepolicy-name
link-type="dfn"} `"default"`, is special; When an [injection
sink](#injection-sink){#ref-for-injection-sink①③ link-type="dfn"} is
passed a string (instead of a Trusted Type object), this policy will be
implicitly called by the user agent with the non trusted string value,
Trusted Type of the sink and the sink type, respectively.

This allows the application to define a fallback behavior to use instead
of causing a violation. The intention is to allow the applications to
recover from an unexpected data flow, and sanitize the potentially
attacker-controlled string \"as a last resort\", or reject a value if a
safe value cannot be created. Errors thrown from within a policy are
propagated to the application.

If the default policy doesn't exist, or if its appropriate `create*`
function returns *null* or *undefined*, it will cause a CSP violation.
In the enforcing mode, an error will be thrown, but in report-only the
original value passed to the default policy will be used.

[Note:]{.marker} This optional behavior allows for introducing Trusted
Type [enforcement](#enforcement){#ref-for-enforcement④ link-type="dfn"}
to applications that are still using legacy code that uses injection
sinks. Needless to say, this policy should necessarily be defined with
very strict rules not to bypass the security restrictions in unknown
parts of the application. In an extreme case, a lax, no-op default
policy defeats all the benefits of using Trusted Types to protect access
to [injection sinks](#injection-sink){#ref-for-injection-sink①④
link-type="dfn"}. If possible, authors should resort to a default policy
in a transitional period only, use it to detect and rewrite their
dependencies that use injection sinks unsafely and eventually phase out
the usage of the default policy entirely.

[Note:]{.marker} See [§ 3.4 Get Trusted Type compliant
string](#get-trusted-type-compliant-string-algorithm) for details on how
the default policy is applied.

::: {#default-policy-example .example}
[](#default-policy-example){.self-link}

``` highlight
// Content-Security-Policy: trusted-types default; require-trusted-types-for 'script'

trustedTypes.createPolicy('default', {
  createScriptURL: (value, type, sink) => {
    console.log("Please refactor.");
    return value + '?default-policy-used&type=' + encodeURIComponent(type) +
          '&sink=' + encodeURIComponent(sink);
  }
});

aScriptElement.src = "https://cdn.example/script.js";
// Please refactor.
console.log(aScriptElement.src);
// https://cdn.example/script.js?default-policy-used&type=TrustedScriptURL&sink=HTMLScriptElement%20src
```
:::

### [2.4. ]{.secno}[[Enforcement]{#enforcement .dfn .dfn-paneled dfn-type="dfn" noexport=""}]{.content}[](#enforcement-hdr){.self-link} {#enforcement-hdr .heading .settled level="2.4"}

[Note:]{.marker} Enforcement is the process of checking that a value has
an appropriate type before it reaches an [injection
sink](#injection-sink){#ref-for-injection-sink①⑤ link-type="dfn"}.

The JavaScript API that allows authors to create policies and Trusted
Types objects from them is always available (via
[`trustedTypes`{.idl}](#dom-windoworworkerglobalscope-trustedtypes){#ref-for-dom-windoworworkerglobalscope-trustedtypes
link-type="idl"}). Since [injection
sinks](#injection-sink){#ref-for-injection-sink①⑥ link-type="dfn"}
stringify their security sensitive arguments, and [Trusted
Type](#trusted-type){#ref-for-trusted-type③ link-type="dfn"} objects
stringify to their inner string values, this allows the authors to use
Trusted Types in place of strings.

To secure the access to [injection
sinks](#injection-sink){#ref-for-injection-sink①⑦ link-type="dfn"}, on
top of the JavaScript code using the Trusted Types, the user agent needs
to enforce them i.e. assert that the injection sinks from a given group
are *never* called with string values, and Trusted Type values are used
instead. This section describes how authors may control this enforcing
behavior.

Authors may also control their [policies](#policies){#ref-for-policies③
link-type="dfn"} by specifying rules around policy creation.

#### [2.4.1. ]{.secno}[Content Security Policy]{.content}[](#content-security-policy-hdr){.self-link} {#content-security-policy-hdr .heading .settled level="2.4.1"}

Applications may control Trusted Type enforcement via [configuring a
Content Security Policy](https://www.w3.org/TR/CSP3/#policy-delivery).
This document defines new directives that correspond to Trusted Types
rules. The
[require-trusted-types-for](#require-trusted-types-for-directive){#ref-for-require-trusted-types-for-directive①
link-type="dfn"} directive specifies the [injection
sinks](#injection-sink){#ref-for-injection-sink①⑧ link-type="dfn"}
groups, for which the types should be required. The
[trusted-types](#trusted-types-csp-directive) directive controls how
[policies](#policies){#ref-for-policies④ link-type="dfn"} can be
created.

[Note:]{.marker} Using CSP mechanisms allows the authors to prepare
their application for enforcing Trusted Types via using the
[Content-Security-Policy-Report-Only](https://www.w3.org/TR/CSP3/#header-content-security-policy-report-only){#ref-for-header-content-security-policy-report-only①
link-type="http-header"} HTTP Response header.

[Note:]{.marker} Most of the enforcement rules are defined as
modifications of the algorithms in other specifications, see [§ 4
Integrations](#integrations).

### [4.3. ]{.secno}[Integration with Content Security Policy]{.content}[](#integration-with-content-security-policy){.self-link} {#integration-with-content-security-policy .heading .settled level="4.3"}

#### [4.3.1. ]{.secno}[[require-trusted-types-for]{#require-trusted-types-for-directive .dfn .dfn-paneled dfn-type="dfn" export="" lt="require-trusted-types-for-directive"} directive]{.content}[](#require-trusted-types-for-csp-directive){.self-link} {#require-trusted-types-for-csp-directive .heading .settled level="4.3.1"}

This document defines *require-trusted-types-for* - a new [Content
Security Policy
directive](https://www.w3.org/TR/CSP3/#directives){#ref-for-directives
link-type="dfn"}.

[require-trusted-types-for](#require-trusted-types-for-directive){#ref-for-require-trusted-types-for-directive②
link-type="dfn"} directive configures the Trusted Types framework for
all the [injection sinks](#injection-sink){#ref-for-injection-sink②①
link-type="dfn"} of certain groups in a current
[realm](https://html.spec.whatwg.org/multipage/webappapis.html#concept-global-object-realm){#ref-for-concept-global-object-realm①
link-type="dfn"}. Specifically, it defines what should be the behavior
when a string value is passed to an [injection
sink](#injection-sink){#ref-for-injection-sink②② link-type="dfn"} of a
given group (i.e. should the type-based enforcement be enabled for such
sinks).

[Note:]{.marker} Currently, only the enforcement for [§ 2.1.1 DOM XSS
injection sinks](#dom-xss-injection-sinks) is specified.

The syntax for the directive's
[name](https://www.w3.org/TR/CSP3/#directive-name){#ref-for-directive-name
link-type="dfn"} and
[value](https://www.w3.org/TR/CSP3/#directive-value){#ref-for-directive-value
link-type="dfn"} is described by the following ABNF:

    directive-name = "require-trusted-types-for"
    directive-value = trusted-types-sink-group-keyword *( required-ascii-whitespace trusted-types-sink-group-keyword)
    trusted-types-sink-group-keyword = "'" trusted-types-sink-group "'"
    trusted-types-sink-group = "script"

::: {#require-tt-for-script-header .example}
[](#require-tt-for-script-header){.self-link} Enforce Trusted Types at
the DOM XSS injection sinks.

``` http
Content-Security-Policy: require-trusted-types-for 'script'
```
:::

##### [4.3.1.1. ]{.secno}[`require-trusted-types-for` Pre-Navigation check]{.content}[](#require-trusted-types-for-pre-navigation-check){.self-link} {#require-trusted-types-for-pre-navigation-check .heading .settled level="4.3.1.1"}

Given a
[request](https://fetch.spec.whatwg.org/#concept-request){#ref-for-concept-request
link-type="dfn"} (`request`{.variable}), a string
`navigation type`{.variable} and a
[policy](https://www.w3.org/TR/CSP3/#content-security-policy-object){#ref-for-content-security-policy-object
link-type="dfn"} (`policy`{.variable}), this algorithm returns
`"Blocked"` if a navigation violates the
[require-trusted-types-for](#require-trusted-types-for-directive){#ref-for-require-trusted-types-for-directive③
link-type="dfn"} directive's constraints and `"Allowed"` otherwise. This
constitutes the
[require-trusted-types-for](#require-trusted-types-for-directive){#ref-for-require-trusted-types-for-directive④
link-type="dfn"} directive's [pre-navigation
check](https://www.w3.org/TR/CSP3/#directive-pre-navigation-check){#ref-for-directive-pre-navigation-check
link-type="dfn"}:

[Note:]{.marker} This algorithm assures that the code to be executed by
a navigation to a `javascript:` URL will have to pass through a [default
policy](#default-policy-explanation){#ref-for-default-policy-explanation
link-type="dfn"}'s `createScript` function, in addition to all other
restrictions imposed by other CSP directives.

1.  If `request`{.variable}'s
    [url](https://fetch.spec.whatwg.org/#concept-request-url){#ref-for-concept-request-url
    link-type="dfn"}'s
    [scheme](https://url.spec.whatwg.org/#concept-url-scheme){#ref-for-concept-url-scheme
    link-type="dfn"} is not `"javascript"`, return `"Allowed"` and abort
    further steps.

2.  Let `urlString`{.variable} be the result of running the [URL
    serializer](https://url.spec.whatwg.org/#concept-url-serializer){#ref-for-concept-url-serializer
    link-type="dfn"} on `request`{.variable}'s
    [url](https://fetch.spec.whatwg.org/#concept-request-url){#ref-for-concept-request-url①
    link-type="dfn"}.

3.  Let `encodedScriptSource`{.variable} be the result of removing the
    leading `"javascript:"` from `urlString`{.variable}.

4.  Let `convertedScriptSource`{.variable} be the result of executing
    [Process value with a default
    policy](#process-value-with-a-default-policy){#ref-for-process-value-with-a-default-policy①
    link-type="dfn"} algorithm, with the following arguments:

    - [`TrustedScript`{.idl}](#trustedscript){#ref-for-trustedscript①⑧
      link-type="idl"} as `expectedType`{.variable}

    - `request`{.variable}'s
      [clients](https://fetch.spec.whatwg.org/#concept-request-client){#ref-for-concept-request-client
      link-type="dfn"}'s [global
      object](https://html.spec.whatwg.org/multipage/webappapis.html#concept-settings-object-global){#ref-for-concept-settings-object-global
      link-type="dfn"} as `global`{.variable}

    - `encodedScriptSource`{.variable} as `input`{.variable}

    - `"Location href"` as `sink`{.variable}

    If that algorithm threw an error or
    `convertedScriptSource`{.variable} is not a
    [`TrustedScript`{.idl}](#trustedscript){#ref-for-trustedscript①⑨
    link-type="idl"} object, return \"Blocked\" and abort further steps.

5.  Set `urlString`{.variable} to be the result of prepending
    `"javascript:"` to stringified `convertedScriptSource`{.variable}.

6.  Let `newURL`{.variable} be the result of running the [URL
    parser](https://url.spec.whatwg.org/#concept-url-parser){#ref-for-concept-url-parser
    link-type="dfn"} on `urlString`{.variable}. If the parser returns a
    failure, return `"Blocked"` and abort further steps.

7.  Set `request`{.variable}'s
    [url](https://fetch.spec.whatwg.org/#concept-request-url){#ref-for-concept-request-url②
    link-type="dfn"} to `newURL`{.variable}.

    [Note:]{.marker} No other CSP directives operate on `javascript:`
    URLs in a pre-navigation check. Other directives that check
    javascript: URLs will operate on the modified URL later, in the
    [inline
    check](https://www.w3.org/TR/CSP3/#directive-inline-check){#ref-for-directive-inline-check
    link-type="dfn"}.

8.  Return `"Allowed"`.

#### [4.3.2. ]{.secno}[[trusted-types]{#trusted-types-directive .dfn .dfn-paneled dfn-type="dfn" export="" lt="trusted-types-directive"} directive]{.content}[](#trusted-types-csp-directive){.self-link} {#trusted-types-csp-directive .heading .settled level="4.3.2"}

This document defines *trusted-types* - a new [Content Security Policy
directive](https://www.w3.org/TR/CSP3/#directives){#ref-for-directives①
link-type="dfn"}. The
[trusted-types](#trusted-types-directive){#ref-for-trusted-types-directive②
link-type="dfn"} directive controls the creation of Trusted Type
[policies](#policies){#ref-for-policies⑤ link-type="dfn"}.

The syntax for the directive's
[name](https://www.w3.org/TR/CSP3/#directive-name){#ref-for-directive-name①
link-type="dfn"} and
[value](https://www.w3.org/TR/CSP3/#directive-value){#ref-for-directive-value①
link-type="dfn"} is described by the following ABNF:

    directive-name = "trusted-types"
    directive-value = serialized-tt-configuration
    serialized-tt-configuration = ( tt-expression *( required-ascii-whitespace tt-expression ) )
    tt-expression = tt-policy-name  / tt-keyword / tt-wildcard
    tt-wildcard = "*"
    tt-policy-name = 1*( ALPHA / DIGIT / "-" / "#" / "=" / "_" / "/" / "@" / "." / "%")
    tt-keyword = "'allow-duplicates'" / "'none'"

::: {#allowlist-of-policy-names-in-header .example}
[](#allowlist-of-policy-names-in-header){.self-link} Types are enforced
at sinks, and only two policies may be created: "one" and "two".

``` http
Content-Security-Policy: require-trusted-types-for 'script'; trusted-types one two
```
:::

::: {#header-that-allows-no-policy-names .example}
[](#header-that-allows-no-policy-names){.self-link} An empty
[directive](https://www.w3.org/TR/CSP3/#directives){#ref-for-directives②
link-type="dfn"}
[value](https://www.w3.org/TR/CSP3/#directive-value){#ref-for-directive-value②
link-type="dfn"} indicates policies may not be created, and sinks expect
Trusted Type values, i.e. no DOM XSS [injection
sinks](#injection-sink){#ref-for-injection-sink②③ link-type="dfn"} can
be used at all.

``` http
Content-Security-Policy: trusted-types; require-trusted-types-for 'script'
```
:::

The keyword `'none'` may be used to explicitly express the above:

::: {#header-with-none-that-allows-no-policy-names .example}
[](#header-with-none-that-allows-no-policy-names){.self-link}

``` http
Content-Security-Policy: trusted-types 'none'; require-trusted-types-for 'script'
```
:::

Keyword `'allow-duplicates'` allows for creating policies with a name
that was already used.

::: {#allow-duplicates-in-header .example}
[](#allow-duplicates-in-header){.self-link}

``` http
Content-Security-Policy: trusted-types foo bar 'allow-duplicates'
```
:::

If the policy named `default` is present in the list, it refers to the
[default
policy](#trustedtypepolicyfactory-default-policy){#ref-for-trustedtypepolicyfactory-default-policy④
link-type="dfn"}. All strings passed to [injection
sinks](#injection-sink){#ref-for-injection-sink②④ link-type="dfn"} will
be passed through it instead of being rejected outright.

::: {#default-in-header .example}
[](#default-in-header){.self-link}

``` http
Content-Security-Policy: trusted-types one two default
```
:::

#### [4.3.3. ]{.secno}[Does sink type require trusted types?]{.content}[](#does-sink-require-trusted-types){.self-link} {#does-sink-require-trusted-types .heading .settled level="4.3.3"}

This algorithm returns `true` if the [injection
sink](#injection-sink){#ref-for-injection-sink②⑤ link-type="dfn"}
requires a [Trusted Type](#trusted-type){#ref-for-trusted-type⑤
link-type="dfn"}, and `false` otherwise.

The [does sink type require trusted
types?]{#does-sink-type-require-trusted-types .dfn .dfn-paneled
dfn-type="dfn" export=""} algorithm, given a [global
object](https://html.spec.whatwg.org/multipage/webappapis.html#concept-realm-global){#ref-for-concept-realm-global③
link-type="dfn"} (`global`{.variable}), a string
(`sinkGroup`{.variable}) and a boolean
(`includeReportOnlyPolicies`{.variable}), performs these steps:

1.  For each `policy`{.variable} in `global`{.variable}'s [CSP
    list](https://www.w3.org/TR/CSP3/#global-object-csp-list){#ref-for-global-object-csp-list
    link-type="dfn"}:

    1.  If `policy`{.variable}'s [directive
        set](https://www.w3.org/TR/CSP3/#policy-directive-set){#ref-for-policy-directive-set
        link-type="dfn"} does not contain a
        [directive](https://www.w3.org/TR/CSP3/#directives){#ref-for-directives③
        link-type="dfn"} whose
        [name](https://www.w3.org/TR/CSP3/#directive-name){#ref-for-directive-name②
        link-type="dfn"} is `"require-trusted-types-for"`, skip to the
        next `policy`{.variable}.

    2.  Let `directive`{.variable} be the `policy`{.variable}'s
        `directive set`{.variable}'s
        [directive](https://www.w3.org/TR/CSP3/#directives){#ref-for-directives④
        link-type="dfn"} whose name is `"require-trusted-types-for"`

    3.  If `directive`{.variable}'s
        [value](https://www.w3.org/TR/CSP3/#directive-value){#ref-for-directive-value③
        link-type="dfn"} does not contain a
        [trusted-types-sink-group](#trusted-types-sink-group){#ref-for-trusted-types-sink-group③
        link-type="dfn"} which is a match for `sinkGroup`{.variable},
        skip to the next `policy`{.variable}.

    4.  Let `enforced`{.variable} be true if `policy`{.variable}'s
        [disposition](https://www.w3.org/TR/CSP3/#policy-disposition){#ref-for-policy-disposition
        link-type="dfn"} is `"enforce"`, and false otherwise.

    5.  If `enforced`{.variable} is true, return true.

    6.  If `includeReportOnlyPolicies`{.variable} is true, return true.

2.  Return false.

#### [4.3.4. ]{.secno}[Should sink type mismatch violation be blocked by Content Security Policy?]{.content}[](#should-block-sink-type-mismatch){.self-link} {#should-block-sink-type-mismatch .heading .settled level="4.3.4"}

This algorithm returns `"Blocked"` if the [injection
sink](#injection-sink){#ref-for-injection-sink②⑥ link-type="dfn"}
requires a [Trusted Type](#trusted-type){#ref-for-trusted-type⑥
link-type="dfn"}, and `"Allowed"` otherwise.

The [should sink type mismatch violation be blocked by content security
policy?]{#should-sink-type-mismatch-violation-be-blocked-by-content-security-policy
.dfn .dfn-paneled dfn-type="dfn" noexport=""} algorithm, given a [global
object](https://html.spec.whatwg.org/multipage/webappapis.html#concept-realm-global){#ref-for-concept-realm-global④
link-type="dfn"} (`global`{.variable}), a string (`sink`{.variable}), a
string (`sinkGroup`{.variable}) and a string (`source`{.variable}),
performs the following steps:

1.  Let `result`{.variable} be `"Allowed"`.

2.  Let `sample`{.variable} be `source`{.variable}.

3.  If `sink`{.variable} is `"Function"`, then:

    1.  If `sample`{.variable} starts with `"function anonymous"`, strip
        that from `sample`{.variable}.

    2.  Otherwise if `sample`{.variable} starts with
        `"async function anonymous"`, strip that from
        `sample`{.variable}.

    3.  Otherwise if `sample`{.variable} starts with
        `"function* anonymous"`, strip that from `sample`{.variable}.

    4.  Otherwise if `sample`{.variable} starts with
        `"async function* anonymous"`, strip that from
        `sample`{.variable}.

4.  For each `policy`{.variable} in `global`{.variable}'s [CSP
    list](https://www.w3.org/TR/CSP3/#global-object-csp-list){#ref-for-global-object-csp-list①
    link-type="dfn"}:

    1.  If `policy`{.variable}'s [directive
        set](https://www.w3.org/TR/CSP3/#policy-directive-set){#ref-for-policy-directive-set①
        link-type="dfn"} does not contain a
        [directive](https://www.w3.org/TR/CSP3/#directives){#ref-for-directives⑤
        link-type="dfn"} whose
        [name](https://www.w3.org/TR/CSP3/#directive-name){#ref-for-directive-name③
        link-type="dfn"} is `"require-trusted-types-for"`, skip to the
        next `policy`{.variable}.

    2.  Let `directive`{.variable} be the `policy`{.variable}'s
        `directive set`{.variable}'s
        [directive](https://www.w3.org/TR/CSP3/#directives){#ref-for-directives⑥
        link-type="dfn"} whose name is `"require-trusted-types-for"`

    3.  If `directive`{.variable}'s
        [value](https://www.w3.org/TR/CSP3/#directive-value){#ref-for-directive-value④
        link-type="dfn"} does not contain a
        [trusted-types-sink-group](#trusted-types-sink-group){#ref-for-trusted-types-sink-group④
        link-type="dfn"} which is a match for `sinkGroup`{.variable},
        skip to the next `policy`{.variable}.

    4.  Let `violation`{.variable} be the result of executing [Create a
        violation object for global, policy, and
        directive](https://www.w3.org/TR/CSP3/#create-violation-for-global)
        on `global`{.variable}, `policy`{.variable} and
        `"require-trusted-types-for"`

    5.  Set `violation`{.variable}'s
        [resource](https://www.w3.org/TR/CSP3/#violation-resource){#ref-for-violation-resource
        link-type="dfn"} to `"trusted-types-sink"`.

    6.  Let `trimmedSample`{.variable} be the substring of
        `sample`{.variable}, containing its first 40 characters.

    7.  Set `violation`{.variable}'s
        [sample](https://www.w3.org/TR/CSP3/#violation-sample){#ref-for-violation-sample
        link-type="dfn"} to be the result of
        [concatenating](https://infra.spec.whatwg.org/#string-concatenate){#ref-for-string-concatenate
        link-type="dfn"} the list « `sink`{.variable},
        `trimmedSample`{.variable} « using `"|"` as a separator.

    8.  Execute [Report a
        violation](https://www.w3.org/TR/CSP3/#report-violation) on
        `violation`{.variable}.

    9.  If `policy`{.variable}'s
        [disposition](https://www.w3.org/TR/CSP3/#policy-disposition){#ref-for-policy-disposition①

5.  Return `result`{.variable}.

This algorithm returns `"Blocked"` if the
[`TrustedTypePolicy`{.idl}](#trustedtypepolicy){#ref-for-trustedtypepolicy①③

link-type="dfn"} (`global`{.variable}), a string
(`policyName`{.variable}) and a list of strings
(`createdPolicyNames`{.variable}), performs the following steps:

1.  Let `result`{.variable} be `"Allowed"`.

2.  For each `policy`{.variable} in `global`{.variable}'s [CSP

    link-type="dfn"}:

    2.  If `policy`{.variable}'s [directive

        link-type="dfn"} does not contain a

    3.  Let `directive`{.variable} be the `policy`{.variable}'s

        `createViolation`{.variable} to true.

        [Note:]{.marker} Like in other CSP directives, \'none\' keyword
        will be ignored if other keywords or policy names are present.

    5.  If `createdPolicyNames`{.variable} contains
        `policyName`{.variable} and `directive`{.variable}'s
        [value](https://www.w3.org/TR/CSP3/#directive-value){#ref-for-directive-value⑥
        link-type="dfn"} does not contain a
        [tt-keyword](#tt-keyword){#ref-for-tt-keyword② link-type="dfn"}
        which is a match for a value `'allow-duplicates'`, set
        `createViolation`{.variable} to true.

        [Note:]{.marker}
        `trusted-types policyA policyB 'allow-duplicates'` allows

    6.  If `directive`{.variable}'s
        [value](https://www.w3.org/TR/CSP3/#directive-value){#ref-for-directive-value⑦

        [tt-policy-name](#tt-policy-name){#ref-for-tt-policy-name①

        link-type="dfn"}, set `createViolation`{.variable} to true.

    7.  If `createViolation`{.variable} is false, skip to the next
        `policy`{.variable}.

    8.  Let `violation`{.variable} be the result of executing [Create a
        violation object for global, policy, and
        directive](https://www.w3.org/TR/CSP3/#create-violation-for-global)
        on `global`{.variable}, `policy`{.variable} and

    9.  Set `violation`{.variable}'s
        [resource](https://www.w3.org/TR/CSP3/#violation-resource){#ref-for-violation-resource①

    10. Set `violation`{.variable}'s
        [sample](https://www.w3.org/TR/CSP3/#violation-sample){#ref-for-violation-sample①

        containing its first 40 characters.

    11. Execute [Report a
        violation](https://www.w3.org/TR/CSP3/#report-violation) on

        [disposition](https://www.w3.org/TR/CSP3/#policy-disposition){#ref-for-policy-disposition②
        link-type="dfn"} is `"enforce"`, then set `result`{.variable} to
        `"Blocked"`.

3.  Return `result`{.variable}.

## [5. ]{.secno}[Security Considerations]{.content}[](#security-considerations){.self-link} {#security-considerations .heading .settled level="5"}

Trusted Types are not intended to protect access to [injection
sinks](#injection-sink){#ref-for-injection-sink②⑦ link-type="dfn"} in an
actively malicious execution environment. It's assumed that the
application is written by non-malicious authors; the intent is to
prevent developer mistakes that could result in security bugs, and not
to defend against first-party malicious code actively trying to bypass
policy restrictions. Below we enumerate already identified vectors that
remain risky even in environments with enforced Trusted Types.

### [5.1. ]{.secno}[Cross-document vectors]{.content}[](#cross-document-vectors){.self-link} {#cross-document-vectors .heading .settled level="5.1"}

While the code running in a window in which Trusted Types are enforced
cannot dynamically create nodes that would bypass the policy
restrictions, it is possible that such nodes can be imported or adopted
from documents in other windows, that don't have the same set of
restrictions. In essence - it is possible to bypass Trusted Types if a
malicious author creates a setup in which a restricted document colludes
with an unrestricted one. In an extreme case, the restricted document
might create a
[`Blob`{.idl}](https://www.w3.org/TR/FileAPI/#dfn-Blob){#ref-for-dfn-Blob
link-type="idl"} from strings and navigate to it.

CSP propagation rules (see [Content Security Policy 3 § 7.8 CSP
Inheriting to avoid
bypasses](https://www.w3.org/TR/CSP3/#security-inherit-csp) partially
address this issue, as new [local
scheme](https://fetch.spec.whatwg.org/#local-scheme){#ref-for-local-scheme
link-type="dfn"} documents will inherit the same set of restrictions,
so - for example - `script-src` restrictions could be used to make sure
injections into
[`Blob`{.idl}](https://www.w3.org/TR/FileAPI/#dfn-Blob){#ref-for-dfn-Blob①
link-type="idl"} contents would not execute scripts. To address this
issue comprehensively, other mechanisms like [Origin
Policy](https://wicg.github.io/origin-policy/) should be used to ensure
that baseline security rules are applied for the whole origin.

### [5.3. ]{.secno}[Script gadgets]{.content}[](#script-gadgets){.self-link} {#script-gadgets .heading .settled level="5.3"}

While Trusted Types logic is called on many operations that results in
creating DOM trees from string, it should not be treated as a mechanism
for guarding all DOM tree creation in a document. This is important
especially in the presence of [script
gadgets](https://github.com/google/security-research-pocs/tree/master/script-gadgets),
where an application reacts to contents of usually benign DOM elements
or attributes. Developers using DOM API directly can trigger such
gadgets without using Trusted Types. However, in order for the gadget to
trigger DOM XSS, it needs to obtain a Trusted Type value via a policy.
Authors need to ascertain that the data passed to Trusted Type policies
is indeed trustworthy, if the policy rules don't enforce constraints or
validate the data themselves.

### [5.4. ]{.secno}[Best practices for policy design]{.content}[](#best-practices-for-policy-design){.self-link} {#best-practices-for-policy-design .heading .settled level="5.4"}

Trusted Types limit the scope of the code that can introduce
vulnerabilities via [injection
sinks](#injection-sink){#ref-for-injection-sink②⑧ link-type="dfn"} to
the implementation of [policies](#policies){#ref-for-policies⑥
link-type="dfn"}. In this design, insecure policies can still expose
[injection sinks](#injection-sink){#ref-for-injection-sink②⑨
link-type="dfn"} to untrusted data. Special emphasis needs to be taken
by use policies that are either secure for all possible inputs, or limit
the access to insecure policies, such that they are only called with
non-attacker controlled inputs.

As policies are custom JavaScript code, they may be written in a way
that heavily depends on a global state. We advise against this. The
policies should be self-contained as much as possible. All objects that
may alter security decisions a policy makes effectively *become* the
policy, and should be guarded & reviewed together.

[](#issue-2eb927d2){.self-link} Refer to the external document on secure
policy design.

## [6. ]{.secno}[Privacy Considerations]{.content}[](#privacy-considerations){.self-link} {#privacy-considerations .heading .settled level="6"}

The specification may partially observe and alter the behavior of
scripts running within the application, e.g. causing certain operations
on [injection sinks](#injection-sink){#ref-for-injection-sink③⓪
link-type="dfn"} to fail, or monitoring and changing their effect with a
[default
policy](#trustedtypepolicyfactory-default-policy){#ref-for-trustedtypepolicyfactory-default-policy⑤
link-type="dfn"}. However, early-running scripts already have this
capability by overriding appropriate property descriptors.

It is possible for the application to report violations of Trusted Types
restrictions. Violation reports would include the trimmed-down payload
passed to the injection sink (40 characters, including the sink name).
These feature is reusing the Content Security Policy reporting
mechanisms.

## [7. ]{.secno}[Implementation Considerations]{.content}[](#implementation-considerations){.self-link} {#implementation-considerations .heading .settled level="7"}

### [7.1. ]{.secno}[Vendor-specific Extensions and Addons]{.content}[](#vendor-specific-extensions-and-addons){.self-link} {#vendor-specific-extensions-and-addons .heading .settled level="7.1"}

Restriction imposed by Trusted Types SHOULD NOT interfere with the
operation of user-agent features like addons, extensions, or
bookmarklets. These kinds of features generally advance the user's
priority over page authors, as espoused in
[\[html-design-principles\]](#biblio-html-design-principles "HTML Design Principles"){link-type="biblio"}.
Specifically, extensions SHOULD be able to pass strings to the
[injection sinks](#injection-sink){#ref-for-injection-sink③①
link-type="dfn"} without triggering [default
policy](#trustedtypepolicyfactory-default-policy){#ref-for-trustedtypepolicyfactory-default-policy⑥
link-type="dfn"} execution, violation generation, or the rejection of
the value.
