# Architecture: A step that calls script may not run through what the call can clear - give the step its own values, as the spec does

**Date**: 2026-11-05
**Lesson**: `new TransformStream(transformer)` called `start()` through the converted Transformer dictionary, and the controller owned that dictionary as its algorithms. When start() terminated or errored the stream, ClearAlgorithms destroyed the dictionary in the middle of the call, and the constructor read it again after the call returned.

**Why**: In the spec, the constructor's step 12 invokes `transformerDict["start"]` with callback this value `transformer`. Both are the constructor's own values. The controller's [[transformAlgorithm]], [[flushAlgorithm]] and [[cancelAlgorithm]] are closures that SetUpTransformStreamDefaultControllerFromTransformer made from them, and TransformStreamDefaultControllerClearAlgorithms only drops those three. Crane kept one object for both: the dictionary served the constructor's call and also held the controller's algorithms. So ClearAlgorithms, which `controller.terminate()` and `controller.error()` run at TransformStreamErrorWritableAndUnblockWrite step 1, freed what the constructor was still using. The code's own comment said "the call may clear the algorithms (release)" and moved `start` and `this` out first. But clearing ran the dictionary's deinit (release, then destroy), not only release. The pointer the step went on with was `self`.

**What Happened**:
- The first generation sweep with crashes8's poison-on-free (main e7101e588f, 2026-11-05) crashed streams/transform-streams/{terminate,errors,general}.any.js at 0xdddddddddddddded. With CRANE_POISON_FREES=0 all three were OK.
- The Debug runner's stack was `JsTransformer.callStart` (streams_transform.zig:214, `js.keepTraced(self.controller.?, ...)`) -> `traceValue` -> protocol_tracing.zig:127 `owner.ctx.engine_ctx`. `self.controller` read 0xdd..dd from the freed dictionary, and `ctx` sits 0x10 into the Instance.
- On the unfixed tree, the unit test crashed in all 5 of its clearing cases at that same frame (`callStart`, streams_transform.zig:214, through the testing allocator's freed-slot fill), alone and in batch.
- Without poisoning, release had set `controller` to null before the destroy, and the DebugAllocator kept those bytes. So the stale read found null, and the file passed for weeks.
- The readable and writable sides' start steps have the same shape, but they were safe: after the call they re-read `controller.source` and `controller.sink`, never the dictionary, and the engine turns the callback's handles into Locals before it calls.

**Fix**: The constructor takes `start` out of the dictionary (`JsTransformer.takeStart`) before the controller takes it over. It then invokes start itself, with its own `transformer_object` as `this`, and never touches the dictionary again. `attach` settles `this` at once. This follows Gecko, whose TransformStream::Constructor step 12 calls its local `transformerDict.mStart` with `transformerObj` (dom/streams/TransformStream.cpp). Blink's TransformStream::InitInternal does the same with `CallOrNoop1(script_state, transformer, "start", ...)` on the transformer object (core/streams/transform_stream.cc). Test: tests/v8/crashes9_transform_start_clears_algorithms_test.zig covers terminate, error, a throwing size() and error-then-throw inside start(), each on the testing allocator, plus `this` for the later calls.

**Takeaway**: **Whatever a step uses after a call into script must belong to the step (its locals, or an object it holds), never to the algorithms the call can clear: map each spec variable to its own owner, and after the call read the controller's slot, not `self`.**
