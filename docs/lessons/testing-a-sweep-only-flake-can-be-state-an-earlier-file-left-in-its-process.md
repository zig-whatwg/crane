# Testing: A sweep-only flake can be state an earlier file left in its runner process

**Date**: 2026-11-05
**Lesson**: Before testing a load or timing hypothesis for a file that fails only in sweeps, list the files its runner process ran before it and the state they leave behind; a spec step that stops at the first miss turns that leftover state into a failure the browsers never show.

**Why**: A sweep's runner process runs up to 40 files in one Browser. The runner clears cookies between files, but not Cache Storage (nor other storage), so a cache one file opens and never deletes is still in the origin's name to cache map for every later file in that process. Service Workers' Handle Fetch step 13.3.3.7 walks that map for a router rule's "cache" source and, as written, returns to the network at the first cache with no match (7.3, "If requestResponses is an empty list, return timingInfo"). Crane followed it literally. Chromium (CacheStorage::MatchAllCaches) and WebKit (CacheStorageManager::query) look in every cache and take the first match.

**What Happened**: service-workers/service-worker/static-router-no-fetch-handler.https.html lost "The router rule is evaluated without fetch handlers in service worker" (404 instead of "From cache") in generation 203, as it had in generations 154 and 195 and in a full A/B, and its siblings static-router-main-resource and static-router-subresource lost their cache-source subtests the same way. Alone it always passed, so the queue's hypothesis was a race between the install step's cache.put and activation under load. Generation 203's per-process report (`full/chunks/queue/wptreport-journal.shard6-s39.json`, one file per runner process) showed resource-timing-cross-origin-server-timing.https.html six files earlier in the same process: its worker opens "test-cache" and never deletes it, so the map was ["test-cache", "v1"] and the lookup stopped at "test-cache". Measured on main's runner (`wpt_runner --repeat`, a fresh process per run): the file alone beside `--load=4` failed 0 of 200 runs; the pair in one process failed 200 of 200; a replay of generation 203's process slice failed 20 of 20. After the fix, interleaved with main's runner: 0/200 against 200/200, and 0/20 against 20/20.

**Fix**: Get Router Source's cache step goes on to the next cache when one has no match (golden rule 2: the two shipping browsers; Firefox does not ship addRoutes; spec issue w3c/ServiceWorker#1853), in `Storage.routerMatch` (src/service_worker/cache/store.zig), with a unit test whose first cache lacks the request and a Crane test (crane/flaky5-sw-router-cache-every-cache.https.html) that opens a cache before the worker's. The method is the one in [When a result moves only under new sharding, replay the shard's prefix serially](testing-a-difference-that-appears-with-new-sharding-replay-the-shard-prefix.md); with the shared queue, the per-process report names the exact prefix.

**Takeaway**: **A file that fails only in sweeps is either load or the files before it in its process: read the sweep's per-process report (`wptreport-journal.shardN-sK.json`) and the state those files leave before designing a timing experiment, and replay that slice in one process.**
