# Architecture: An engine upgrade changes what a collection may drop - the identity tests are the contract, and each "V8 does X" line in a comment is a dated reading

**Date**: 2026-11-13
**Lesson**: A design that leans on the collector's rules ("a scavenge never drops a wrapper script could tell apart") holds only for the engine version the rules were read from. V8 15.7 treats WeakRef and FinalizationRegistry targets weakly in a young-generation collection (flag `handle_weak_ref_weakly_in_minor_gc`, on by default: 15.7.112.43 src/flags/flag-definitions.h:3901-3908, src/heap/scavenger.cc:1659-1661); 13.1.203 held them strongly there. With droppable node wrappers (the wrapper redesign's P8) that turned one sentence of the design - "a WeakRef or FinalizationRegistry target is held strongly by a scavenge" - false, and a FinalizationRegistry callback ran for a node still in its document.

**Why**: P8 hands V8 the question "can script tell this wrapper from a fresh one?" (`JSObject::IsUnmodifiedApiObject`: its constructor's initial map, no elements, no identity hash). On 13.1 the cases that rule does not see - a WeakRef target, a FinalizationRegistry target - were covered by a second rule in a different file: the scavenger treated them as strong. V8 removed that second rule for young collections. A WeakRef target is still spared, by accident: `Heap::KeepDuringJob` puts it in a hash set and so gives it an identity hash. A FinalizationRegistry target gets nothing, so an unmodified wrapper registered and let go is reclaimed at the next scavenge and its cell is cleared - while the node, and a new wrapper for it on its next access, are still there. ECMA-262 9.9.2-9.9.3 allow that only for an object that is not live.

**What Happened**: Lane wr1 batch 11 merged P4..P8 onto main's V8 15.7. Everything compiled and 13,260 of 13,294 tests passed; two of the four failures were tests/v8/wr8_young_generation_test.zig's R3 identity cases, written in batch 4 precisely to pin "what V8 lets a scavenge drop": `fr.register(o, 'probe')` now answered "dropped". The same page in three browsers (tmp/scratch probe, 2026-11-13): Chrome 157.0.8103.51 runs the callback for an in-tree span registered and dropped; Firefox 159.0.1 does not (Gecko preserves such a wrapper on purpose: bugzilla.mozilla.org 1642685); WebKit keeps a wrapper whose node an opaque root reaches (source; a hidden Safari would not run the probe). Two web searches found no Chromium issue for the in-tree run (2026-11-13). The integrator's ruling (golden rule 2: the browsers split, the majority and the spec agree): Crane starts V8 with `--no-handle-weak-ref-weakly-in-minor-gc` (src/runtime/engines/v8/snapshot_loader.zig RUNTIME_V8_FLAGS, with the evidence), which restores 13.1's rule; with it the file is 9 of 9.

The same merge found four more dated readings in comments that the upgrade had moved, each caught by a test or a static_assert that named its version: the anchor's size (Object::Wrap now takes a `v8::Object::Wrappable*`, a vptr: 24 -> 32 bytes with its header), TryResetRoot (never called on 13.1; called from V8's workers on 15.7), cppgc's idle tasks (gone: the sweeper uses a low-priority foreground runner, so batch 10's idle periods had no client), and a dead wrapper's CppHeapPointerTable entry (born unmarked on 15.7: one full collection, not two).

**Fix**:
1. Write the identity contract as tests against the ENGINE's answer, not against the design's sentence: `v8_test_NodeTemplateWrapperDroppable` asks V8 itself whether it drops the binding's wrapper shape after each use script could make of it. The upgrade then fails a named test instead of shipping a behaviour change.
2. Put a `static_assert(V8_MAJOR_VERSION == ...)` beside every rule read from one version's source (the roots handler's contract had one; it sent the merge to re-read traced-handles.cc before it compiled).
3. On an upgrade, grep the adapter for the old version string and re-read each cited function at the new version; update the citation or the code. A comment that still says "13.1.203" after the upgrade is an unverified claim.
4. When the engine's new behaviour is a browser's too, measure the three browsers before choosing (here Chrome had inherited the change and the other two had not).

**Takeaway**: **A rule you read out of the engine's source is a fact about one version. Pin it with a test that asks the engine, stamp it with a version assert, and after an upgrade re-read every one - the collector's rules about what it may drop are behaviour script can observe.**
