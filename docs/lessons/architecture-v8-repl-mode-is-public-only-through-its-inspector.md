# Architecture: V8's REPL mode is public only through its inspector, and it answers from a promise job

**Date**: 2026-11-03
**Lesson**: A browser console needs V8's REPL scripts (top-level `await`, `let` declared again). V8 13.1 has them only behind its inspector - Runtime.evaluate with `replMode` on a V8InspectorSession - and the inspector answers from a promise reaction, so the engine operation hands the outcome to reaction steps, never to a host promise, and the inspector it needs writes to the page unless told not to.

**Why**: v8::debug::EvaluateGlobal's repl flag is internal (src/debug/debug-interface.h), and the one public C++ shortcut, V8InspectorSession::evaluate, passes `repl_mode=false` (13.1.203 v8-inspector-session-impl.cc:525). A REPL script always completes through a promise of `{".repl_result": value}` (parser.cc WrapREPLResult): the wrapper is what keeps a completion value that is itself a promise from being adopted. The inspector unwraps it in ProtocolPromiseHandler::thenCallback (injected-script.cc) and only then calls the channel's sendResponse - from a promise job, at a microtask checkpoint, or inside the dispatch for input that does not parse.

**What Happened**: tools/repl.zig had rebuilt REPL mode as text rewriting (any input containing "await" wrapped in an async IIFE; `const {a} = await f()` turned into `globalThis.{a} = ...`, a SyntaxError; `let` became a property of the window), and waited by polling microtask checkpoints, so `await fetch()` and timers never settled. Lane console1 replaced it with one protocol operation, `engine.evaluateReplScript`, built the way Deno's REPL is (cli/tools/repl/session.rs: an in-process session, Runtime.evaluate with replMode) - and found three things reading 13.1.203's sources before building:

1. The answer is asynchronous, so the operation's outcome reaches `PromiseReactionSteps` (fulfilled / rejected / dropped, exactly one). Returning an `Owned` promise that the adapter resolves with the value would ADOPT a thenable completion value: `Promise.resolve(1)` would print `1` - the very thing `.repl_result` exists to prevent. The old repl did exactly that (RED: it printed `1`).
2. Telling the inspector about a context changes the page: InspectedContext's constructor installs `console.createTask` on the context's `console` (inspected-context.cc, installAsyncStackTaggingAPI), and the inspector draws its ids from the isolate's random number generator unless the client answers `generateUniqueId` - the generator a seeded agent's Math.random is seeded from. The session deletes `createTask` again and answers ids from a counter of its own.
3. The inspector has an end order. Its promise jobs read `v8::debug::GetInspector(isolate)` and dereference it, so it must outlive every microtask checkpoint of the agent; and a context it knows holds a weak handle whose second-pass callback (contextCollected) would not run once the agent's task runner is closed. So the agent's end forgets every known context (contextDestroyed) and drops every waiting evaluation BEFORE its realms end and its collections run, and deletes the inspector AFTER its last checkpoint, before the isolate is disposed. A realm's end forgets its own context the same way, through the realm's finalizer list.

**Fix**: src/runtime/engines/v8/protocol_repl.zig (per-agent `Session` on the AgentRecord, evaluations on their realm's finalizer list) and v8_wrapper.cpp `CraneReplSession` (the client and channel: responses parsed in the session's own plain context, values unwrapped with `unwrapObject`, primitives from `value` / `unserializableValue`, the object group released at the next dispatch). Pinned by tests/v8/repl_script_test.zig and tests/repl/console_test.zig.

**Takeaway**: **An engine feature only its inspector exposes is an in-process session per agent: hand its asynchronous answers to reaction steps (a host promise would adopt them), read what the inspector writes to a context and undo it, and end it after the agent's last checkpoint.**
