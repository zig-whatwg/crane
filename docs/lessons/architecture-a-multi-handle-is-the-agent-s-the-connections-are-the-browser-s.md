# Architecture: A curl multi handle is its agent's; the connections are its Browser's

**Date**: 2026-10-12
**Lesson**: Split network state by who may touch it: what one thread drives (a curl multi handle, the fetches its loop delivers) belongs to the agent whose event loop pumps it; what every thread of a Browser shares and no other Browser may (connections, DNS, TLS options, proxy, WebSocket's CONNECTING gate) belongs to the Browser, behind locks.

**Why**: A curl multi handle may be driven by one thread at a time, and Crane runs every worker's agent on its own thread with its own loop. The instances design (4.2) put "the scheduler and its multi handle, fetches in flight" on the Browser when workers still shared the Browser's thread; one Browser-wide scheduler would have needed one thread to pump every agent's transfers, or a lock around curl's own iteration. The connection cache is the opposite: a share every Browser joined let one profile reuse - and observe - another's connections.

**What Happened**: Before lane inst5, the scheduler and the live fetch list were threadlocals (one per thread, so one per agent only by accident - two Browsers driven from one thread would pump each other's fetches), and the curl share, its mutexes, the default TLS options and the handshake gate were process-wide (`setDefaultCertOptions` set one trust store for every Browser; the gate's comment still said the page and its workers ran on one thread).

**Fix**: `fetch.algorithms.AgentFetches` (scheduler + live fetches) on `AgentHost.fetches`, pumped by that agent's loop (browser/event_loop.zig, html/worker_event_loop.zig), reached from a realm by `dom.agent_fetches.of(realm)`; `fetch.network.NetworkContext` (Chromium's name) as a BrowserScope supplement with the connection share, TLS options, proxy, user agent and the CONNECTING gate under a mutex; a request carries its client's context as it carries the cookie jar. The curl parts live in the platform's kit, where the platform boundary says curl belongs (src/platform/kit/curl/share.zig - the share with locks of its own, found through CURLSHOPT_USERDATA - and options.zig, which applies a Browser's proxy, TLS and user agent to fetch's and WebSocket's handles alike); fetch holds them opaquely, so no new curl reference appears outside src/platform. curl's global init went to crane.Process.

**Takeaway**: **Choose a network object's owner by its thread rule: single-threaded handles go to the agent that pumps them; shared, locked state goes to the Browser - never to a thread, and never to the process.**
