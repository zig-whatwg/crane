# Architecture: An account that was wrong in the useful direction was also doing another account's work - make it true and the collections it asked for stop, with whatever else they swept

**Date**: 2026-11-15
**Lesson**: Before replacing a figure the collector is paced by with a truer one, list every OTHER thing the collections it asked for were cleaning up. Lane wrap1's account told V8 200 bytes for every Event ever wrapped until the next full collection, dead or not. Lane dm3 made it true - a dead Event leaves the figure at the young collection that finds it dead - and the full collections that the false bytes had been asking for stopped. They had also been sweeping V8's own pointer-table entries of the dropped wrappers, 8 bytes each, which only a full collection sweeps: four rows of the attributes page settled 11% to 19% higher.

**Why**: Three accounts tell V8 about a non-node wrapper, and each asks for a different collector. The wrapper's own 16 bytes fill the young space and ask for a YOUNG collection. What the instance holds (200 B for an Event) is external memory and asks for a FULL collection. The pointer-table entry a dropped wrapper leaves behind (V8 15.7.112.43: `CppHeapPointerTable` has one space, swept only in `mark-compact.cc:3419`; the external pointer table has a young space the scavenger sweeps, `scavenger.cc:1809`, the C++ heap's table has none) is told as 8 B of external memory by lane wr1's account and also asks for a full collection. With the instance's bytes never falling, the second account reached V8's limit about every 100,000 Events and its collections swept the entries as a side effect: the third account was never the one that asked. With the instance's bytes true, only the third asks, and 8 bytes a wrapper reach a limit of 64 MB (V8's initial global limit, before any full collection) or of 8 MB over what is alive (after one) thirteen to a hundred times later.

**What Happened**: chat2.local, diagnosis consoles with V8's trace, 6 runs a side, macOS malloc's deferred reclamation off. Main ran 18 to 21 full collections on the attributes page, the lane 4 (the 4 of the page's end). `dom.event-ctor` settled at 68 MB against 61, the three rows after it at 73 against 61 to 63. The split at the last mark (one run a side, the console's own figures): malloc in use 54.1 against 53.8 MB, V8's heap committed 12.6 against 10.6 MB, and the adapter's counter of pointer-table bytes told to V8 (`node_wrapper_table_bytes`) 12.5 MB against 0.5 MB - 1,560,119 anchors freed after a young drop against 707,397. The 12.0 MB between the two counters is the 11.7 MB between the footprints. First reading, before the counter was looked at: "garbage promoted to the old generation", which the V8 heap figures (2 MB) did not support.

**Fix**:
1. For each collection the old figure asked for, ask what it freed that the new figure does not ask for: here `full_gc_count` and `minor_gc_count` at every mark on both sides, then every counter that only a full collection resets.
2. Read the split before naming the cause: footprint, malloc in use, the engine's committed heap, and the adapter's own counters, at the same mark on both sides. A difference that is in none of the first three is in memory the engine holds outside its heap statistics.
3. Report the cost as its own row with its cause; do not put the false bytes back. The honest levers are the collector's (here none: V8 has no young sweep of that table and no public call that asks for one) or the user's ruling on the cost.
4. Expect the gain on the other axis and measure it in the same window: the collections that stopped were CPU (lane wrap1 had paid +10% instructions on `dom.event-ctor` for them).

**Takeaway**: **A wrong figure that asks for too many collections hides every account that depends on those collections. Before making it true, count what each of its collections swept; after, read the split at the same mark on both sides before saying where the memory is.**
