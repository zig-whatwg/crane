# Debugging: A per-call allocation in a lonely size class maps a page every call

**Date**: 2026-10-16
**Lesson**: Under the WPT runner's DebugAllocator, freeing the only live object of a size class empties its bucket, which is unmapped; the next call maps it again. A short-lived allocation per call can cost an mmap and a munmap.

**Why**: `std.heap.DebugAllocator` (tests/wpt_runner/runner_allocator.zig, `never_unmap = false`) keeps one page per size class and returns an empty page to the system. Whether a given call pays that depends on whether anything else keeps the class's page occupied - so two implementations that make the same number of allocations of slightly different sizes can differ several-fold in cost.

**What Happened**: Lane selectors' new parser made exactly as many allocations per parse as the old one (2 for `li`, counted with a wrapping allocator), yet `querySelectorAll('li')` on an empty container cost 5.3 us against 1.8 us at the base, and crane/qs-perf ran ~3% over budget. `sample` on the shard child showed `__munmap` and `__mmap` at the top of the stack under DebugAllocator: the larger AST nodes had moved into a size class nothing else kept alive.

**Fix**: The parsed selector lives only for the call, so dom.selector_matching parses into `std.heap.stackFallback(8192, allocator)`: a typical query allocates nothing. Profile the shard child (`pgrep -f "wpt_runner.*--journal"`), not the supervisor.

**Takeaway**: **Count allocations AND look at where they land: a per-call allocation that empties a DebugAllocator page costs a syscall pair; put call-lifetime data on the stack.**

**Update (2026-11-09, lane wr1 batch 6)**: A size-class neighbour shrinking ELSEWHERE can expose it, with no change to the call that pays. The wrapper redesign's P6 made a MutationRecord's state 128 bytes (about 176 with the old chained Holder) and its holds 24 bytes a node (48), moving both from the 256-byte class to the 128-byte one. `queueMutationRecordInternal`'s interestedObservers list - untouched by P6, 6 x 24 = 144 bytes, allocated and freed by every record - was then alone in the 256-byte class, and crane/ed-mo-parse-page.html (about 27,500 records in one parse) ran 2.25x slower on the runner than P2 and P5. Two eliminations of P6's tracing missed it; one profile named it: `queueMutationRecordInternal` 56.3 samples a run against P5's 4.2, all of it the DebugAllocator's bucket `mmap`, first-touch `memset` and `munmap` (disassembly: the `append` at +676 and the `defer deinit` at +4740). To profile a runner page, run it N times in ONE process with no supervisor and no child - `wpt_runner --from-file=<a list naming the page N times> --journal=<file> --wpt-root=... --output=...` - and `sample <pid> 300 1 -mayDie` from launch to exit. Zig 0.17 renamed the fix's allocator: `std.heap.BufferFirstAllocator` over a caller's buffer (the list now takes 16 entries on the stack; tests/v8/wr6_record_queue_alloc_test.zig counts 0 frees in 100 queueings). All of it was the allocator: on the release console (libc malloc; x7 rotated) the same parse took 54.25 ms on P2, 54.50 on P5, 54.12 on P6 and 54.12 with the fix, while the runner's cost pair read P6 at 2.25x P2 (119.9 against 53.2 ms) and the fix at 0.971 (55.4 against 57.0) - so time a runner-only cost on the release console before calling it the change's.
