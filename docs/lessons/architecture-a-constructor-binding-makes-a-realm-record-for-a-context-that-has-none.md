# Architecture: A constructor binding makes a realm record for a context that has none, and the record keeps it alive

**Date**: 2026-11-11
**Lesson**: The V8 constructor binding (binding_plumbing.zig) takes its runtime context from `context_manager.getOrCreateWithIsolate`, which MAKES a realm record for a context that has none: a strong `Global<Context>` and an event loop, kept until the agent ends. So any engine path that constructs a platform object in a context the engine hosts no realm in keeps that context alive. A path that makes platform objects (a DOMException to throw) must first ask whether the context is a realm the engine hosts (`context_manager.get`), as Blink's code requires a `ScriptState` (V8PerContextData) before it wraps.

**Why**: Lane v8up b3e made `conversions.newDOMExceptionFromContext` build a thrown DOMException from the realm's own interface object (the template's instance, `materializeInterfaceObject` + `NewInstance`), where it had read `DOMException` off the context's global. In a bare context the global had no `DOMException`, so the old path fell back to a plain Error and constructed nothing. The new path materialized the interface object there and ran its constructor, and the constructor binding made the record.

**What Happened**: tests/v8/page_realm_operations_test.zig "an exception thrown in a realm does not keep that realm alive" failed on both hosts: "native contexts: 1 before, 2 after the thrower realm was released". Three other tests failed with it, and none of them was a leak: two asserted the old global-property lookup (a test deleted or replaced `globalThis.DOMException` and expected creation to follow it), and "every conversions throw helper leaves no handle behind" counted one handle a throw that was the new DOMException wrapper's WEAK handle in the realm's wrapper cache (`wrapper_cache.armWeak`). Read after a full collection, the count was flat, with or without the fix.

**Fix**: `newDOMExceptionFromContext` returns null (its callers throw the plain Error named so) unless `context_manager.get(context)` finds the realm's record, as `newQuotaExceededError` already required. A navigated-away frame realm keeps its record while script reaches it (`protocol_realms.detach`), so its errors stay its own DOMExceptions. The tests now say what the spec says: a hosted realm makes its own DOMException whatever script did to the global, a context with no realm makes none, and a handle count is read after a collection.

**Takeaway**: **Before a new engine path constructs a platform object, check that the context is a realm the engine hosts: the constructor binding will otherwise make (and keep) a realm record for it. And read a handle count after a collection when the path makes wrappers: their handles are weak until then.**
