# Performance: A second call site can cost a hot function its inlining

**Date**: 2026-11-14
**Lesson**: A rare new path that calls the same function as a hot loop can slow the hot loop by percents even when the new path never runs: LLVM inlines a local function with one call site almost unconditionally, and loses that bonus at the second. Give the rare path its own `noinline` function, and force the shared callee `inline` when the hot loop depends on it being inlined.

**Why**: The style engine's rule loop (`matchContents`) called `StyleMatcher.matches` once, and LLVM inlined it - and, through it, the matcher's combinator walk - into the loop. Lane quick2 added @scope (CSS Cascade 6): a scoped style rule matches through `scopedProximity`, which called `matches` too. Nothing on the style1 benches has @scope, so the new branch is one null test per candidate rule; yet `matches` became an out-of-line call with its own prologue, `matchCombinators` and the matched-list append went out of line with it, and the generic scoped helper, inlined into the loop at its single call site, grew the loop past the inliner's budget for its other callees.

**What Happened**: The cost window (release consoles on chat.local, base main vs the lane) measured per-resolution instructions above the no-style control at +1.5-4.4% on all seven style1 benches - flush, gcsTen and gcsInline over the 3% bar - while perf_bench's 66 rows stayed clean (geomean time 1.0033). A macOS `sample` profile of the flush bench, base console against tip, showed `selector_matching.StyleMatcher.matches` with 205 self samples in the tip and none in the base (inlined there), `matchContents` correspondingly smaller. Making `matches`, `matchesHost`, `matchesSlotted` and `matchesPart` `inline fn`, `scopedProximity` `noinline`, and the unscoped arms of the loops direct calls again brought the seven benches to +0.2-2.0% (chat2, x5).

**Fix**: In a hot loop, keep the common branch's calls the loop's own: put the rare branch behind a `noinline` helper, and where that helper must call the same entry point, force the entry point `inline` (a short wrapper around the shared work) with a comment naming the measurement. Count instructions retired (`/usr/bin/time -l`) on base and tip consoles of the same build line: they are load-independent enough to compare on a busy host, and the per-resolution figure above a control isolates the style work.

**Takeaway**: **Before reaching for an algorithmic cause of a hot-path regression, profile base against tip and look for a function that appears only in the tip: a lost inline shows up as a new symbol, not as a slower one.**
