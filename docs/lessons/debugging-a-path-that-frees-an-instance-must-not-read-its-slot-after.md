# Debugging: A path that frees an instance must not read its slot after - another thread of the Browser takes it at once

**Date**: 2026-11-02
**Lesson**: A Browser's slab is shared by its window thread and every worker thread, and its free list is LIFO, so the slot an instance is freed into is the very next allocation on ANY of those threads; code that frees an instance and then reads it - even only its generation stamp - races that thread's new object.

**Why**: runtime.SlabAllocator is one per Browser (BrowserScope.slab), every thread of the Browser allocates from it under its mutex, and `generationOf` and the lifecycle flags are read without it, on the reasoning "a holder only asks about an object of its own thread, which no other thread frees". True, and not enough: no other thread FREES the holder's object, but once the holder's own thread has freed it, any thread may REISSUE the slot. Single-threaded the read is harmless - it sees the dead generation, and `getNodeBase` answers null - so no unit test and no Debug check saw it.

**What Happened**: Lane tsan1's ThreadSanitizer variant caught a nested dedicated worker's realm teardown (WrapperCache.deinit) reading a slot's stamp (`instance_bridge.getNodeBase` -> `SlabAllocator.generationOf`) while the window thread stamped the same slot for a MessageEvent (mx2_data_worker_test 2/3, tt4_worker_cookie_threads_test 1/3). The cache's sweep freed an entry's instance (`gc.onObjectFreed`) and THEN disposed the entry's wrapper, whose `disposeEntryWrapper` asked the node bridge for the instance's node to clear its wrapper alias. The same free-then-read order was in the weak callback's finalizer, the realm-end clear, and the paths that release a torn-down node's storage. Reissued to a node, the read would have answered the other thread's NodeBase.

**Fix**: `disposeEntryWrapper(entry, .kept | .freed)`: a path that freed the instance says so, and then nothing of the slot is read; `unbindNode` runs only while the stamp is still the entry's. `slotReissued` reads the stamp first and alone, and the stamp itself is atomic, so the "is it still mine?" read of a slot freed earlier is a defined race the holder loses safely. RED without TSAN: the node bridge counts `getNodeBase` calls on a freed slot per Browser (`instance_bridge.deadSlotLookups(scope)`), and tests/v8/tsanfix1_entry_read_after_free_test.zig asserts a realm's end makes none (RED before the fix, GREEN after). The deinit sweep's debug dump, which read every entry's node state through an impl before any check, went too.

**Takeaway**: **After a free, the slot is another thread's. Read everything you need first, free last - and make "freed, then read" countable, because on one thread it is invisible.**
