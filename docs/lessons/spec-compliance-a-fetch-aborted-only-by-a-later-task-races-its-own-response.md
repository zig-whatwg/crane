# Spec Compliance: A fetch aborted only by a later task races its own response

**Date**: 2026-11-10
**Lesson**: When a test expects call X to abort a fetch and the engine passes "most of the time", first check whether X aborts anything at all. If the abort really comes from a later task, the result depends on which is faster, the network or the task chain. Read how the browsers abort it synchronously.

**Why**: "Abort a document" step 2 cancels a fetch and discards the tasks queued for it, so an abort that runs before the response's task always wins. An abort queued behind other tasks only wins while the network is slower than those tasks. Under load the response task can be queued first, and then it resolves the promise.

**What Happened**: html/webappapis/dynamic-markup-insertion/opening-the-input-stream/abort-refresh-immediate.window.js calls fetch() and then document.open() from the frame's onload. The frame's document has a declarative refresh of time 0. Its fetch() cases flipped in generations 179, 184 and 214. On the generation 214 production runner, x40 under --load=28 on server1, the <meta> case failed 6 of 40 runs and the Refresh-header case 8 of 40. Crane's document.open() followed the spec text of step 8 exactly: it stops loading only when the ongoing navigation is a navigation ID, and a refresh that is set up but not yet due is no navigation. So open() aborted nothing. An instrumented x40 under load (std.log.scoped, 80 fetches) showed the real order. Every abort came from the refresh's own navigation in its timer task. That navigation is a navigate, not the reload lane fl3 had patched: open() had set the frame's URL to the entry document's. The timer runs two tasks after the fetch starts, because the lifecycle task queued behind the load event arms it. All 12 fetches that resolved had their response arrive while the load task still ran, so their settle task was queued ahead of that lifecycle task. Blink (Document::open: `IsHttpRefreshScheduledWithin(base::TimeDelta())` -> StopAllLoaders) and WebKit (Document::open: `NavigationScheduler::hasQueuedNavigation()` -> stopAllLoaders) count a time-0 refresh as the navigation to stop. Gecko does not, and passes only because its refresh's own Stop comes first in practice. That is the same race, run on faster hardware.

**Fix**: In Document.call_open step 8, a declarative refresh of time 0 that has not navigated yet counts as an attempt to navigate (golden rule 2: Chrome and Safari against the spec text and Firefox). The refresh is canceled and the navigable stops loading, which aborts the document. The Crane test crane/do1-open-stops-zero-refresh.html forces the window: a data: URL's response is ready at once, so its task is queued before the refresh even starts waiting. Its three cases fail 5 of 5 runs before the fix. After the fix, the upstream file passes 6/6 in 40 of 40 runs under the same load: no fetch() failures, and the XMLHttpRequest cases, which had always timed out, now pass as in Chrome. Before, 6/40 and 8/40 runs failed.

**Takeaway**: **A pass that depends on the network losing a race is not a pass. Name the task that really aborts the fetch, and if it is not the call the test names, read the browsers' version of that call: the deterministic order is usually a synchronous stop there.**
