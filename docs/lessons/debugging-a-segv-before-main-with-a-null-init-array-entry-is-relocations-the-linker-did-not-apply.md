# Debugging: A SEGV before main with a null .init_array entry is relocations the linker did not apply

**Date**: 2026-11-11
**Lesson**: An archive built by another toolchain can carry a relocation format our linker does not read. Zig 0.17's self-hosted ELF linker does not apply SHT_CREL relocations, which Chromium's build emits on Linux, and the resulting executable called address 0 before main.

**Why**: Chromium compiles every object with `-Wa,--crel,--allow-experimental-crel` when it targets Linux with lld (V8 15.7.112.43's build/config/compiler/BUILD.gn:673-679; crbug.com/357878242). The relocations then live in compact `SHT_CREL` sections (`.crel.text`, `.crel.data`, `.crel.init_array.100`), which lld has read since LLVM 19 and Chrome's link consumes. Zig 0.17 links a Debug x86_64 executable (the snapshot generator, every test binary) with its own ELF linker. That linker treated the `.crel.*` sections as unknown, copied them into the output, and applied none of the relocations. A `zig cc` smoke links with LLD, which reads CREL, so it passed and hid the problem.

**What Happened**: Lane v8up b3d ran the first gate of the V8 15.7 port on Linux (server1). `zig build wpt-runner` failed at its first step: `run exe snapshot_generator ... process terminated with signal SEGV`, with nothing printed (Zig's segfault handler is installed in main, and the crash came earlier). The kernel log: `segfault at 0 ip 0000000000000000`. An LD_PRELOAD SIGSEGV handler that printed the words at rsp showed the return address inside `__libc_start_main`, with `_start+0x25` further up, so a pre-main call had gone through a null pointer. `readelf -x .init_array` showed the second of four entries was 0. `readelf -S` listed `[53] .crel.init_array.100 40000014: <unknown>`, as well as `.crel.text` (2.6 MB), `.crel.data`, `.crel.rodata` and `.crel.eh_frame`, all unapplied. The `.comment` section said `zig 0.17.0` with no `Linker: LLD` line. The installed archives held 102,928 `.crel` sections in libv8_monolith.a, plus more in libc++, libbase, libplatform and 3 in librust_v8.a. `ld.lld -r` was tried first as a converter: it keeps an input's CREL. That attempt also rewrote the pinned install's SHA256SUMS in place, losing the old sums.

**Fix**: scripts/build-v8-15.7.sh runs every Linux compile with `CCC_OVERRIDE_OPTIONS='#x-Wa,--crel,--allow-experimental-crel'`. This is clang's driver variable for editing its own command line: `x` deletes the argument and `#` keeps it quiet. The objects carry RELA relocations, args.gn is unchanged, and no V8 or Chromium file is touched. Step `verify` fails on any `.crel` section. Step `smoke` also links the program as a Debug Zig executable with Zig's own linker (`-fno-lld`), and it must run past main. Step `install` builds beside the pinned archive, checks the new one, swaps it in, and keeps the replaced SHA256SUMS.

**Takeaway**: **A SEGV at ip 0 before main, with a null `.init_array` entry, means relocations were not applied: run `readelf -S` on what you link and look for section types the linker does not know (`<unknown>`, `.crel.*`). A smoke test proves only the linker it used. And never rewrite a pinned artifact in place: build beside it, verify, swap, and keep the old sums.**
