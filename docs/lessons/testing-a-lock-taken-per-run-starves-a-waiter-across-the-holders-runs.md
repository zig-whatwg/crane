# Testing: A lock taken per run starves a waiter across the holder's runs

**Date**: 2026-11-03
**Lesson**: A waiter that bounds its wait by ONE hold, while the holder releases and re-takes the lock between consecutive runs, is starved through all of them and gives up although no hold outlasted its bound - lock once for the unit the bound describes, and bound the wait by all of it.

**Why**: flock(2) is not fair. The WPT runner's file lock (tests/wpt_runner/file_lock.zig) was taken per run - each global times each variant of a file - with a bound of one run's ceiling + 30 s, counted from the waiter's first refusal. Between two runs the holder released and re-took the lock within microseconds; the waiter polls every 50 ms, so it almost never won the gap and sat through every run of the holder's file.

**What Happened**: Two "load flakes" of hookfreeze2's A/B (both sides run the same list at once against one wpt serve), queued for lane testfix3 as test budgets that broke under load: crane/fm4-radio-arrow-cost.html, OK 41 -> ERROR 34, and crane/ds1-destination-case.https.html, TIMEOUT 48 -> ERROR 46. Their journal records said why: "Not run: another runner on this host held the file for over 90 s (pid 44797 (running), holding it for 8 s)" and "over 40 s". 20 and 29 variants: the holder's whole file took far longer than one run's bound, though its current hold was 8 s. The tests were never slow; the runner gave up on them.

**Fix**: The runner takes the lock once per file, before its first run, and holds it to the end of the file; the waiter's bound is `file_lock.fileBound(runCount, ceiling, 30 s)` - every run's ceiling and margin. A refusal still journals each run as not run, naming the holder. RED/GREEN, two runners at once against one wpt serve (chat.local, testfix3's window): main's runner pair journalled "Not run ... over 40 s (... holding it for 6 s)" for ds1-destination-case and "over 90 s (... holding it for 12-14 s)" for fm4-radio-arrow-cost; the fixed pair's second runner waited 83 s and 372 s and ran every variant. In the same FULL A/B (old runner as the base, new as the tip, both at once) the only two Crane-test differences were the base side's "Not run" records for those two files - an A/B between a per-run and a per-file locker shows the old side's starvation, never a gain of the new one.

**Takeaway**: **Bound a wait by the unit the holder holds. If the holder may release and re-take between steps, the waiter's bound is the sum of the steps - or take the lock once for all of them.** And read the journal's message before calling a result a load flake: "Not run" is the harness.
