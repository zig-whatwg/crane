# Architecture: A per-use host check asks its cheapest question first - the one that is almost always no

**Date**: 2026-11-06
**Lesson**: A check that a binding runs on every use of a member (a report hook, an observer test, a use counter) must begin with the question that is almost always "no", answered from state the binding already holds - before any realm lookup, incumbent realm or host call. Find what makes the browser's version cheap before shipping yours: it is usually one early return, not a faster lookup.

**Why**: In Crane's V8 adapter every way from a context or an isolate to Crane's state takes the process-wide `agents_lock` and a hash get (`protocol_agents.recordOf`, `context_manager.get`, `getWindowForContext`), and `GetIncumbentContext` allocates a Global. Each is tens of nanoseconds, and a check on a hot member pays it on every use, same origin or not, from the realm's own script too. What the binding already holds - the receiver instance, its `ctx`, the realm's `browser_scope`, the global's internal fields - is a load away.

**What Happened**: Lane coi2 batch 2 added HTML 7.1.3.3's access report check (`report_window_access`) to every CrossOriginProperties(Window) member. Its first cost pair (chat.local, ReleaseSafe, 5 runs a side): about 65 ns per use - a frame's blur() 244 -> 316 ns, and the page's own `window.self === window` 300 -> 495 ns a loop, since the `window` getter's path also looked the Window up (realmWindow) before reporting. Chromium reports from the same generated callbacks (bind_gen/interface.py make_report_coop_access) and pays nothing, because DOMWindow::ReportCoopAccess begins `if (coop_access_monitor_.empty()) return;  // Fast early return. Very likely true.` - monitors exist only on main-frame windows of a browsing context group whose virtual groups have parted. The integrator first read Chromium's call as cross-origin-only; the generator says otherwise, and the early return is the real design.

**Fix**: `runtime.BrowserScope.window_access_monitored`, set by dom.coop_reporting.startMonitoring at the one place virtual browsing context group IDs part ("obtain a browsing context to use for a navigation response" step 9.1), read first by protocol_realms.reportWindowAccess (two loads) and by answerWindowGetter through the global's Window field (null once the realm ends) before realmWindow. Coarser than Chromium's per-window monitors (the whole Browser, never cleared) and it misses no report, because checkAccess returns for equal virtual IDs. Cost pair after (chat.local, 5 runs a side, median ns a loop): with no virtual split a frame's blur() 248 -> 234 and self+closed+length 549 -> 526 (at base), own `window.self === window` 306 -> 326 - the last 10 ns a `window` read is the global's internal-field read, an FFI call where Blink's ToWrappableUnsafe is an inline load; with monitoring on, the check's ~70 ns a use stays. A TARGETED A/B over COOP/COEP/reporting lost no report against the tip without the gate.

**Takeaway**: **Before a per-use check does any lookup, ask the question that is almost always "no" from state the binding already holds; a browser's cheap version is usually that early return.**
