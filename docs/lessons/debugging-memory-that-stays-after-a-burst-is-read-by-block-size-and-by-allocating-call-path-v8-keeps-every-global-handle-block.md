# Debugging: Memory that stays after a burst is read by block size and by allocating call path - and V8 keeps every global-handle block it ever made

**Date**: 2026-11-16
**Lesson**: "N blocks of 10 KB, owner not found" has an owner one command away: run the page under `MallocStackLogging=lite` and read `heap -s` beside `malloc_history <pid> -callTree -invert` at the mark. Here the 10 KB blocks were V8's global-handle node blocks, which V8 never gives back.

**Why**: `heap -s` groups live malloc blocks by size and by the function that called malloc; `malloc_history`'s call tree gives the path above it. V8 allocates global handles in blocks of 256 nodes (15.7.112.43 src/handles/global-handles.cc:41 `kBlockSize`; a node is 32 bytes - V8's own handle-byte count reads 32.0 per weak Global - so a block is an 8.2 KB request, which `heap -s` on macOS 27 shows as a 10,240-byte block). `NodeSpace::Free` returns a node to a free list and takes an empty block off the used list only (:278-288); a block is deleted in `~NodeSpace` alone (:230-234). So the most Global handles an isolate ever held at once is memory for the isolate's life - and in the adapter every `v8_*` call that returns a pointer makes a Global, so a transient handle counts toward that peak like a kept one.

**What Happened**: Lane wrap1 found 110-118 MB of malloc still in use after the perf suite's streams page had dropped everything (200,000 streams alive at once in one task), split it by size - "4,656 blocks of 10 KB, 2,362 slabs of 8 KB, the cache's map 17.8 MB" - and left the 10 KB blocks without an owner. Lane wrap2 ran the page once in each console with stack logging on (untimed, a shared host; bytes and owners only). At the page's end, on main: 40.05 MB in 3,911 blocks from `v8::internal::GlobalHandles::Create` - 1,564 of them made under `v8_Object_GetCatching` <- `streams_js.getMember` (a property read's result), 1,561 under `v8_GetGlobalPrototype` <- `template_registry.wrapInstanceAsV8Object`, 781 under the wrapper cache's own weak handle; 18.4 MB in 2,354 slabs of the Browser's slab allocator; 17.84 MB in one block, the wrapper cache's hash map; 12.6 MB in the bucket arrays of two `std::unordered_map`s of the adapter's weak arms; 9.5 MB in 16 arena blocks. The map and 11 MB of the bucket arrays were this lane's to fix (the map now shrinks; the cache's records no longer enter those maps). The rest were filed with these paths.

**Fix**:
1. Start the console with `MallocStackLogging=lite` (and `MallocLargeCache=0`, so freed memory is not counted as held), stop at the mark, and take `heap -s --showSizes <pid>` and `malloc_history <pid> -callTree -invert` (lane wrap2's `mem_driver.py` STACK_MARKS, `item3.sh`).
2. Read counts as well as bytes: 3,911 x 10,240 B is a block size, and a block size names an allocator.
3. For a container that only grows - V8's handle blocks, `std::unordered_map`'s bucket array, std's hash map, a slab list - the cost of a burst is its PEAK, for as long as the container lives. Either bound the peak (fewer handles alive at once) or give the container a way down (the wrapper cache's map: rebuilt smaller when an eighth is in use).

**Takeaway**: **Do not file "owner not found": the allocating path is one tool run away. And count transient Global handles at a burst's peak - V8 keeps their blocks until the isolate ends.**
