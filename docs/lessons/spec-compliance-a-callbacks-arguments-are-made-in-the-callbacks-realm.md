# Spec Compliance: A callback's arguments are made in the callback's realm, not the invoker's

**Date**: 2026-11-22
**Lesson**: Make any sequence or dictionary a host builds for a callback in F's associated realm (WebIDL invoke steps 5 and 10). Made in the invoking object's realm, it is the wrong realm's object, and in an isolated world it becomes null.

**Why**: WebIDL "invoke a callback function" takes F's associated realm (step 5), prepares to run script there (step 8) and only then converts the IDL arguments (step 10). So a `sequence<T>` argument is "a new Array created as if by []" in the callback's realm, and each platform object in it is its wrapper as seen from there. Blink's generated Invoke binds `script_state` to `CallbackRelevantScriptState()` for its conversions. Crane's engine protocol takes ready-made JavaScript values, so the hosts (the observers) build the Array themselves. They built it in the observer's realm.

**What Happened**: Vue's Puppeteer e2e suite timed out on 27 of 36 tests on the ICU build. Before every click, Puppeteer runs `ElementHandle.isIntersectingViewport` in its utility world: `new IntersectionObserver(entries => resolve(entries[0].intersectionRatio))`. In Crane, `entries` was `null` there, so the promise never settled. The observer, created in the world, belongs to the main realm, so its entries Array was made in the main world. The callback's argument conversion then carried that main-world Array across the world boundary the way any ordinary object crosses (protocol_worlds.acrossWorlds: a structured clone). An Array of IntersectionObserverEntry cannot be cloned, so the clone was null. A puppeteer-core probe showed it: `page.evaluate` (main world) gave Array(1) in Chrome 157 and in Crane; `isolatedRealm().evaluate` gave Array(1) in Chrome and null in Crane. A sweep of all 22 callback invocations found the same pattern in ResizeObserver, MutationObserver, ReportingObserver (the reports) and PerformanceObserver (its callback options). In the main world it also gave the wrong realm whenever the callback was another frame's function.

**Fix**: `dom.callback_sequences.argumentRealm(realm, &callback)` returns `engine.functionRealm(callback.function.value)` (under `exact_function_realm`), falling back to the observer's realm. Each site creates its sequence or dictionary there. Entering F's realm to make the Array also makes each element the world's wrapper (relevantWrapper reads the converting world from the current context). tests/html/fw2_world_callback_sequences_test.zig covers each observer in a world (the Array, `e instanceof` the world's interface, `e.target` the world's wrapper) and the page-observer-with-frame-callback cases. A typed generated invoke that does steps 5 and 10 itself is a 0.2 item.

**Takeaway**: **A callback argument the host builds before invoking is made in F's realm. "The realm of the object that calls back" is the wrong default, and with isolated worlds the wrong realm turns into null. Test every observer from a world and with another realm's function.**
