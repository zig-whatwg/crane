# Workflow: A gate that builds one target cannot see another target's code

**Date**: 2026-10-23
**Lesson**: Every gate built for macOS only, so a Zig 0.16 API removal in a Linux-only branch, a glibc-only C declaration and a libc link that Darwin supplies for free all stayed broken, unseen, until someone built for Linux.

**Why**: Zig analyses only what a compilation reaches, and `switch (builtin.os.tag)` decides at comptime: the `.linux` arm of a switch compiled for macOS is never analysed, so an identifier removed from std (`std.posix.open`) is no error there. The same holds below Zig. A Darwin target links libSystem whatever a module says, so a module that uses `std.heap.c_allocator` without `link_libc` builds on macOS and fails on Linux. Apple's headers declare POSIX functions under a strict `-std=c11`; glibc hides them without a feature-test macro. And a whole module (src/webdriver) that only the `crane` step compiles sat out the migration for the reason in [A re-export does not mean the code is compiled](architecture-a-re-export-does-not-mean-the-code-is-compiled.md): no gate builds that step.

**What Happened**: Lane fontcap1 built for Linux in a container and hit three breaks no gate had seen. Lane linuxbuild1 cross-compiled every step for aarch64-linux-gnu and x86_64-linux-gnu: `src/platform/memory.zig` called the removed `std.posix.open`/`close` (every platform test compile failed); libjpeg-turbo's `setenv` was undeclared under `-std=c11` (100 errors); `zig build lib` lacked libc (5 errors); `zig build crane` failed on macOS too, at `std.heap.GeneralPurposeAllocator`, then `std.process.argsAlloc`, then `std.net` - removed in 0.16, in code only that step compiles. Two more traps sat behind them. First, a cross-compile from macOS resolves `-lsqlite3`/`-lleveldb` when the compiler starts, even with `-fno-emit-bin`, and fails with "searched paths: none" before analysing any Zig, because there is no Linux sysroot. Second, the x86_64 ELF linker rejects the Mach-O V8 archives at startup ("not an ELF file"). So every existing V8 step stopped before it reached the code under test.

**Fix**:
1. Build the target, red first: `zig build <step> -Dtarget=aarch64-linux-gnu -Dplatform=linux` (and x86_64), recording each first error before fixing it.
2. Fix each break with the 0.16 API the macOS path of that code already uses (`std.c` in memory.zig, `std.process.Init` and `std.Io.net` in src/webdriver), and the C define or link line the target needs.
3. Check what cannot link by compiling it without a binary: an executable that nothing installs is built with `-fno-emit-bin`, which analyses all its Zig and still compiles its C++, but links nothing. For a foreign Linux target, give that compile empty shared libraries named sqlite3 and leveldb so library resolution passes (`addCrossLibraryStubs` in build.zig), and never link anything against them. `zig build check-target -Dtarget=<t>` does this; `zig build check-linux` runs it for both Linux targets, in the integrator's merge check, and `zig build test` includes `crane-check`, the host's crane compiled the same way.
4. A Linux container (colima) runs what the cross-compile builds: `zig build test -Dspec=platform -Dplatform=linux` natively on aarch64, and `-Dtarget=x86_64-linux-gnu -fqemu` under qemu-user. Under the build runner's `--listen` protocol, qemu-user SEGVs binaries that pass when run directly. Count direct runs before believing a SEGV seen only through the build runner.

**Takeaway**: **A platform you claim is a target you build in a gate. Code behind a target branch, a libc the OS links for you, and a step no gate runs are all unchecked until that target or step is compiled.**
