# Debugging: Footprint levels that vanish with one malloc magazine are placement, not held memory - count live blocks, calls and call order before looking for a retainer

**Date**: 2026-11-23
**Lesson**: When a ring-off memory row is over the bar and "retained after a full collection", first ask the process what it holds and does: live malloc blocks at the mark, malloc calls by size, and the order of those calls, on the frozen consoles. If all three match the base and `MallocMaxMagazines=1` puts both sides on one level, the gap is where libmalloc's per-CPU magazines left free pages, and no code path keeps anything.

**Why**: perf_bench reads `phys_footprint`. With `MallocLargeCache=0` the small zone's free pages are charged or not depending on which were given back (`footprint -w`: Malloc Small "Dirty" against "Reclaimable"), and with one magazine per CPU that depends on which magazine each free landed in. The fetch page touches about 27.5 MB of small-zone pages while 6.3 MB is live at the end: the 21 MB of free space is split into charged and uncharged pages differently launch to launch, in steps of 0.7 to 1.4 MB. A full collection does not move it - nothing there is garbage - so "collected is higher too" does not mean "retained".

**What Happened**: Lane bind1's B3 (the binding's union conversion rewritten from codegen's tables) read page.fetch 1.038 and fetch.loopback-small 1.030 steady, 1.043 collected, with instructions 0.9998. The first agent ruled out JS handles and escalated on "what does the conversion keep that is not a handle". Measured on the frozen consoles (chat2, the fetch page launched as the memory pass launches it, read at the idle end):
- `heap -s`: 10,246-10,255 live blocks, 6.292 MB, in all 24 launches of tip, base and a second build of base's code. V8's regions (3.03-3.28 MB dirty) and `__DATA` (2.84 MB) equal.
- an interposer counting calls by size (a `DYLD_INSERT_LIBRARIES` dylib of about 100 lines of C over the frozen console: `__DATA,__interpose` entries for malloc, calloc, realloc, valloc, aligned_alloc, posix_memalign and free; relaxed atomic counters per 16-byte size step, main thread apart from the others; a watcher thread writes them out when a request file appears, so the page is read while idle): 14.313 M main-thread calls a launch on both, 560 size buckets, none with the two sides' launches apart.
- the same interposer counting, in a hash table, every run of four consecutive main-thread events (alloc or free, with its size bucket; a free's size from `malloc_size`): 28.32 M events, about 12,900 distinct 4-grams; the tip apart from base's code in 3 of them by 10 calls or more (35 calls), under what base's code shows against itself (6-21 4-grams, 212-758 calls).
- `footprint -w`: the whole spread (17.3-22.0 MB) in Malloc Small's dirty figure; the 20-22 MB launches were the ones with swapped pages (the host was building).
- `MallocMaxMagazines=1`: one level, 0.2 MB wide, on every build - 71 of 74 launches on two hosts (the other 3 swapped); the pair read 0.998 on chat.local (21 launches a side).
On chat.local three builds then showed three level structures on page.fetch: main built in the lane's mirror 17.5-17.9 and 18.2-18.8; main's code built in another lane's mirror 18.2-18.9 only; the tip 17.9-18.5 and 19.3-19.8. The lane's base alone moved its median 1.018 between two passes of the same binary. What stayed unexplained was reported as such: the 19.3-19.8 level was seen only in builds holding the new code (19 of 42 and 1 of 21 launches, against 0 of 105).

**Fix**:
1. Copy the frozen consoles to a host with no timed window (never read a host inside another lane's window - even `ls` and `rsync` move its measurements) and launch the page as the memory pass does (`MallocLargeCache=0`, `collect=1`, cwd the console's directory, stdin held open). At the idle end read `footprint -w -f bytes`, `vmmap -summary`, `heap -s`.
2. Equal live blocks and bytes: nothing is retained. Then count calls by size with an interposer, then call order (4-grams). A per-operation temporary shows as thousands of calls in the rows that run thousands of operations.
3. Run the pair with `MallocMaxMagazines=1` as well. One level on both sides means the levels are magazine placement.
4. Discard launches with swapped pages (`footprint -w`, the Swapped column) before reading levels on a busy host.
5. Say what is not shown. Equal live set, calls and order prove the code holds and does nothing more; they do not prove why one build's launches land on a level another's never visit.

**Takeaway**: **A footprint gap is a claim about pages; ask the allocator what is live, what was called and in what order before reading any conversion path - three equalities and a one-magazine pass turn "what does it retain?" into "where did free pages land?".**
