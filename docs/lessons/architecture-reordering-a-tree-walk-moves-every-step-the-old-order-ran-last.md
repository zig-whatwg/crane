# Architecture: Reordering a tree walk moves every step the old order ran last

**Date**: 2026-11-16
**Lesson**: When an unload walk switched from children-first to parent-first, the parent's destroy (unload step 20) still ran at the end of its own unload, so it now ran BEFORE its children's unload handlers. A handler of the parent's realm then found nothing.

**Why**: In the children-first order (HTML "unload a document and its descendants" as written since 2022), a document's unload is the last thing that happens in its subtree. Its last step, "if oldDocument's salvageable state is false, then destroy oldDocument", could run inside its own unload, because nothing in the subtree ran after it. Lane nav4 changed the walk to the browsers' order: the parent's pagehide and unload first, then its child navigables' documents, inside it (golden rule 2: Chrome, Firefox and Safari all do it, as unloading-documents/001, 003 and 005 show). That kept "destroy at the end of my own unload" as it was, so each parent was destroyed, with its realm, before its children unloaded. In the browsers the document's shutdown comes after its children: Blink's FrameLoader::DetachDocument dispatches the unload events, then LocalFrame::DetachChildren, and Document::Shutdown comes after both.

**What Happened**: Lane nav4's FULL A/B (window 1, 2026-11-15) showed one loss: fetch/api/redirect/redirect-keepalive.any.js went from 12 to 8, deterministically (all three browsers pass 12/12). The test closes a window whose iframe's `unload` listener is a function of the PARENT's realm. That listener reaches the frame through `iframe.contentWindow` and sends a keepalive fetch. With the parent destroyed first, the listener's realm was gone and `contentWindow` was null, so the fetch never ran and the 4 stash asserts failed. None of the batch's target tests covered a child's handler that needs its parent. The full A/B found the loss; the targeted runs did not.

**Fix**: The unload operation takes a choice, `dom.document_lifecycle.UnloadDestroy` (`.now` or `.by_caller`). `unloadLeavingDestroy` runs every step but 20. HTMLIFrameElement's `unloadDocumentTree` walks the tree parent-first with it, raising each document's unload counter. Once the whole tree has unloaded, a second loop destroys each document the bfcache did not keep, children first (the walk's order backwards). It skips a document a handler already destroyed (its generation moved, or `isDestroyed`). tests/html/nav4_unload_tree_test.zig pins it at window close and at navigation: the parent's listener on its frame's window runs, sees the frame's window, and its keepalive fetch reaches the server.

**Takeaway**: **When you reorder a walk to match the browsers, list every step each node ran at the END of its turn under the old order (destroy, release, forget) and ask whether it must now wait for the nodes that come after it. In a tree, teardown waits for the whole subtree. A full A/B catches what the targeted files cannot.**
