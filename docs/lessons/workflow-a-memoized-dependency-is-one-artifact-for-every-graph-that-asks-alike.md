# Workflow: A memoized dependency is one artifact for every graph that asks alike

**Date**: 2026-11-10
**Lesson**: The trap is writing a per-graph setting onto a shared dependency artifact. Zig memoizes `b.dependency`/`b.lazyDependency` by its arguments, so two module graphs that ask for a package with the same target and mode get the SAME artifacts; whatever one graph writes onto them (`root_module.sanitize_c`, a link entry, a macro) is every graph's, and the graph configured last wins - silently.

**Why**: build.zig built one C-library set per graph by calling the same function per graph, and the function took the dependency's mbedTLS and zlib artifacts and set the graph's C sanitizer on them, and added the graph's nghttp2 and Brotli decoder to the dependency's libcurl. The production WPT runner's graph and the bug-finding runner's graph both have ReleaseSafe C libraries, so they passed identical arguments and were handed one mbedTLS, one zlib and one libcurl. A comment above the function said the runner's set was "a second curl dependency instance, since its arguments differ" - true while the runner's C libraries were the only release ones, false from the day a second graph asked in the same mode (lane wptcfg's production/bug-finding split). And nothing compared what a binary links with what its modes say.

**What Happened**: lane wr1 found main's release console (`zig build repl-exe -Dwpt-runner-release -Dcpu=apple_m1`) failing to link on ten `___ubsan_handle_*` from libmbedtls.a: the bug-finding graph's `.full` had overwritten the production graph's `.trap` on mbedTLS and zlib, and a `.trap` console links no UBSan runtime. The runners linked because every runner bundled the runtime, which hid that generation 214's PRODUCTION runner - the build published and timed as "Crane exactly as it ships" - carried full-sanitizer mbedTLS (1,283 functions calling a handler) and zlib (30), plus the 34 handlers of the runtime (`nm` and objdump of the frozen binary on server1). The one libcurl both graphs linked carried each graph's nghttp2 and Brotli decoder, so which copy a binary got was the linker's archive order: the bug-finding runner's nghttp2 was production's `.trap` one, not the `.full` its modes say. Generation 214 was not published as the first production generation.

**Fix**: the dependency's artifact is a recipe, only read: `copyCLibrary` (build.zig) compiles each graph's own libcurl, mbedTLS and zlib from it - the recipe's root module whole (C sources and flags, macros, include directories, link entries, system libraries, frameworks), a config header of its own, the recipe's installed headers - in the graph's mode with its sanitizer. No package declares an option to vary instead (mbedtls: `threading`; zlib: `pie`; curl: none for the sanitizer). nghttp2 takes its sanitizer at creation. The runtime is bundled only for C libraries at `.full` (`CModes.compilesFull`), so the production runner links none, as the console. Two checks hold it, in both directions (production: no `.full` C and no runtime; bug-finding: `.full` everywhere, nghttp2 and Brotli included, and the runtime):
- at the end of every configuration, build.zig walks each build's executable through its modules' link entries to every C library it links, and `checkCLibraries` (tests/wpt_runner/build_mode.zig, pinned by its tests) fails the configuration, naming the artifact, when a library or the root differs from the build's modes, a build links two artifacts of one name, two builds with different modes link one artifact, or a build links the runtime when its modes need none (or the reverse). On main's graph it names 22 problems (38 with `-Dwpt-runner-release`);
- once built, `tools/ubsan_symbols.zig` reads each binary's symbol tables back as part of its own step (`wpt-runner`: none; `wpt-runner-bug-finding`: some; the release `repl-exe`: none).
Writing the check exposed a second crossing: under `-Doptimize=ReleaseSafe` the bug-finding runner shared the shared graph's `.trap` C under modes that say `.full` (`ownCLibraries` now compares the sanitizer too).

**Takeaway**: **A dependency instance is shared by everyone who asks for it with the same arguments: never write a per-graph setting onto it - copy what each graph needs. And check what each binary actually links against what its modes say, at configure time and on the built binary, so a crossing fails the build instead of shipping.**
