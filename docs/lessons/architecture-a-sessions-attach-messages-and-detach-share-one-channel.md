# Architecture: A session's attach, its messages and its detach share one channel

**Date**: 2026-11-22
**Lesson**: Every step of one session's life - attach, each message, detach - and the teardown that frees every session must go through the same ordered channel; when one step takes a channel a pause can hold back while the others take one it runs, they reorder, and a step runs on a session that is not there yet or is already freed.

**Why**: The Browser thread has two queues: ordinary tasks (`BrowserHost.post`) and session messages (`host_bridge.postSessionMessage`). Outside a pause they interleave in posting order. Inside a debugger pause (runtime.BrowserPause, policy `.debugger`, Blink's ClientMessageLoop) the nested loop runs session messages and nothing else, so anything posted as an ordinary task waits for the resume while later session messages run first. Blink keeps the three on one task runner for the same reason: "devtools relies on a disconnect handler for detaching and is sensitive to reordering of detach and attach" (third_party/blink/renderer/core/inspector/devtools_agent.cc, DevToolsAgent::AttachDevToolsSessionImpl; IOAgent::AttachDevToolsSession appends the attach to the InspectorTaskRunner, which interrupts a paused or busy V8).

**What Happened**: CDP part 1 gap 6 (lane tpg's test pass): stopping the server while the debugger had the page paused crashed with a general protection fault in host_events.remove, from page.sessionEnded <- PageSession.detach <- DetachTask.run. Closing the connection posted the session's DetachTask as an ordinary task; the server's `uninstallAndWait` went as a session message, ran inside the pause, detached and freed every session - and after the resume the waiting DetachTask detached the freed one. The same split hid a second bug: a client attaching while the page was paused had its AttachTask held back while its first message ran in the pause, found the session not attached, and was never answered.

**Fix**: `AttachTask`, `MessageTask` and `DetachTask` (src/devtools/browser_side.zig) all post through `host_bridge.postSessionMessage`, as `uninstallAndWait` already did: one FIFO, run inside a debugger pause and held during a dialog's. Tests: tests/devtools/cdpt2_browser_test.zig, "gap 6: stopping the server while the debugger has the page paused..." and "a session attached while the debugger has the page paused is answered inside the pause...".

**Takeaway**: **When a loop can run one queue and hold another, every step that touches the same object - its creation, its use, its end, and the teardown that ends it wholesale - goes through the same queue; ordering by "it was posted first" holds only within one queue.**
