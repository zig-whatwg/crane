# Workflow: Measure estimates for timing windows from complete pairs

**Date**: 2026-10-28
**Lesson**: Estimate a protected timing window from measured elapsed time for complete pairs on chat, including all variants and any permitted repeat.

**Why**: A timed window pauses other lanes. Fixture count alone says little about its duration: one radio source expands to twenty URLs, and trusted input actions dominate the elapsed time.

**What Happened**: Row 129 declared an unmeasured estimate of 20–40 minutes for seven pairs over five sources. The first complete pair took about 15 minutes. Each arm included twenty radio variants at about 18 seconds each, plus other controls and checks. That implied roughly 105 minutes for seven pairs and 210 minutes if the predeclared repeat ran. The seven-pair series finished in about 101 minutes, passed, and needed no repeat. The integrator allowed it to finish and required future READY estimates to be measured.

**Fix**: Use a prior equivalent pair or the series's own per-pair elapsed time on chat. Include every expanded URL, both arms, process overhead and verification outside the fixture timers. State the seven-pair duration, the conditional pooled-fourteen duration, and load-wait uncertainty separately. If there is no usable measurement, disclose the missing estimate and ask the liaison about a duration-only rehearsal during an open gap under ordinary runner tokens. Its wall time supplies scheduling evidence; it never enters acceptance statistics. Do not run an ungranted priority timing. Update the ETA promptly from observed throughput without changing the accepted workload or statistical protocol.

**Takeaway**: **A timing window reserves shared resources: measure its duration from complete pairs and every expanded URL.**
