# Debugging: Two executables take different paths through the system allocator for the same calls - split libmalloc out before chasing a small instruction delta

**Date**: 2026-11-12
**Lesson**: perf_bench's instructions per op are a property of the EXECUTABLE, not only of its code. They repeat to within a few instructions for one binary, and differ by tens of instructions an op between two binaries whose code makes exactly the same allocator calls - even between one binary and the same bytes signed again under another identifier. Before reading disassembly for a delta of that size, single-step one iteration in each binary and compare the engine's functions and libmalloc's separately.

**Why**: On macOS the allocator's own path for a given `malloc` or `free` depends on more than the sequence of calls. The measurements below show it follows the executable's identity (its code directory hash): the same call sequence spends a different number of instructions inside `_xzm_xzone_malloc_tiny`, `_xzm_malloc_tc` and `__xzm_xzone_free_to_freelist_chunk`. What inside libmalloc keys on the executable was not read in its source; the measurements are what this lesson rests on. A ratio between two builds therefore carries a term that no change to the engine's code made, and the usual noise row (a build against a byte-identical copy of itself) cannot show it: the copy has the same hash.

**What Happened**: Batch 3 of lane nd2 left a follow-up: `dom.matches-churn` rose 38 instructions an op (1.004) between two commits that differ only in src/dom/attribute_values.zig, "cause not isolated in the disassembly". Batch 5 found it in three steps, on the two release consoles kept for it.

1. Split the row (a scratch page, five runs a side, a minute): the `matches()` half +0; the half that writes a 300-byte attribute value +41 - and +42 at 600 bytes, +41 at 1,200, so a fixed cost per write, not the per-byte flag scan the code suggested. Each console's five runs agreed within 3 instructions: deterministic, not chance.
2. Single-stepped one iteration of the write in each console under lldb, counting instructions per function (tmp/plans/nd2-scripts/b5/stepcount.sh and stepcount.py). 12,659 against 12,500. The engine's own code differed by 7: `Table.intern` +3 (the lookup adapter's `found` out-pointer) and `Table.release` +4 (the ring's `removeAt` inlined - a wider frame, the price of -917 on the values that park). JavaScript, V8 and every other Crane function were equal to the instruction. libmalloc differed by 152, with equal counts in `malloc`, `_malloc_zone_malloc`, `_free` and the Zig allocator shim: the same calls, a longer path. Three consecutive iterations gave the same numbers.
3. Signed the newer console again ad hoc under another identifier (`codesign -s - -f -i <other>`: another code directory hash, the same instructions) and ran the split rows against the original: +15 to +17 on every write row, +23 on `matches`, +56 on `matches-churn`. A second identifier gave -5 to +6; a byte-identical copy -2 to +1 (one row +8).

So the +38 was 7 instructions of code and about 31 of the allocator's, an amount the same binary moves by when it is signed twice. The same term explained three "regressions" in batch 5's own cost table: `attrs.parse-repeated` read 1.0028 against main and 0.9996, 1.0003 and 1.0005 under three other identity pairs, where the step count of that path showed +12 instructions of Crane code in 166,000 and six allocator calls fewer.

**Fix**:
1. Split the row first - its halves, then one input at several sizes. It says which half moved and whether the cost is fixed or scales.
2. Print each run's instructions per op. Equal within a few instructions per binary means the delta is deterministic; then it is the code or the executable, never chance.
3. Single-step one iteration in each binary: a breakpoint on a function entered once per iteration, `thread.StepInstruction` until the same entry, a counter per symbol. About 4 ms a step, so keep the iteration under a few hundred thousand instructions. The console needs a copy signed with `com.apple.security.get-task-allow`. Zig passes an error union's result pointer first, so a `[]const u8` argument's length was x3, not x2: read the registers at the first stop before writing a condition. Run a wall-clock read to its return instead of stepping it (`thread.StepOut()` on `gettimeofday` and `__commpage_gettimeofday_internal`): the commpage read retries until the kernel's time data stands still across it, which never happens at milliseconds a step - a document parse stepped for half an hour inside that loop.
4. Compare the groups separately: the engine's functions, libmalloc's (`_xzm*`, `__xzm*`, the shims), JavaScript, V8 - and the counts of allocator ENTRIES, which are the engine's doing where the instructions inside are not.
5. To confirm an allocator-only delta, sign the same binary again under another identifier and run the row against the original.
6. For a ratio under about half a percent on an allocation-heavy row, measure each side under several identities (tmp/plans/nd2-scripts/b5/cost-id.sh) and report the median and the range - or report the step count's engine-only delta.

**Takeaway**: **An instruction count belongs to the executable: for the same allocator calls two builds - or one build signed twice - differ by tens of instructions an op inside libmalloc. Split the row, single-step one iteration, compare the engine's functions and the allocator's separately, and re-sign the binary to tell the two apart.**
