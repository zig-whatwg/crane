# Architecture: curl's mbedTLS backend parses its CA store for every connection

**Date**: 2026-11-08
**Lesson**: With mbedTLS, curl reads and parses its CA file and its whole CA directory again in each connection's first step, and the bundled curl's build compiles in whatever CA paths the build machine has - so trust is Crane's to load once for each Browser and hand to each of its handles, with curl built to load none.

**Why**: lib/vtls/mbedtls.c `mbed_connect_step1` calls `mbedtls_x509_crt_parse_file(CAfile)` and `mbedtls_x509_crt_parse_path(CApath)` on a fresh chain per connection; unlike curl's OpenSSL backend it has no CA cache (CURLOPT_CA_CACHE_TIMEOUT does not apply). allyourcodebase/curl's build.zig defaults `ca-bundle` and `ca-path` to "auto", which on a native build probes the build machine at configure time: on Linux it found /etc/ssl/certs/ca-certificates.crt AND /etc/ssl/certs (357 entries, the bundle among them); on macOS /etc/ssl/cert.pem. Setting CURLOPT_CAINFO replaces the file but not the directory.

**What Happened**: On server1 (x86-64 Linux, 2026-11-08) a same-origin HTTPS fetch cost ~101 ms of CPU against 1.35 ms over HTTP; curl's CLI (OpenSSL) did the same request in ~3 ms. HTTPS-heavy WPT directories ran 1.6-2.1x slower than on the Macs. On Ubuntu 26.04 (241 entries in /etc/ssl/certs) it was 65 ms per fetch - the cost scales with the directory. macOS paid a smaller share: one bundle file per connection, and the WPT runner's CAINFO replaced even that. With the fix, on server1 (Ubuntu, 30 same-origin fetches through the console, 3 alternating rounds): https 64.9-65.0 -> 8.1-9.1 ms per fetch, user CPU 1.9 -> 0.25 s; http unchanged at 1.2-1.4 ms. Connection reuse was never the problem: WPT's /common/blank.html has no Content-Length, so every client - curl's CLI too - reconnects; against a keep-alive handler 30 fetches open one connection.

**Fix**: build.zig passes `ca-bundle` and `ca-path` = "none" (explicit, never "auto": a configure-time probe of the build machine) - and, because allyourcodebase/curl writes "none" into curl_config.h as a PATH (upstream CMake unsets it; every connection then failed to read a CA file named "none"), leaves both undefined in that header. src/platform/kit/curl/trust.zig's Store, owned by the Browser's network context, parses the system bundle (the distribution's file, first match) plus the Browser's extra anchors the first time a connection asks, and kit/curl's options attach the chain to every handle - transfers and WebSocket handshakes - through CURLOPT_SSL_CTX_FUNCTION (`mbedtls_ssl_conf_ca_chain`). Chrome's shape is a root store per process with additional anchors per network context; the integrator ruled against process-wide state here (no new container-level var): one parse per Browser is still one instead of one per handshake. tests/fetch/trust_store_test.zig pins that curl names no CA file or directory of its own (CURLINFO_CAINFO and CURLINFO_CAPATH null).

**Takeaway**: **A library's per-connection default can be a per-process cost in disguise: profile one connection on each platform, and own the loading of anything that is the same for every connection.** A build option left at "auto" is a read of the build machine compiled into the binary - and check what a dependency's build actually writes for "none" (CURLINFO_CAINFO says).
