# Spec Compliance: A parallel queue run from loop tasks is late by a task per item

**Date**: 2026-11-16
**Lesson**: When Crane runs one of the spec's parallel queues from tasks on an event loop, a task the spec orders after the queue's steps can run before them. Find every such reader and let the queue catch up there; and make a "flake" of this kind deterministic by holding the event loop until the slow side has arrived.

**Why**: HTML's session history traversal queue is a parallel queue ("start a new session history traversal parallel queue" step 2): its steps start when they are appended and wait for an event loop only where they queue a task on one. Crane runs it on the traversable's agent thread, one item per service task (src/html/navigation/traversal_queue.zig). Each service task goes to the back of the loop's task queue, so the queue is late by one task per item ahead, plus every task queued before each of them. A navigation's response task ("attempt to populate the history entry's document" step 5) reads the navigable's ongoing navigation at step 5.1. "Apply the history step" step 8.4 writes it on the queue. In the spec the write has happened by the time the response's task runs. In Crane the response's task could run first.

**What Happened**: html/browsers/browsing-the-web/overlapping-navigations-and-traversals/cross-document-nav-same-document-traversal.html does `location.search = "?1"; history.back()` in a frame, after two fragment navigations. It failed in 5% to 15% of runs under load on server1 (8 of 160, 15 of 160, 24 of 160), never alone on a quiet host, and held generation 225's publication. The trace of a failing run: history.back()'s item was appended behind the second fragment navigation's finalize item, whose service task was already queued. Networking is single-threaded: the request leaves inside navigate, and the response is read by the loop's network step, once per turn. In the failing runs the response was readable at the network step right after the script's task, 0.4 ms after the navigation started. Its task was queued behind the finalize's service task and ahead of the traversal's, which is queued only when the finalize ends. It ran first and marked the navigation as committing; step 8.4 leaves a committing navigation alone; the navigation committed after the traversal, and the test's `step_wait` timed out (3,063 ms against 150 ms). In a passing run the response came a turn later and step 8.4 ended the navigation. Lane nav2 had fixed a real misreading of step 8.4 next to this flake and measured no change (4 of 20 before, 5 of 20 after): the step was right, its timing was not.

Two deterministic forms made it testable. A Crane WPT test holds the event loop for 300 ms after `history.back()`, so the response is there before the next task (tests/wpt/crane/nr1-same-document-back-stops-cross-document-nav.html: 3 of its 4 cases failed in 5 of 5 runs on generation 225's runner, with no load). A Browser test navigates to `about:blank?9`, whose response needs no network, so its task is queued inside navigate, ahead of the traversal's service task (tests/html/nr1_back_stops_navigation_browser_test.zig). Chrome and Safari pass the WPT form in every case; Firefox fails every case and the upstream file.

**Fix**: `TraversalQueue.catchUp` runs the service work the queue has already asked for - each queued item in order until one waits - and nothing appended after the call began. The response's task (HTMLIFrameElement `runCommit`) calls it before it takes its navigation's record and asks whether it is still the ongoing one. The steps are the ones the service task would have run, in the same order, from a task of the same loop; the service tasks already queued find what is left. The alternative - every service task drains all items that finish inline - changes the timing of every traversal against every other task and still loses to a response queued inside navigate.

**Takeaway**: **An "in parallel" queue emulated with loop tasks is behind the loop: before a task reads what the queue's steps write, the queue catches up.** When a result depends on which of two things arrives first, do not repeat the test under load to study it: hold the loop (a synchronous spin after the racing calls) or remove the network (about:blank, blob:) so the "slow" side is always first, and the flake becomes a red test.
