# Debugging: V8 delays a finished marking up to 50 ms for its task - and a burst of the task's own re-runs arms the delay for the next long script

**Date**: 2026-11-24
**Lesson**: A memory row whose peak roughly doubles while live objects, per-object bytes and allocation sites are equal may be V8's completion delay: when an incremental marking finishes inside a running script, V8 waits up to 50 ms for its marking task before the final pause, if its recorded average time-to-task is at most 50 ms. Grep a `--trace-incremental-marking` run for `Completion: Delaying GC via stack guard` before reading anything else.

**Why**: V8 15.7.112.43 `src/heap/incremental-marking.cc`: `AdvanceOnAllocation` (:747) requests the final pause through the stack guard only when `ShouldWaitForTask()` (:571) is false. `TryInitializeTaskTimeout` (:605-670) allows a delay of `max(50 ms, 10% of the marking's wall time)` less the time the scheduled task has already waited, when `GCTracer::AverageTimeToIncrementalMarkingTask()` exists and is at most that allowance. The average is a halving one (`src/heap/gc-tracer.cc` `RecordTimeToIncrementalMarkingTask`: `avg = (avg + sample) / 2`), with one sample per run of the marking task (`src/heap/incremental-marking-job.cc` `Task::RunInternal`). While marking is running the task re-posts itself ("Using regular task based on flags"), and an idle event loop runs each re-post at once: every one is a sample near 0 ms. Three re-runs take an average of 205 ms to 25.6 ms. A task scheduled in the middle of a long script, on the other hand, records the rest of the script: 100 to 300 ms. So the average an embedder with long synchronous tasks holds is a two-valued state, and which value a script meets is decided by how the script before it ended. While the pause is delayed, marking stays open: what the script allocates is allocated black and survives the cycle, V8 computes its next limits from that larger heap, and Crane's structures sized by a peak (the Browser's state arena, which returns no chunk; malloc's dirty pages) keep it.

**What Happened**: Lane rc8's cost pair read `observers.resize-construct` at 1.500 steady / 1.773 peak / 1.408 collected on the tip (9 launches a side, no overlap), in a row whose code the lane does not touch. Two runs disproved retention, a wrapper mark and unreturned allocator pages, and escalated twice with "the tip runs half the collections there, cause unknown". Measurement consoles of both trees with V8's trace (16 traced launches) showed one thing separating high rows from low ones on BOTH sides: V8 printed `Completion: Delaying GC via stack guard, avg time to task: 1.5-25.6ms` in the tip's resize row in 8 of 8 launches (marking then started at a global limit of 27-33 MB) and `Not delaying ..., avg time to task: 141.6-162.1ms` on main in 8 of 8 (limit 14 MB). Main was the delayed side in the mutation-deliver row in 8 of 8 (the pair's 0.829 there) and in the intersection row in 3 of 8 (87.5-90.5 MB against 50.4-51.0). The tip's mutation-deliver row ended with the marking task starting a cycle and re-running three times (204.7 -> 25.6 ms); main's ended 34 ms after a stack-guard finish, one run (153.8 ms). The flip: with V8's marking task off (`--no-incremental-marking-task`, so no delay can happen) the same two binaries read, 5 launches a side: resize 42.4-42.7 against 42.5-42.6 MB settled, 32.8-32.9 against 33.5-33.6 collected; the tip at or below main on all four rows. gc_bench's allocation-site table at the row's end was equal on both sides.

**Fix** (the method; there was nothing to fix in the lane):
1. Build a measurement console of each side that takes V8 flags per run (an uncommitted switch, or `-Dv8-extra-flags`), and run the real page with `--trace-gc --trace-gc-verbose --trace-incremental-marking` under the memory pass's allocator settings, several launches a side.
2. Per row, count `Completion: Delaying GC via stack guard, avg time to task` against `Not delaying`, and read the `[IncrementalMarking] Start (...) global: size / waste / limit` lines: a delayed row's limits climb (9 -> 17 -> 27 MB here), an undelayed row's stay near the floor (9 -> 11 -> 14).
3. Look at the END of the row before: `Job: Run` / `Job: Schedule` repeated in one millisecond is the burst that arms the delay.
4. Prove it by removing the delay on both sides: `--no-incremental-marking-task`. If the rows then agree, the difference was V8's task-wait state, and the evidence goes to a ruling. Never quote a traced console's timings.
5. A row with two levels is reported as levels and counts on both sides (debugging-two-medians-of-a-bimodal-row-compare-coin-flips-list-every-run.md): here the tip also reached the low level and main the high one.

**Takeaway**: **V8 trusts its record of how fast the embedder runs its marking task, and Crane's record flips between "at once" and "after the script". When a row doubles its peak with nothing more kept, find which side V8 was delaying for a task that could not run.**
