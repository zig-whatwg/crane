# Testing: A freed block's poison lasts until its reuse - quarantine it in the detection run only

**Date**: 2026-11-16
**Lesson**: Poison-on-free shows a stale read only while the freed block still holds the poison, and a last-in first-out free list hands the block to the very next request of its size; keep freed blocks out of reuse for a while in the run that exists to detect stale reads, and give that its own switch - a build-mode default changes what every unit test measures.

**Why**: A node's State block goes back to its Browser's arena (`runtime.ArenaAllocator.destroyRaw`), which pushed it on a LIFO free list; `createRaw` zeroed it and gave it to the next node of that size class. So in a poisoning build the 0xdd bytes were readable only between the free and that next allocation. A pointer kept past the free and read after a callback that made one more div found a live, different node - in every build - and nothing could flag it. Lane uaf1's instrument (a liveness test of a NodeBase whose owner word is all poison panics in Debug; continues [A poison byte with a tag bit set reads as the tagged case](architecture-a-poison-byte-with-a-tag-bit-set-reads-as-the-tagged-case.md)) would have been blind in exactly the case the finding was about.

**What Happened**:
1. The arena got a quarantine, AddressSanitizer's shape (compiler-rt `sanitizer_quarantine.h`: freed chunks wait in a FIFO with a byte budget and are recycled oldest first): a freed block is poisoned to the end of its class, waits in one queue per arena (1 MiB), and is checked on its way out - a byte that is no longer the poison is a write after the free, as Zig's testing allocator checks a bucket it releases. A block that left the queue goes on the normal free list, so `createRaw` is the same code in every build.
2. The first version turned the quarantine on with the poison in every Debug scope. The macOS native step then failed 7 of 15,225 tests, and none showed the instrument's panic: `instance_initialization_test` (a recycled block's address), three `nd2_element_name_test` tests (a million dropped elements leave memory where it started; "the next two divs take the freed blocks at once"), `rep1_navigable_lifetime_test` (live bytes per navigable: 643,253 -> 997,181 over 24 navigables), `abort_signal_slot_reuse_test` (its arrangement needs an impostor to take the freed signal's block at once) and `context_counter_test` (realm bytes left after a dispatch). Each depends on a freed block being reissued at once, which is what production does, and 1 MiB of freed state now stayed out of reuse before any came back. (For the last two that reading is from their source: the run's failure text was overwritten by the next job before it was read.)
3. The quarantine became a flag of its own (`ArenaAllocator.quarantine_freed`), set only by `BrowserConfig.poison_freed_state` - the bug-finding WPT runner's Browser. A Debug build's default only poisons (`BrowserScope.poisonsFreedStateByDefault`) and reuses as production does. All seven pass unchanged on that tree (Linux: tests-html 2,793 and tests-v8 1,965 with no failure).
4. Measured with both on (bug-finding runner, lane/uaf1 ff3ce37d1de, server1): 13,683 worklist files, the DOM lifetime list (820 files) three times and 80 lifetime Crane tests three times - no liveness read of a freed node block, no write after a free. That says no test hands a freed block to a liveness test while it is poison; it does not say no code can.

**Fix**:
1. In the detection run, delay reuse: FIFO, a byte budget, poison the whole block, check the poison when the block leaves.
2. Leave the allocation path alone: blocks that left the quarantine rejoin the ordinary free list, so production and detection run the same `createRaw`.
3. Give "poison" and "delay reuse" separate switches. Poison changes no address and no byte count, so it can be a Debug default; delayed reuse changes both, so only the runner that asks for detection gets it.
4. Pin the instrument's question as a function of the build mode (`NodeBase.freedBlockReadPanics(mode, owner)`), since the panic itself ends the process; show the panic once with a scratch test and say so.

**Takeaway**: **Before trusting a poison to expose stale reads, ask how long a freed block keeps it: with immediate reuse the answer is "one allocation". Quarantine freed blocks in the detection run - and only there, behind its own switch, because anything that changes reuse changes what every memory-measuring test sees.**
