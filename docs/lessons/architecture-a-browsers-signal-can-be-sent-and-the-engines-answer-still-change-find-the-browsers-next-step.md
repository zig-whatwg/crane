# Architecture: The browser's signal can be sent exactly and the engine's answer still change - look for the browser's NEXT step at that point

**Date**: 2026-11-12
**Lesson**: When Crane already sends an engine the same notice a browser sends and memory still regressed after an engine upgrade, the notice is not the gap: the engine's answer to it changed. Read what else the browser does at that point, under which condition, and take the narrowest condition that the measurement supports.

**Why**: Crane tells V8 a main frame's context was disposed exactly as Blink does (`ContextDisposedNotification(kNoDependants)`, local_window_proxy.cc:171-241 -> v8_gc_for_context_dispose.cc:65-91, Chromium 157.0.8103.50). V8 13.1 answered by resetting its allocation limits, which made it collect every other page; V8 15.7, with the preconfigured old generation Chrome ships, resets nothing and only arms the memory reducer 30 s away (src/heap/heap.cc:1795-1820). Pages left one after another in a tab then wait for V8's 64 MB global limit: the perf suite's load rows ended at 1.14 to 1.42 of main. Desktop Chrome would hold the same garbage; the difference is that Blink has a second step at that point for a device short of memory: a critical memory-pressure notice when the page being left used much memory and the frame will be reused (v8_gc_for_context_dispose.cc:69-87, set by OomInterventionImpl, oom_intervention_impl.cc:164-166).

**What Happened**: Lane v8up b7 measured that step on one console with a switch, five arms alternating x7 (end memory MB on load.news / docs / app / page-growth; time per navigation against none): none 55.6 / 103.2 / 79.4 / 64.4; every disposal 23.6 / 39.3 / 28.3 / 24.6 at +7.6% to +20.6%; only when V8's heap holds 16 MB 33.8 / 61.5 / 46.9 / 41.0 at +0.3% to +2.2%; at 32 MB never reached; moderate pressure every time as costly as critical. A per-notice log gave the cost: 1.9 to 5.4 ms each, so every-disposal gives back the time the port had won, and the threshold sends one notice in about ten pages. The 16 MB arm shipped as a V8 adapter build option, `-Dv8-navigation-collection-mb`, on with the low-memory default build and off for a desktop build - as Blink's step is on only for a device short of memory.

**Fix**: (1) Confirm the notice is sent (a counter the tests read: `v8_Debug_ContextDisposals`) before designing anything. (2) Diff the engine's handler of that notice between the two versions. (3) Read the browser's function to its end, and find who sets each flag it tests (`SetForcePageNavigationGC` had one caller). (4) Measure every candidate condition as an arm of one binary, with memory AND time per row and the cost of one firing in ms. (5) Ship the narrowest arm that gets the memory back, send it where finalizers may run (the event loop's engine-task step, not inside the realm's end), and pin what must never owe it: a frame, a closed page, a page the back/forward cache keeps.

**Takeaway**: **"We send what the browser sends" answers only half the question after an engine upgrade. Diff the engine's handler, then read the browser's code past the shared notice: the remedy is usually a step the browser already has, under a condition - measure the condition's arms and keep the narrowest one that pays.**
