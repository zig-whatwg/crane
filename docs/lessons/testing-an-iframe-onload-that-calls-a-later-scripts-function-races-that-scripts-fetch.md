# Testing: An iframe onload that calls a later script's function races that script's fetch

**Date**: 2026-11-16
**Lesson**: A page whose `<iframe onload="f()">` comes before the parser-blocking `<script src>` that defines `f` passes only while the script arrives before the iframe has loaded. The parser spins the event loop while it waits for the script, in the HTML Standard and in every browser, so the iframe's load event may fire first. The browsers win that race by fetching the script speculatively; an engine without a speculative fetch runs it level.

**Why**: HTML's "An end tag whose tag name is script" says to spin the event loop until the pending parsing-blocking script is ready. A spun loop runs other tasks, and a child navigable's load is one of them. Nothing orders the iframe's load event after a script that merely follows the iframe in the markup. Chrome, Firefox and Safari request a later parser-blocking script as soon as its bytes arrive (the preload scanner; HTML "speculative HTML parsing"), which is while the parser still waits on an EARLIER script - testharness.js here - and long before the tree builder inserts the iframe. That head start, not the markup order, is why the pattern passes in them.

**What Happened**: html/webappapis/dynamic-markup-insertion/html-unsafe-methods/Document-parseHTMLUnsafe-url.html, -url-base.html, -url-pushstate.html and -url-base-pushstate.html have `<iframe ... onload="window.resolveLoadPromise();">` followed by `<script src=".../parseHTMLUnsafe-url-tests.js">`, whose first line defines `window.resolveLoadPromise`. Crane reported `TypeError: window.resolveLoadPromise is not a function` (a harness ERROR, 6 or 7 subtests lost) on a first attempt in three sweeps under 32-runner load - 2026-11-10, 2026-11-12 and 2026-11-16 - and 10 of 10 OK on every quiet repeat, so each sighting was queued as a flake.
Lane flk2 probed the three browsers with a page of the same shape and a local server that delays one resource (2026-11-16; Chrome 157.0.8103.51 and Firefox 159.0.1 headless, Safari 27.0 in a background tab):
- With the tests script delayed 2 s, all three ran the iframe's onload first - 16 to 33 ms after the script before the iframe, with `typeof window.resolveLoadPromise` "undefined" - threw the same TypeError, and ran the tests script 2 s later.
- The smallest delay that broke them: 25 ms in Chrome, 50 ms in Firefox and Safari. With no delay, 10 loads of 10 ran the script first in each.
- With the page's FIRST script delayed 1.5 s instead, each browser requested the tests script 0.2 to 2 ms after that first script and the iframe's document 1.5 s later: the speculative fetch. With no delay the tests script's request led the iframe's by 12 ms (Chrome), 26 ms (Firefox) and 35 ms (Safari) on average.
Crane suspends the parser and spins the loop as the Standard says (src/html/scripted_parser.zig, `can_suspend`), and has no speculative fetch, so it requests the tests script just AFTER the iframe's navigation began: one response against two in a row (the iframe's document, then its own script), on a server 32 runners share.
The files were adapted from domparsing/DOMParser-parseFromString-url*.html, which have the script BEFORE the iframe. The adaptation swapped the two.

**Fix**:
1. Before treating "the onload ran too early" as an engine bug, ask the question in the browsers with the script made slow: a local server that sleeps before one response, the page reporting its event order back with `fetch`. Headless Chrome and Firefox and a background Safari tab answer in a minute.
2. Log when each REQUEST reaches the server, not only when events fire: the browsers' head start showed there and nowhere else.
3. Pin the agreed behaviour with a test no clock decides: tests/wpt/crane/flk2-iframe-load-during-blocked-parse.html holds the blocking script on the server until the iframe's load handler releases it (resources/flk2-gated-script.py). It passes in the three browsers and in Crane; an engine that kept the child's load back would never release the script.
4. The upstream files are a test bug, filed as web-platform-tests/wpt#65281 (2026-11-16, on the user's approval: put the script first, as the DOMParser originals do). Crane's lasting answer is the queued speculative fetch; until then a first-attempt ERROR on one of the four under load is this race.

**Takeaway**: **Markup order does not order a child's load event after a blocking script: the parser spins the event loop while it waits. When a test passes in every browser by such an order, look for the browsers' speculative fetch before looking for a bug in the event loop - and prove it by making the script slow.**
