# Architecture: V8's platform must outlive exit() - its worker threads still post to it

**Date**: 2026-11-11
**Lesson**: A process that never disposes V8 ends with V8's worker threads still running, and a task on one of them may post to the platform at any moment. A platform held by a C++ static object with a destructor is destroyed by exit() while those threads run, so a post becomes a call through a destroyed object.

**Why**: `static PlatformStart g_platform` held the platform as a `std::unique_ptr<Platform>`. At exit() the static destructors ran: the unique_ptr nulled its pointer, then CranePlatform's destructor nulled its `backend_` and began tearing down DefaultPlatform's workers. V8 15.7's MemoryPool runs `ReleasePooledChunksTask` on a worker, and that task posts its next release with `PostDelayedTaskOnWorkerThread`. That post landed on the half-destroyed CranePlatform. V8 13.1's workers were idle at exit, so the window was rarely hit there.

**What Happened**: In lanes v8up b3b-b3d, tests-v8 processes "exited non-zero AFTER their test passed" under load. It happened 4 times in one macOS run and never when the tests ran one by one, so for two batches it was a flake with no message. The test launcher began printing the exit status and the last 2 KiB of stderr (f7f8152dab5). The first Linux gate then showed 21 of 1,813 processes, each one: `panic: member call on null pointer of type 'v8::Platform'` at `v8_wrapper.cpp PostDelayedTaskOnWorkerThreadImpl: backend_->PostDelayedTaskOnWorkerThread(...)`, under `MemoryPool::PostDelayedReleaseTask <- ReleasePooledChunksTask::RunInternal <- DefaultWorkerThreadsTaskRunner::WorkerThread::Run`. The chat2 full run showed the same trace in 2 processes.

**Fix**: `PlatformStart.platform` is a plain `Platform*` that is made once and never deleted, neither by v8_Platform_Dispose nor at exit. It still lives in the same static, so leak checkers see it as reachable, and the global's declaration (the lint-global-state key) is unchanged. Chrome does the same: gin's V8Platform is a `base::LazyInstance::Leaky`, and Chromium builds with `-Wexit-time-destructors`. Counts on server1 for tests/v8 whole, fresh seeds: with the unique_ptr, 12 and 9 after-exit aborts (21 in the gate run); with the fix, 0, 0 and 0.

**Takeaway**: **Anything an engine's background threads can call - the platform, its task runners - lives for the life of the process: no exit-time destructor. An "exits non-zero after the test passed" flake is a teardown race until the exit status and stderr say otherwise, so make the launcher print them first.**
