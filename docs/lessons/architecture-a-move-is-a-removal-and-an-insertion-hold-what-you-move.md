# Architecture: A move is a removal and an insertion - under counts, hold what you move

**Date**: 2026-10-28
**Lesson**: When a DOM algorithm moves a node it holds no reference to, its removal step leaves the node's tree garbage by the counts until its insertion step; once counts decide lifetimes, the algorithm must hold what it moves across the two.

**Why**: Reference counting (tmp/plans/refcount-design.md) makes a tree garbage the moment its root's total reaches zero, and frees it later through the agent's deferred teardown queue (decision D8). DOM `insert` of a DocumentFragment removes the fragment's children first (insert step 4) and links them under the new parent afterwards; `Range.extractContents`, `replaceAll` (innerHTML, outerHTML, insertAdjacentHTML, setHTML), `selectedcontent`'s clone and the options length setter do the same with nodes nothing else holds. Between the two steps each moved subtree is a parentless tree holding nothing: the counts call it garbage. D8 makes that safe today (nothing is freed before the slice), but step 7's re-check treats a garbage tree held again before its slice as a resurrection - a bug in Debug unless allowlisted (design 1.4 step 2).

**What Happened**: Lane refcount7 built the zombie audit (step 6: `CRANE_REFCOUNT_AUDIT=1`), which runs step 7's schedule beside the old model, marks garbage trees zombie at their slice, and reports reads of zombie nodes and resurrections with their stacks. On all 2,229 Crane tests plus refcount6's 1,233-file list it marked 1,063,315 trees zombie, found zero zombie reads - and 770,500 resurrections. Every printed stack was one shape: `refcount.linkChild` <- `mutation.insert` <- `replaceAll`/`append`/`replace`/`Range.extract`/`selected_content.cloneContents`/`options.appendBlank`. WebKit has no such window: `ContainerNode::insertBefore` with a fragment calls `collectChildrenAndRemoveFromOldParent`, which returns a `NodeVector` - a `Vector<Ref<Node>>` - so the children are held across the removal.

**Fix**: Not in lane refcount7 (mutation.zig was not its file): a step-7 item. Insert takes a counted hold on every node it removes from an old parent (or a fragment) and releases it after the node is linked - one `holderRef` per moved root, released after `linkChild` - so the removed subtree's total never reaches zero. The audit's resurrection count on the same list is the before-number; zero is the after.

**Takeaway**: **A move is a removal and an insertion. Under reference counting, anything that moves a node it holds no reference to must hold the node across the two steps (WebKit's NodeVector of Refs), or the removal makes the tree garbage in between.**
