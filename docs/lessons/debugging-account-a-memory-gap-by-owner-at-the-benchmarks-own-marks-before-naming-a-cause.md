# Debugging: Account a memory gap by owner at the benchmark's own marks before naming a cause

**Date**: 2026-11-12
**Lesson**: A footprint difference between two engine versions is several mechanisms added together. Read it by owner - malloc zones, the engine's heap by space, its C++ heap, the external figure, the collections that ran and their limits - at the marks the benchmark itself reads, on both sides, before proposing any one cause.

**Why**: The V8 15.7 port's perf-suite memory stood at 1.33 of main for three batches. Each batch had one hypothesis from the collector's source (no idle-time collection; the memory reducer's 30 s delay; the removed external-memory interrupt), built a console for it, and disproved or half-confirmed it on a blank page with a hand-written loop. None of them measured the suite's own pages, and the blank-page loop hid two of the four mechanisms (the young generation never grows when nothing survives; no page ever ends).

**What Happened**: One uncommitted measurement patch (SIGUSR1 = dump V8's heap by space, cppgc at the brief level and the external total at the next pump; an environment variable for extra V8 flags) and one script that serves the suite's page, and at every mark the harness posts runs `vmmap -summary` and the dump, beside `--trace-gc-nvp` (15.7 prints each collection's reason, the global consumed size and BOTH allocation limits) gave, in the first hour, four mechanisms with their megabytes: native state of dead wrappers held two scavenge intervals (Malloc Large 70.1 | 113.5 MB); a 24 B cppgc object per aligned pointer in an internal field that only a full collection frees, with none coming under 15.7's preconfigured 32 MB / 64 MB limits (cppgc 0 | 36.6 MB); a young generation of up to 64 MB against 16 MB (new space 16.0 | 63.2 MB on the fetch page); and external-memory-driven collection that starts marking at the limit but collects 32 MB past it. Only the first was Crane's to fix; the other three are V8 15.7's policy as Chrome 157 ships it, which is a ruling, not a bug.

**Fix**: `.v8up/suitediag-b7.py` (lane v8up's scratch tooling; the method is what matters): the harness's page in the console as perf_bench runs it; a mark server that reads the process before it answers; the engine's own statistics on a signal; the GC trace placed between marks by its timestamps; the same on the baseline. Then one-change experiments on ONE console with switches, the whole suite each.

**Takeaway**: **Before reading the collector's source for a cause, print the gap by owner at the benchmark's own marks on both sides - malloc zones, heap by space (committed, physical, used), the C++ heap, the external figure - with the collections between marks and their limits (`--trace-gc-nvp`). A gap that has stood through two disproved hypotheses is more than one mechanism, and a hand-written loop on a blank page shows only the ones it happens to exercise.**
