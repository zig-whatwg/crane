# Architecture: A promise kept past its algorithm keeps what waits on it

**Date**: 2026-11-25
**Lesson**: A spec promise that native code keeps by a strong handle after the algorithm that made it is done roots every reaction still waiting on it - and in Crane a pending streams reaction holds its object - so a promise that never settles keeps those objects until the realm ends.

**Why**: The collector frees a pending promise, and the reactions waiting on it, when nothing reaches the promise. Crane's streams reactions (dom/streams_js.zig `reactHolding`) keep the controller they will run on until their promise settles, and give it back when the promise is collected unsettled. That works only while nothing roots the promise. A `js.Deferred` that an object keeps for its whole life is such a root. When that object is one of the objects the reactions hold, the cycle has a root at each end: the holds keep the object, the object keeps the promise, and the promise keeps the reactions and their holds. In a browser, every edge of that cycle is a traced member or a closure, so the collector sees no root and frees the whole cycle.

**What Happened**: Lane ctor1's failure-family tests (queue item 9: a construction that fails frees what it made) found `new TransformStream({ start() { throw 7; } })` leaving eight platform objects after two full collections: the stream, its controller, both sides and their controllers, and the writable controller's AbortController and AbortSignal. The constructor never released the stream, but that was not the cause. The sides' setup had traced the stream, so it had a wrapper, and its wrapper owned it. The cause was `Stream.start_promise`, a Deferred the stream kept for its life, although Streams 6.2.2 has no such slot: InitializeTransformStream step 1's start algorithm closes over startPromise, and each side runs that algorithm once, during its setup. When start() threw, startPromise stayed pending, so the sides' start reactions held their controllers forever. `start() { return new Promise(() => {}) }` leaked the same way on a construction that succeeded. The red test read platform objects 513 -> 1025 over 64 constructions for each case, and 129 -> 257 for 16 controllers that script kept, used and dropped.

**Fix**:
1. The constructor owns startPromise (`defer start_promise.deinit()`), and `initialize` borrows it for the sides' setups only (`stream.start_promise = start_promise; defer stream.start_promise = null;`). `Stream.deinit` no longer disposes it. "Set up a TransformStream" (§ 9.3) owns its resolved one the same way.
2. The constructor frees the stream and the controller whole on a failed step when no wrapper took them (`releaseIfUnwrapped`). One the setup wrapped is its wrapper's, so a controller that start() was given still works while script keeps it.
3. tests/v8/ctor1_transform_stream_start_test.zig covers all three shapes, plus a ReadableStream/WritableStream guard: their start() throws before any startPromise exists.

**Takeaway**: **Keep a spec promise exactly as long as the algorithm that names it - a local of the steps, not a field of the object - whenever pending reactions hold objects until it settles: a strong handle that outlives its algorithm makes an unsettled promise immortal, and everything waiting on it with it.**
