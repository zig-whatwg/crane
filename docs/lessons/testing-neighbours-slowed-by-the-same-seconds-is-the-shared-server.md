# Testing: Neighbours slowed by the same seconds are the shared server, not the file

**Date**: 2026-11-12
**Lesson**: Before reproducing a file that fails only in full sweeps, look in the same journal for the files that ran beside it: a cluster of neighbouring files all slowed by the same few seconds is a stall in something they share (the host's one `wpt serve`), and the file that failed is only the one whose own time budget is shorter than the stall.

**Why**: Every runner on a pool host talks to the host's one `wpt serve` (tests/wpt_runner/wpt_server.zig adopts whatever answers its port), and each of its children (http :8000, https :8443, ...) is one Python process. A long-running serve's children grew to multi-GB heaps (http 2.27 GB with ~150 handler threads and no connections, https 2.94 GB after ~2.4 days of sweeps) and paused whole-process for ~1.5-2 s (http) and ~4.3-4.7 s (https), a few times per sweep, one child at a time. Every file running at that moment waits the same amount; almost all have budgets of 10 s or more and pass a little later. controlled-iframe-postMessage.https.html has a 2 s `with_iframe` timeout over a worker that answers after a 1 s timer, so it fails whenever a pause of more than ~1 s lands on its frame's fetch.

**What Happened**: The file lost subtests in generation 217's production sweep (2/4, subtests 2 and 3 "with_iframe timed out", 6,445 ms; retry 4/4) - its third sighting, so it held the results site. Replays found nothing: the runner process's own 38-file slice x20, the file alone x40 with 24 spin threads, beside 12 runners looping service-workers/, 8 and 16 concurrent copies: 0 of 168, every run 5.03-5.14 s. Generation 217's own journal had the answer all along: indexes 10599-10635 were slowed by the same ~4.3 s at once (fetch-event-handled 50 -> 4,355 ms; four files' load_ms 14-22 -> 4,001-4,219 ms), and nothing else among 13,146 files moved more than 2.5 s. Counting clusters of >= 4 neighbouring short files slowed > 0.8 s against the previous generation showed 3-5 per sweep in every recent 32-runner sweep, http-only regions ~1.5-1.9 s and https regions ~4.3-4.7 s, the one other-scheme file inside a span never slowed. A probe beside two full sweeps (every 100 ms: the host's oversleep of a 10 ms sleep, fresh-connection GETs over https and http) saw host oversleep 0 ms in every sample and GET stalls in one child at a time (https 4,594 and 4,630 ms; http up to 1,956 ms). Sixteen copies of the file run at once failed together, 16/16, in one pass. After a fresh `wpt serve`: one full sweep had 0 probe stalls and 0 clusters, and 0 of 81 target runs failed (against 16 of 179 on the old serve). A diagnostic runner's timestamps put Crane's own critical path (Handle Fetch -> iframe load) at 1,004-1,014 ms in all 234 frames measured: the worker's 1 s timer plus ~10 ms.

**Why the children pause** (item 0b, the same day): the serve was restarted with a crane-owned `sitecustomize.py` on its PYTHONPATH (nothing under tests/wpt) that logged every garbage collection of 50 ms or more per pid, dumped thread stacks (faulthandler) and the top object types on request, and six full sweeps ran beside the probe. `multiprocessing.util._afterfork_registry` - a WeakValueDictionary - grew by one entry per handler thread that touched the stash: +17.8k entries per sweep in the https child, +6.8k in the http one, every entry keyed by a fresh lambda and pointing at the same long-lived `ForkAwareLocal`. wptserve's Stash proxies cache their manager connection in a `multiprocessing.util.ForkAwareLocal`, a `threading.local` whose `__init__` calls `register_after_fork(self, lambda ...)` - and `threading.local` runs `__init__` once in every thread that touches it, while wptserve's ThreadingHTTPServer makes a thread per connection. The entries never go (their value never dies): CPython python/cpython#70368, open since 2016. Each entry is three GC-tracked objects, so the cyclic collector's pauses grew with them (149 -> 416 ms over five sweeps from a fresh serve), and every probe stall over 300 ms in the window matched one of the https child's logged collections to within ~60 ms. Two days of sweeps make the multi-second pauses item 0 saw. (The http child's ~150 idle threads were a separate test-resource bug: eventsource/resources/message2.py loops forever writing to a closed socket.)

**Fix**: None in Crane. The integrator re-ran generation 217's production sweep on a freshly started serve, and the pool now starts a fresh `wpt serve` per full run (as wptrunner's TestEnvironment starts its servers per run), which bounds the registry to one window's threads (pauses under ~0.4 s, inside the file's 1 s slack; 0 stall clusters in six sweeps).

**Takeaway**: **A file that fails only in full sweeps: first diff the whole journal's durations against the previous generation and look for a cluster of neighbours slowed by the same seconds - if there is one, the cause is the shared server or host, and a latency probe beside the next sweep says which; to find why a Python server pauses, log its own gc pauses from a sitecustomize on its PYTHONPATH and match them to the probe's stalls.**
