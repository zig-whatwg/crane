# Architecture: Return the allocator's free memory from an idle loop, and measure what the OS call really returns before building on it

**Date**: 2026-11-16
**Lesson**: Memory the system allocator keeps after a page freed it is returned away from the allocation path - asked for by an event loop that has had nothing to run for a while, at most once per idle stretch, with a hold-off between releases, and run on a detached thread of its own, never on the loop's - and the OS call that does it must be probed on each OS first: glibc's `malloc_trim(0)` returns hundreds of MB in milliseconds, while macOS 26 and later answer `malloc_zone_pressure_relief` with 0 and return nothing.

**Why**: glibc keeps a freed block that lies between two live ones for the life of the process; no `mallopt` threshold reaches inside a heap, and the thresholds that do return a heap's top slow every large allocation (lane mem2: every fixed pair cost perf_bench's `fetch.loopback-stream` x1.10 to x1.47; `architecture-a-low-glibc-trim-threshold-returns-the-heaps-top-and-maps-every-large-buffer-afresh.md`). The browsers return such memory when the page is idle, not when it allocates: Chrome runs PartitionAlloc's `MemoryReclaimer::ReclaimFast` as an idle-time task every 4 seconds (`base/allocator/partition_alloc_support.cc`), Firefox purges when the main thread has no task left, 500 ms after the memory was last reused (`xpcom/threads/TaskController.cpp`, `MayScheduleMemoryCleanup`), and WebKit calls `malloc_trim(0)` / `malloc_zone_pressure_relief(NULL, 0)` 10 seconds after its process has no visible page and on memory pressure, then refuses the next pressure event for 20 times the release's duration, at least 5 seconds, 30 seconds when under 1 MB came back (`Source/WebKit/WebProcess/WebProcess.cpp`, `Source/WTF/wtf/unix/MemoryPressureHandlerUnix.cpp`). What each OS call returns is not what its documentation says:

- glibc 2.43 (server1), a plain C program: 200,000 blocks of 1,500 bytes written, all but every 64th freed - resident 293.5 MB before and after the frees; `malloc_trim(0)` took 8.4 ms and left 18.8 MB. 4,000 blocks of 64 KiB: 5.1 ms, 250.3 -> 6.2 MB. A second call with nothing to return: 0.02 to 0.43 ms. Writing the same blocks again took 38 ms after a release against 13 ms without one (64 KiB blocks: 34 against 8 ms): a release costs about 0.03 ms per MB returned and about 0.1 ms per MB when that memory is used again. It returns nothing of a free block smaller than a page (2,000,000 blocks of 200 bytes, every other one freed: 414 MB before and after), and `mtrim` trims a heap's top only for the main arena, so a thread arena's free top stays.
- macOS 27.0.1 (chat2.local): `malloc_zone_pressure_relief(NULL, 0)` returned 0 in 1 microsecond in every case. 77 of 286 MB of freed 1,500-byte blocks stayed in the footprint, and all of 250 MB of freed 64 KiB blocks and all of 200 MB of freed 1 MiB blocks (252.3 and 202.0 MB after the frees; a smaller case unchanged after 12 idle seconds). The default allocator's entry for the call is a stub; its freed pages wait in a ring only the kernel drains (`debugging-a-footprint-after-a-burst-of-frees-counts-pages-malloc-queued-for-the-kernel.md`). The one routine that drains the ring on request, `mach_vm_deferred_reclamation_buffer_flush`, is hidden from user programs by the SDK (`mach/mach_vm.defs`, `#if !defined(LIBSYSCALL_INTERFACE)`): called through `dlsym` in a throwaway process it returned 248 of 250 MB (252.3 -> 6.2 MB) - and afterwards the footprint read 8.2 MB with 250 MB written again. Private, and it breaks the footprint's count: not used.

**What Happened**: Lane idle1 was briefed to add a platform operation with "a Linux implementation (malloc_trim(0)) and a macOS one (malloc_zone_pressure_relief)" and a test that resident memory falls on both. Two five-minute probes before any design showed the macOS half cannot lower the footprint through any public call, so the rule was sent to the integrator with that finding instead of being discovered at the red test: the darwin implementation is the public call WebKit makes (it works on older systems and other zones), the footprint assertion is Linux-only, and the macOS footprint went to the queue (Crane's own heap returning its pages; the private flush as a possible user ruling). On Linux the red test read "resident 362 MiB before the frees, 361 MiB after 400 ms idle; 246 MiB were freed" on main.

**Fix**:
1. Probe the OS call with a plain C program on every OS first: write blocks, free all but every Nth (so nothing is at a heap's top), read the resident size (Linux `/proc/self/statm`; macOS `proc_pid_rusage` footprint), call, read again, time it, call again, then write the blocks again and time that too. Three block sizes: under a page, a few pages, 1 MiB.
2. Put the call behind the platform protocol (`platform.releaseFreeMemory(level)`), and the rule for WHEN in one place (`src/browser/memory_release.zig`): the loop's side (`IdleWatch`: nothing to run for 200 ms, counted from the first idle turn after work; once per idle stretch) and the process's side (`Gate`: no release until 20 times the last one's duration has passed, at least 5 seconds, 30 seconds when under 1 MiB came back; claimed with a compare-and-swap, because the allocator is the process's whichever Browser's loop asks).
3. Never from inside a task, and never a timer of the loop's own: an armed timer is pending work, and every host that waits for a quiet loop would wait for it. The step runs at the end of a turn that found nothing to run and adds no clock read to a turn that worked.
4. Never on the loop's thread. The first version called `malloc_trim` from the idle turn; the integrator ruled it out the same morning: the call cannot be interrupted or time-boxed, a worker's reply posted meanwhile would wait for it, and no browser accepts that for a foreground page (Chrome bounds its foreground reclaim to about a millisecond, Firefox's purge yields to a ready task, WebKit hands the darwin call to a background queue). The second version parked one helper thread in the platform, with a mutex, a futex, a pending slot and a stop at the platform's end - and a second new process-wide variable; the integrator asked for the count to stay where it was. The third is WebKit's own shape and needs neither: the loop starts a thread for the one release and detaches it (`platform.spawnThread`, `platform.detachThread`); that thread calls `platform.releaseFreeMemory(level)` and writes the hold-off when it has ended - atomics only. The hold-off record says whether a release runs, so nothing is joined: the process's end waits on the record (`Gate.settle`, from `crane.Process.deinit`), and a host that exits without ending the process exits with a detached thread still running, which no sanitizer reports (an ended thread that was never joined is reported). What is left is an allocation from the arena being trimmed at that moment: say so.
5. Put process-wide state in the process's one record before adding a variable: the hold-off (three atomics) lives in `src/process/start.zig`'s record, the gate in the browser layer is a view of it, and the global-state count did not move.
6. Give each test's loop a gate over a record of its own (`EventLoop.memory_gate`): the process's record holds the next release off for 5 to 30 seconds, which a test repeated ten times in one process (verify mode) or run beside a second Browser would meet. A test waits for the release it started before its record goes out of scope (`Gate.settle`): the release's thread writes to it.
7. State what the call does not reach, in the code and the report: free blocks under a page, thread arenas' tops, everything on macOS 26 and later.

**Takeaway**: **Before designing around an OS memory call, run it in a 60-line C program on each OS and read the resident size before and after: glibc's `malloc_trim(0)` returns what no threshold does, in milliseconds; macOS's `malloc_zone_pressure_relief` returns nothing since macOS 26. Then return memory only when a loop has been idle, once per idle stretch, behind a process-wide hold-off, on a thread that is no loop's - the browsers' rule: an uninterruptible allocator call never sits between a page and its next wake.**
