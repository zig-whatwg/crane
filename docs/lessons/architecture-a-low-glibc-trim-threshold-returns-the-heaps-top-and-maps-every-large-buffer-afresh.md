# Architecture: A low glibc trim threshold returns the heap's top and then maps every large buffer afresh - the memory glibc keeps is what makes its large allocations cheap

**Date**: 2026-11-16
**Lesson**: glibc malloc's moving thresholds keep megabytes of free space at the top of every heap, and fixing the thresholds low gives that memory back at the price of a fresh mapping for every large buffer: no fixed pair was shown to keep both the memory and the time.

**Why**: glibc starts with an mmap threshold and a trim threshold of 128 KiB and moves both when a mapped block is freed (to the block's size, and to twice it: glibc 2.43 `malloc/malloc.c`, `free`). Free space at a heap's top is returned only past the trim threshold, so after one freed 2.5 MiB block each heap may keep up to 5 MiB of free top - and each thread's arena has heaps of its own. But that free top is also what serves the next large request: `_int_malloc` takes a request from the top when it fits (`use_top`) and tests the mmap threshold only when it does not (`sysmalloc`). With no free top every large request becomes its own mapping: an `mmap`, page faults for fresh zero pages, a `munmap`.

**What Happened**: On server1 (Ubuntu, glibc 2.43) the same console read tens of MB more resident than on macOS on rows that free a lot. Lane mem2 ran main b0eb9116cea's frozen console, unchanged, under glibc's own environment settings and read malloc's account per arena through a preloaded library. As glibc starts, the mmap threshold stood at 2.1-2.5 MiB at the end of the attributes, fetch and Event drop-loop pages and at about 21 MiB after the streams page. On the attributes page six thread arenas each held 1.2-5.0 MB of free top and the main heap 3.9 MB: 20.2 MB, against a resident gap of 19.0 MB to a run with fixed thresholds. Fixed at 128 KiB and 128 KiB the memory fell: `dom.event-ctor-dict` 139 -> 118 MB (x0.85), four streams rows x0.94. And `fetch.loopback-stream` (4 MiB bodies read as chunks) went from 7.5 to 11.0 ms a sample, x1.47, in 14 launches of 14 over two quiet windows; the fetch page made 3,712 `mmap` calls against 467. The cost follows the TRIM threshold: with the same 128 KiB mmap threshold and a 4 MiB trim threshold the page made 805. But a higher trim threshold did not make the row fast, it made each launch fast or slow: slow launches were 1 of 7 in one window and 5 of 7 in the next (pooled median x1.10), 4 of 7 with a 32 MiB trim threshold (which also kept 4 MB more on four rows). The first window's median over seven launches, x1.017, had passed the 3% bar. A 1 MiB mmap threshold with a 4 MiB trim threshold kept less of the memory (x0.92 where 128 KiB gave x0.85) and was slow in 2 launches of 7 in its one window; it was not tested again. No source change landed. On the streams page 221-228 MB sat free inside the main heap under both settings measured there, and `malloc_trim(0)` returned 188-195 MB of it.

**Fix**:
1. Do not set glibc's thresholds for the process to get memory back: measure the time of every row that allocates buffers of 128 KiB or more first, on a quiet host. Memory read beside three build jobs was sound; every time read there was not.
2. Find WHERE the kept memory is before choosing a knob: per arena, how much is free top (a threshold reaches it) and how much is free inside the heap (only `malloc_trim` does). A preloaded library that answers a signal with `malloc_info` reads an unchanged binary.
3. Test settings on the unchanged binary through `MALLOC_MMAP_THRESHOLD_` / `MALLOC_TRIM_THRESHOLD_` before building anything; naming any of them also turns the moving off (`MALLOC_MMAP_MAX_=65536` turns it off and changes nothing else).
4. For a row that is fast in some launches and slow in others, count the launches on each side. A median of seven passes with three slow launches and fails with four.
5. Write the acceptance rule before the data, with the count of slow launches in it.
6. Memory glibc keeps is better returned apart from the allocation path - a trim after a collection or on an idle task - than refused on every free. The browsers' own allocators work that way: PartitionAlloc's MemoryReclaimer decommits empty slot spans every few seconds, and mozjemalloc purges an arena's dirty pages once they pass a limit, at once or deferred (WebKit's was not read).

**Takeaway**: **The free space glibc keeps at the top of its heaps is its cache for large blocks: a threshold low enough to return it turns every large buffer into a map, fault and unmap, so return memory at idle instead - and judge an allocator setting by counting slow launches, never by one median.**
