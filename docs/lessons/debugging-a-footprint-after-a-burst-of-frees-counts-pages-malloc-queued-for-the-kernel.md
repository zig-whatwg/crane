# Debugging: A footprint read after a burst of frees counts the pages malloc has queued for the kernel - the side that frees MORE can read LOWER

**Date**: 2026-11-15
**Lesson**: On macOS the system allocator does not return a freed page at once: it lists it in a ring it shares with the kernel, and the page stays in the process footprint until the ring fills or the kernel trims it. A steady-memory row read seconds after a burst of frees therefore compares how often each side's ring filled, not what each side holds. Run the same binaries with `MallocLargeCache=0` before looking for what a change "keeps".

**Why**: macOS's allocator (xzone malloc; the pool's Macs run macOS 27.0.1) uses deferred reclamation: a freed span is entered into a ring buffer, and the kernel decides when to take the pages back. From Apple's published sources (apple-oss-distributions/libmalloc `main`, read 2026-11-15: `src/xzone_malloc/xzone_segment.c`, `xzm_reclaim_mark_free_locked` and `_xzm_reclaim_sync_and_resize`; `xzone_malloc.h`, `XZM_RECLAIM_BUFFER_COUNT_DEFAULT`; `doc/xzone_malloc.md`, "Deferred reclaim"): the ring starts at a default count of 512 entries, rounded up to whole pages; when a free finds it full, the allocator has the kernel reclaim everything in it and doubles it. The kernel side (apple-oss-distributions/xnu `main`, `osfmk/vm/vm_reclaim.c`) samples a ring at most once per 10-second period and trims only what stayed free through a period, or drains it under memory pressure. The zone's `pressure_relief` entry is a stub that answers 0 (`src/malloc_common.c`, `malloc_zone_pressure_relief_fallback`), so a process cannot ask for the drain through `malloc_zone_pressure_relief`. The physical footprint counts every page still in the ring. So after a burst the footprint falls in steps, each a whole ring, and a process whose last frees stop short of filling the ring keeps those pages in its footprint for the rest of a short run - while a process that frees a little more crosses the threshold and reads lower.

**What Happened**: Lane wrap1 batch 3's cost window read the perf suite's streams page 12% higher in steady memory on the lane than on main for the five rows after `streams.reader` (428-432 against 368-373 MB, every run), with the lane's peak lower. Two hypotheses about the wrapper cache were tested and disproved, a third (the kind of collection V8 runs) was proposed, and the lane escalated. The split at the first mark after the burst, main against lane: footprint 368.7 / 439.4 MB; V8's heap with its pooled pages and the C++ heap 209.9 / 199.2; malloc bytes allocated 117.9 / 110.4; malloc dirty-but-free (vmmap's FRAG) 68.4 / 122.6. The lane held less of everything in use. `streams.reader` keeps 200,000 streams alive at once and one full collection frees them; main freed 44 MB more small blocks (the cache's old 88-byte entries and 16-byte boxes). Read every 20 ms, main's footprint fell 608 -> 487 -> 367 MB in two steps and the lane's 536 -> 427 in one. With the consoles started under `MallocLargeCache=0` (the one switch `xzone_malloc.c` reads in every build; it turns the deferral off) the same rows read main 336-338, lane 322-328, and both fell in 20-40 MB steps. That the steps are ring drains is read from the sources and from the step sizes; the ring's entry count was not observed.

**Fix**:
1. At the mark, set malloc's own figures beside the footprint: `malloc_zone_statistics` (in use) from inside, `vmmap -summary` (the zone's ALLOCATED and FRAG) from outside. Equal or lower allocated bytes with higher FRAG is freed memory that has not gone back.
2. Run both sides again with `MallocLargeCache=0` in the process's environment. If the order of the two sides flips or the gap closes, the row is the reclaim ring's timing.
3. Sample the footprint every 20 ms across the burst (`proc_pid_rusage`). Falls of 100 MB in one sample are whole-ring drains; count them per side.
4. Report both readings, and bring the row to the integrator as the allocator's: the change has nothing to fix, and the only way to lower the default reading is to free more.
5. On Linux the same question has another answer (glibc's trim and mmap thresholds): `debugging-a-memory-excess-on-one-host-with-equal-collection-counts-is-the-allocator.md`.

**Takeaway**: **Before asking what a change keeps after a burst, ask whether the OS has taken back what both sides freed: on macOS start both with `MallocLargeCache=0`. A footprint that falls in 100 MB steps is a reclaim ring, and the side that frees more empties it sooner.**
