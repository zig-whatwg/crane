# Architecture: Ask an instance's type before a Browser's table - those tables are the window thread's

**Date**: 2026-11-03
**Lesson**: "Is this instance a node?" and "is it a document?" are questions about its type, and the vtable answers them (`VTable.counted` is `&lifetime.node` for every node type). Looking an instance of any type up in a Browser's per-type InstanceRegistry to find out reads a table that belongs to the window thread. A worker thread asking that about its own objects races the page's node and document churn.

**Why**: A Browser's InstanceRegistry tables (Node's, Document's, ...) are side tables of its BrowserScope, keyed by address, with no lock. Their contract is that every entry is made and freed on the Browser's window thread. The wrapper cache is shared code that runs on every thread of the Browser, and it asked those tables about any instance it held. `treeOwns` called `NodeImpl.getInternalState(instance)` at a realm's end and in its finalizers; `engineHoldsWrapper` called `DocumentImpl.getInternalState(instance)` at every wrap (`shouldBeStrong`). For a worker realm none of those instances is a node, so every lookup was a miss. But a miss still probes the map that the window thread is inserting into, removing from and rehashing.

**What Happened**: Lane gstate4's `-Dsanitize-thread -Dmany-browsers` run caught a data race in tests/html/page_retention_test.zig ("a port transferred to a worker outlives its collected channel"). On the worker thread, `WrapperCache.deinit -> treeOwns -> Node.getInternalState -> Registry.get`. On the window thread, the navigation's `Document.deinit -> Node.deinit -> Registry.remove`. On the base it reproduced in 2 of 10 and 3 of 10 runs. Lane crashes7 wrote a test aimed at the race: a worker wrapping thousands of objects and then ending while its page makes and frees documents and nodes. It raced in 10 of 10 runs, and the race it found first was the other lookup: `URLSearchParams` constructor `-> WrapperCache.set -> shouldBeStrong -> engineHoldsWrapper -> Document.getInternalState`.

**Fix**: Answer the type question first (8f8be07401b). `treeOwns`, `unbindNode` and `engineHoldsWrapper` return at once for `instance.vtable.counted == null`. For a node, `treeOwns` takes the NodeBase from `dom.instance_bridge`, which locks, instead of Node's impl. That also paid an impls-boundary reference. Blink answers the same question from the type: `WrapperTypeInfo::wrapper_class_id` is `kNodeClassId` for a node (platform/bindings/wrapper_type_info.h), with no lookup. `dom.template_contents.ownedByLiveTemplate` already did it this way: it checks `stateAs(DocumentFragment.State)` before its hook.

**Takeaway**: **Code that runs on every thread of a Browser decides an object's kind from its vtable, and touches a per-type table only for an object of that type: a miss in a window-thread table, read from a worker, is still a race.**
