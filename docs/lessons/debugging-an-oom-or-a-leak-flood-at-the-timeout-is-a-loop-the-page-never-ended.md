# Debugging: An OOM or a leak flood at the timeout is a loop the page never ended

**Date**: 2026-10-03
**Lesson**: When one file crashes out of memory or prints thousands of leak reports, and its run lasts its whole timeout, look for a handler that re-arms itself - a load handler that navigates or writes its frame again - and for the missing spec step that should have ended it, before looking at the memory.

**Why**: Each pass of such a loop allocates (a new Window per navigation, a new nested frame per write), and the loop runs until the harness times out: 10 s of passes. A page only stops when its tests complete, so anything that keeps a test from completing - an event never fired, a flag never set - turns a 50 ms pass into ten seconds of allocation. The memory is the symptom; what is missing is the signal.

**What Happened**: After the secfeatures merge, two regressions looked like engine problems:
1. content-security-policy/frame-src/frame-src-blocked-path-matching.sub.html crashed 6/6 with `FatalProcessOutOfMemory` in `createWindowRealm` from `HTMLIFrameElement.runCommit`. Its third test's frame navigates from its own load event to a URL frame-src blocks. A blocked navigation's error document still fires load (HTML "populate a session history entry"), and each is a new Window, so the frame navigated again and again. The tests waited for `securitypolicyviolation`, which never came: navigation requests carried their initiator's policy container but no violation reporter. The previous main TIMEOUTed with 843 native contexts and 993 MB of heap - the same loop, slower because nothing was blocked. Reporting the violation (CSP 2.4.2: the source document's global is the request's client's) ended the page in 51 ms.
2. Chunk aab's leak reports went from 0 to 2,763, and 2,727 of them were content-security-policy/generic/policy-inherited-correctly-by-plznavigate.html alone. Its iframe's onload calls `contentDocument.write()` and `close()`. Once write() ran the document open steps (f4e26fd5f), close() completed the document again, load fired at the iframe again, and onload wrote again. Each pass removed the previous pass's inner frame, whose strings are never freed (an old node-lifetime leak). HTML ends this loop with the "mute iframe load" flag: a document opened while load is being fired at its iframe ("iframe load in progress") fires no further load there. Crane had not modelled it. The same loop is why the ReleaseSafe runner CRASHed on this file in the main-e14d43177-rs sweep: there the old write() appended each pass's inner frame, a realm per pass, until V8 ran out of heap.

A trap on the way: the red Crane test first made its re-navigating frames during parsing, and it crashed with the fix too. HTML says that a frame navigated again while its load event is being handled "will further delay the load event" of its container document, so the page's load never fired and the harness never finished. Make such frames after the page's load event.

**Fix**: (1) a navigation request gets a guarded reporter for its source document's global (`csp_violations.GuardedReporter`, held by the Navigation record), cd5ca339e. (2) Document's "iframe load in progress" and "mute iframe load" flags, through `dom.document_lifecycle` (iframe load event steps 2-3 and 5-7; document open steps step 14), 629007419. Red tests: crane/cf-frame-src-violation-renavigate.sub.html, crane/cf-iframe-onload-write-close-once.html.

**Takeaway**: **A file that dies or leaks at its timeout is usually running a loop: find the handler that re-arms itself and the spec step - an event, a flag - that should have stopped it. The allocation each pass makes is the symptom, not the bug.**
