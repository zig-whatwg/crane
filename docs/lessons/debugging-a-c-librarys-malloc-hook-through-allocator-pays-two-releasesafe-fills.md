# Debugging: A C library's malloc hook through `Allocator.alloc` pays two ReleaseSafe fills per block

**Date**: 2026-11-14
**Lesson**: In safe builds `std.mem.Allocator.alloc` fills every new block with `undefined` (0xaa) and `Allocator.free` fills it again before releasing it, so a C library whose malloc hooks go through them pays two full writes of every block - its ring buffer or window, once per stream - that its own malloc never makes.

**Why**: std/mem/Allocator.zig (Zig 0.17.1-dev+77c319a0f0) does `@memset(byte_ptr[0..byte_count], undefined)` in `allocAdvancedWithRetAddr` (line 326) and `@memset(bytes, undefined)` in `free` (line 475). In ReleaseSafe - Crane's production build - those writes happen. The vtable calls `rawAlloc` and `rawFree` do not fill. A C library initialises what it reads (it must, under malloc), so the fill buys nothing there.

**What Happened**: Lane quick1 b3 moved HTTP content decoding from libcurl into Fetch. The perf pair's `fetch.loopback-br` row stayed at 1.039-1.046x main's instructions after the decoder's 32 KiB stack buffer was fixed (docs/lessons/debugging-in-releasesafe-an-undefined-stack-buffer-is-a-memset-per-call.md). A macOS `sample` of each console reading the 1 MB body for 12 s showed the same Brotli decode cost on both. The tip-only cost was 125 of 2,695 busy samples in memset (`<deduplicated_symbol>`, see docs/lessons/debugging-a-deduplicated-symbol-in-a-sample-profile-is-a-folded-routine.md) under kit/brotli's `Memory.free`. Brotli's ring buffer, about 1 MB per response, was filled on alloc and again on free; on main libcurl gave Brotli plain malloc. A second tip-only cost was 73 samples in four scans of the raw headers per transfer where main made two.

**Fix**: In the C-callback shims only (kit/brotli `Memory`, kit/inflate/zlib.zig `Memory`), call `allocator.rawAlloc(total, .@"16", @returnAddress())` and `allocator.rawFree(block, .@"16", @returnAddress())`. Keep the block's length in the 16-byte header so `rawFree` gets exactly what `rawAlloc` returned, with the same alignment. The allocator still sees every block: a test drops a free and std.testing.allocator reports the leak. The header block is now found once per attempt and shared. After both fixes the br row was 0.998x instructions.

**Takeaway**: **Memory a C library asks for through its malloc hooks goes through `rawAlloc`/`rawFree`, never `alloc`/`free`: in ReleaseSafe the latter write every byte twice. When a ported hot path costs more than the C code it replaces, profile both builds and diff the busy samples per caller before guessing.**
