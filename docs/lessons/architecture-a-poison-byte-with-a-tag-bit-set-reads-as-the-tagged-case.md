# Architecture: A poison byte with a tag bit set reads as the tagged case

**Date**: 2026-11-16
**Lesson**: A word that carries a tag in its low bit, inside memory that is poisoned on release, reads the poison as "tagged" - so a check that branches on the tag can answer quietly for freed memory, in exactly the build that exists to catch reads of it.

**Why**: The arena's poison byte is 0xdd (`runtime.ArenaAllocator.poison_byte`), an odd number. `NodeBase.owner` named either the node's Instance (bit 0 clear) or, for the test-only owner-less nodes, an allocator (bit 0 set). `ownerInstance()` answered null for the tagged form. Node's release writes the poison over the NodeBase in a Debug build and in the bug-finding WPT runner, so there a released node's owner word is 0xdddddddddddddddd: tagged, null. In production the release writes 0: also null. Every `ownerInstance() orelse return` therefore did nothing, quietly, for a released node in both builds - and for a node whose State block had already gone back to the arena's free list, which is a read of freed memory that the poison-read gate never saw.

**What Happened**: Lane wb1 retired the owner-less nodes (node-memory plan v2, X3) and went to remove the tag. The plan was to make the "live-tree" callers panic on a node with no Instance, on the argument that the bug-finding sweep would already have faulted if a released node reached them. It would not have: the poison read as the tag. Reading on, the block's path showed the larger hazard (src/runtime/gc_integration.zig `releaseStorage` -> `ArenaAllocator.destroyRaw` pushes the State block on a last-in first-out free list -> `createRaw` hands it to the next node of that size): a raw NodeBase pointer kept past the free reads a NEW node's owner word and answers "registered" with another node's Instance, in every build.

**Fix**: The batch stayed behaviour-neutral: the reading of the poison as "no Instance" is kept, but as a stated rule - a named bit (`NodeBase.not_an_instance_bit`), a comptime assert against the arena's poison byte, and a test (tests/dom/wb1_withbase_retired_test.zig). The hazard itself went to the integrator's queue with a way to measure it: keep the owner word 0 across the release's poison (as the `live` byte is kept), so that 0 means "released, block still its own" and 0xdd... means "block freed", then panic on 0xdd... in the liveness accessor in poisoning builds and let one bug-finding sweep name the sites.

**Takeaway**: **When a struct is poisoned on release, check what the poison pattern MEANS to every tag, flag and sentinel in it: a poison that decodes as a valid quiet case hides the reads it was written to expose. Before arguing "the bug-finding build would have faulted", read one freed word through the accessor in question.**
