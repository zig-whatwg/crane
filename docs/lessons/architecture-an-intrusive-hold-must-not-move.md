# Architecture: An intrusive hold must not move - and a transient holder needs none

**Date**: 2026-10-24
**Lesson**: A `node_holds` hold (Hold, MemberHold, TaskHold, RefHold) is a link in its node's doubly linked chain (`NodeBase.holds`). Embedded in something that can move - an item of a growable list, a value copied out of a struct - it leaves the chain pointing at the old address, and the next removal or free walks into freed or reused memory.

**Why**: The chain is how a hold survives its node: `nodeReleased` walks it when a node's storage goes and empties every hold on it, so a later `release` writes nothing to the freed node. That needs the hold's address to be stable from link to unlink. Every holder until refcount step 5g embedded its holds in an arena block or a heap state that never moves (a range's state, a collection's state, a task record).

**What Happened**: Refcount step 5g (lane refcount4) gave each item of an event's path a counted reference on its invocation target, WebKit's EventContext `RefPtr<Node> m_node` (Source/WebCore/dom/EventContext.h). The path is an `infra.List(PathItem)` that `dom.event_path.build` appends to, so an append can reallocate it. The first design embedded two chained holds (`RefHold`, 48 B each) in every item and linked them only after the build ended, so nothing moved them. That was safe, but the gc_bench event-churn row measured +79% peak RSS, +22% instructions and +26% cycles against main. An event keeps its path's capacity after dispatch, and `infra.List` keeps four items inline in the event's own state, so every uncollected event carried 104 B more per item. An exactly-sized hold array allocated per dispatch fixed the memory, but still cost +4% instructions locally (one allocation and free per dispatch).

**Fix**:
1. For a short, bounded holder whose storage can move, use a chainless counted reference: `node_holds.CountedRef`, a NodeBase pointer plus the instance's slab generation, 16 B. Its release recognises a node freed under it the way the wrapper's own reference does (`wrapper_cache.releaseCounted`): a reissued slot, or a teardown begun (`instance_lifecycle.isCleanupStarted`). Then the reference is forgotten, never released. With no chain link there is no address to keep stable. Each PathItem carries two (`invocation_ref`, `related_ref`), taken by `EventState.holdPath` once the path is built and released in `clearPath` and `deinit`. Locally (Debug gc_bench, 20,000 cycles) event-churn went from +10.3% instructions (chained holds) and +3.9% (allocated array) to -5.4% against base, with flat RSS.
2. A chained hold (`Hold`, `MemberHold`, `TaskHold`, `RefHold`) stays the right tool for long-lived holders: one whose node can be freed outside the collector while its slot stays live (a realm's coordinated teardown, the final sweep), where `nodeReleased` must find it. Embed one only in storage that does not move until it is released (an arena block, a heap state, a stack frame), and release it on every path that frees that storage.

**Takeaway**: **A chained hold is an address in someone else's list: keep it where nothing moves it. For a transient holder that moves, or lives in many objects at once, use a chainless counted reference with the wrapper's freed-node check - and measure the holder's size where many copies are kept.**
