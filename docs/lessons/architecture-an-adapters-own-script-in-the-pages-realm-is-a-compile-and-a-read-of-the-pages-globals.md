# Architecture: An adapter's own script in the page's realm is a compile and a read of the page's globals

**Date**: 2026-11-13
**Lesson**: Engine-adapter code that evaluates a script of its own to get a value pays a compile wherever the engine's cache is off, and reads whatever the page made of the globals the script names; ask the engine for the value by name, once per realm, and keep one source for it.

**Why**: Evaluating `(async function* () {}).prototype` or `new Date().getTimezoneOffset()` from native code looks like the shortest way to a value the embedder API does not hand over directly. It has two costs that do not show where it is written. The first is time: it is a parse and a compile unless the engine's compilation cache answers, and a flag that turns that cache off - for a reason that has nothing to do with these scripts - makes every one of them real. The second is correctness: the script runs in the page's realm, so `Date`, `Object`, `Symbol` are whatever the page left there. A browser never does this; V8 exposes intrinsics by name (`v8::Intrinsic`, include/v8-template.h) and Blink asks for them through templates (Chromium 157 third_party/blink/renderer/bindings/core/v8/generated_code_helper.cc:166-206).

**What Happened**: After the V8 15.7 port, gc_bench's stream-values row (`new ReadableStream(...).values()`) ran at 1.128 of main's time while stream-reader did not move. A `sample` profile put 21.0% of the main thread under `asyncIteratorPrototype` on the tip against 4.1% on main: `engine.createAsyncIterator` compiled and ran a script on every call to reach %AsyncIteratorPrototype%. The realm already recorded that intrinsic once, when it was made, for exactly this use - and nothing read the record: two copies of one script, the per-call one live. The port had turned V8's compilation cache off (`--no-compilation-cache`; its eval cache answers `new Function()` with another script's base URL and nonce) and measured that as free on the page suite, which has no row that makes an async iterator; the comment recording it said "It costs nothing today because every script carries its own host-defined options" - the adapter's internal scripts carry none. A grep for the same call found Intl's local time zone read the same way, from the page's `Date`, at today's offset: a page that replaced `Date.prototype.getTimezoneOffset` changed what `Intl.DateTimeFormat` printed, and a July date printed in November was an hour off.

**Fix**:
1. Ask by name: one adapter function instantiates a template carrying `SetIntrinsicDataProperty(name, v8::kAsyncIteratorPrototype)` in the realm's context and reads the property. Once per context, the answer kept in the context's embedder data - not a template per call: V8 caches every template's instantiation in the context, by the template's serial number, for up to 1,048,576 of them (src/api/api-natives.cc InstantiateObject; src/objects/templates.h).
2. One source: the realm's record takes it from that function, the operation reads the record, and the second script is deleted. A realm with no record (a ShadowRealm's context) asks the function directly.
3. A source check that only shrinks (tests/infra/v8up_adapter_script_compiles_test.zig): every `v8_Script_Compile` call in the adapter is on a list with its owner, and an unlisted one fails.
4. A value that is the host's, not the engine's - the local time zone - comes from the platform protocol, for the instant in question.

**Takeaway**: **Native code that needs a realm's intrinsic or a host fact never evaluates script for it: the page owns the realm's globals, and the compile is only free while a cache you do not control happens to be on. When a flag is measured as costing nothing, name what the measurement did not exercise - here, every internal compile the adapter makes.**
