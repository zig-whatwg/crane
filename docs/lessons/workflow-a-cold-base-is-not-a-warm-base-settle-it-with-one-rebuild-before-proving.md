# Workflow: A cold base is not a warm base - settle it with one rebuild before proving

**Date**: 2026-11-16
**Lesson**: The first rebuild after a cold build can recompile every engine-linked executable once with nothing changed; a proof's "every compile step a cache hit" holds only against a base built at least twice.

**Why**: The build migration's proof (tmp/plans/build-protocol-design.md 5.1a) reads "every compile step a cache hit" as "the compile commands and their inputs are the base's". That reading needs a cache that has settled. A cold build leaves it unsettled: the next build of the same tree, or of a tree whose difference no compile reads, recompiles some executables once, and only the build after that is all hits. The recompiled macOS executables then differ by hash too (their debug map, UUID and signature: workflow-a-macos-executable-is-not-byte-reproducible-from-a-cold-cache.md), so check C fails as well, for nothing.

**What Happened**: Lane build4 (batch E4, 2026-11-16) made two new mirrors and built main's base cold in each (chat.local: 478 + 331 + 343 s). The first proved commit on chat.local, a build.zig identifier rename whose binary configuration was byte-identical to the base's, ran its 11-artifact build past the 100 s limit and was stopped; the second was stopped too. Run without a limit at the second commit's tree, the main build recompiled repl, the snapshot generator and both WPT runners (crane had been recompiled by the stopped job), gc_bench recompiled, and the release console recompiled 20 of its 34 compile steps - every engine-linked executable, while every C library and libwhatwg_full.a (no engine) were cache hits. Six of the 11 artifacts then differed by sha256. After that, nothing recompiled again: the same tree, a comment-only build.zig change, the base's own tree and the release console then crane all came back cache hits, and a warm re-capture of the base followed by all ten commits was 49/49, 14/14 and 34/34 cache hits with 11 of 11 artifacts hash-equal, every commit. server1 did the same: the first rebuild of main's tree after its cold base (the re-capture itself) recompiled 31 of the 49 compile steps of the 11-artifact set, gc_bench and the release console, and then every commit was 49/49, 14/14 and 34/34 cache hits with 11 of 11 artifacts hash-equal. The cause was not attributed. No compile's cache manifest names a build-side file (searched on the host), so it is not the commits' content. Unverified reading: the cold build compiled some C library twice in parallel under one command (two runner graphs; its summary shows one copy `cached` beside one `success`), the two writers left consumers pointing at different output digests, and the next build settled them - which would also explain the open item "Zig's o/<digest> for five C libraries differs between two cold builds", and the integrator's queued "chat2 recompiles every job" item if that mirror is often rebuilt cold.

**Fix**: In a new or wiped mirror: build the base, then capture and build the base AGAIN (prove.sh with `BASE=<label>` and the base commit as its first label), and prove the commits against that second capture. If a commit's B shows compiles, rebuild its tree once more before reading anything into them: a compile that is a hit on the second build was the cache settling, not the commit.

**Status (2026-11-16, lane build5)**: confirmed on two new mirrors - the first rebuild of main's tree after their cold base recompiled 31 + 1 + 20 (chat.local) and 31 + 1 + 1 (server1) compiles - and narrowed: in those same mirrors, a WIPED cache rebuilt cold and then built again at once was all cache hits the second time on both OSes (97 of 97 compile steps, 11 of 11 artifacts hash-equal to the cold build). In both recompiling cases the mirror was new and the native test step ran between the cold build and the rebuild; which of the two matters is not known. The fix stands: prove against a base whose second build was all cache hits.

**Status (2026-11-17, lane impls9)**: CAUSE FOUND - neither the cold build nor the test step: the mirror's `zig-pkg/` (the packages Zig fetched: curl, mbedtls, brotli...) getting new mtimes. crane-remote's `rsync -a --delete` excludes `/.zig-cache` but not `/zig-pkg`, so whenever the Mac worktree's `zig-pkg/` changes - it appears when something on the Mac runs build.zig in the worktree (Claude Code's zls-lsp plugin does, after an edit of build.zig), or it is absent and `--delete` removes the mirror's own, which the next configure re-fetches - the next job's sync rewrites 9,028 package files with the same content and new mtimes, and every compile that uses them runs again: the C libraries' steps re-run and hit Zig's cache in ~100 ms, the engine-linked executables recompile in full, to the same program. Reproduced on a new mirror (impls9-x, chat.local): a base built cold then again, then base / c1 / base / c1 each in a new job - all cache hits; `touch` of every file in `zig-pkg/` - 32 + 1 + 20 recompiles, this lesson's counts. The compile commands were identical before and after (masked and unmasked), so no proof mask is involved. Fix: crane-remote's sync excludes `/zig-pkg` since 2026-11-17 5:14 AM ET (the integrator), so a mirror keeps the packages it fetched; a proof's base is warm once built twice in that mirror.

**Takeaway**: **Warm means built twice. Prove against a base whose second build was all cache hits; a mirror's first rebuild after a cold build recompiles engine-linked executables once with no change at all, and on macOS changes their hashes. The cause (2026-11-17): the sync rewrote the mirror's zig-pkg/ with new mtimes - keep zig-pkg out of the sync.**
