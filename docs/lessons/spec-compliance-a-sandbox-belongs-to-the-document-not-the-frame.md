# Spec Compliance: A sandbox belongs to the document it was created with, not to the frame

**Date**: 2026-10-16
**Lesson**: Crane kept one set of "allow" flags on the iframe's browsing context, copied from the sandbox attribute as it changed, and only the frame parser ever read it - so a sandboxed document ran every script that did not come from its parser, a CSP `sandbox` reached only the frame's origin, and changing the attribute changed the current document's origin at once.

**Why**: HTML puts the sandbox on the Document. Every Document has an active sandboxing flag set, fixed by the navigation that made it (navigationParams's final sandboxing flag set: the target's creation flags - the iframe's attribute united with the container document's own flags, or a popup's popup sandboxing flag set - united with the response's CSP-derived flags). "Scripting is enabled" asks that set, and so does every other restriction: forms, modals, popups, navigation, document.domain, downloads, autoplay. The iframe's sandbox attribute only parses into the element's iframe sandboxing flag set, which reaches a document at the frame's next navigation. A model with the flags on the frame cannot express any of that: not the nesting (a frame inside a sandboxed document has no attribute of its own), not CSP (the response decides, after the frame exists), not the timing (the attribute changes between documents), and not popups (they have no frame).

**What Happened**: Codex row 46 found `SandboxFlags.blocksScripts()` with no caller. The sandbox lane's red Crane tests showed the reach of it on main 6e25660ace: inside `<iframe sandbox="allow-same-origin">` the embedder could fire `onclick` content attributes, follow javascript: links, navigate the frame to a javascript: URL and run timers on its window; under a CSP `sandbox` even the parser's inline scripts ran; a frame nested in a sandboxed document, and a popup opened from one, ran everything. Two more copies of the same flags existed: a second `SandboxFlags` in security_policies.zig whose navigation check nothing called, and HTMLMediaElement reading the policy container for its own CSP sandbox. A test resource trap hid one CSP case for a while: a `.headers` file is applied only to the path it names with `.headers` (or `.sub.headers`) appended - `foo.headers` is not `foo.html`'s, and a `{{GET[...]}}` substitution needs the `.sub.headers` name, so the frame was served with no policy, or a literal one.

**Fix**: `dom.sandboxing` is the spec's flag set (a set flag restricts, so every combination is a union) with "parse a sandboxing directive", the CSP-derived flags (united across enforced policies, as every engine does) and the creation flags. Document takes its set as a construction argument and answers for it through `dom.document_scripts`; "scripting is enabled" asks it. The frame commit, the initial about:blank, popups, javascript: URL results and the top-level page each compute the set where they make the document, and its sandboxed origin flag makes the origin opaque there - which also decides Window reuse. Every enforcement site reads the document's set; the browsing context keeps only the popup sandboxing flag set and the one permitted sandboxed navigator.

**Takeaway**: **Put a security state on the object the spec puts it on, and fix it where the spec fixes it. A flag kept on a longer-lived object (the frame) cannot say which document it applies to, and every check that reads it there is answering for the wrong document.**
