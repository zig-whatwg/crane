# Architecture: Freeing an object's native half ahead of the collector removes the growth the collector paced itself by - account for what the engine still keeps

**Date**: 2026-11-13
**Lesson**: A collector decides when to run from what it can see growing. An embedder that frees a dead wrapper's native memory early - the right thing for the footprint - also removes that growth, and whatever the ENGINE still keeps for the dead wrapper then accumulates with nothing asking for the collection that would free it. V8 keeps 8 bytes: the wrapper's CppHeapPointerTable entry, swept by full collections only and counted toward no limit.

**Why**: V8 weighs three things against its global limit - the old generation, the C++ heap and the external memory an embedder reports (15.7.112.43 src/heap/heap.cc:5353-5360). In Blink a dropped DOM wrapper's ScriptWrappable stays on the C++ heap until a full collection (BlinkRootsHandler::ResetRoot only clears the reference, platform/heap/thread_state.cc:38-66), so wrapper churn grows the C++ heap, V8 collects, and the same collection sweeps the pointer table (src/heap/mark-compact.cc:3419, the table's only sweep). The wrapper redesign frees a scavenge-dropped wrapper's anchor at once and its node by the counts. Each step was measured and was a win; together they left pure wrapper churn with no growth V8 counts at all.

**What Happened**: The user's churn condition (12,000,000 wrapped divs made and dropped) had stopped the redesign's merge twice. Batch 8 freed the anchors eagerly and the footprint still climbed; batch 10 found the table entries and a V8 13.1 defect that kept them for two collections; on V8 15.7 that defect was gone and the climb was the same - 8 to 9 bytes a dropped wrapper, 137 MiB at the peak against main's 82, two full collections in the whole run where main ran thirty. The cause was not what the table kept but that nothing triggered its sweep. Reporting the entries as external memory through an ExternalMemoryAccounter (8 bytes a dropped wrapper, at the agent's drain) made V8's own limit pace the collection: 75.8 MiB, fourteen collections, time 0.978 of main over the perf suite. Two details decided the result. The report is taken back in the full collection's PROLOGUE: V8 recomputes its limits before its epilogue callbacks (heap.cc:1514, :1604, :1621), and a figure taken back after the collection is still in the size the next limit is set from - that variant's limit alternated 20.2 / 27.8 MB and peaked at 98.4 MiB. And the report is made at a safe point, never from the callback that drops the wrapper, because it can start a collection.

**Fix**:
1. When a change frees something early, list what the collector used to count for that object and what still counts after the change. If nothing does, something of the engine's is now unpaced - find it (here a growth of 8 bytes per object pointed at one table entry) before the footprint probe does.
2. Report the remainder through the engine's accounting API (v8::ExternalMemoryAccounter; JavaScriptCore's Heap::reportExtraMemoryAllocated), sized as what the engine keeps, not as what was freed.
3. Take a report back BEFORE the collection that frees the thing recomputes its limits - on V8 the collection's prologue callback - never after it.
4. Check the fix against the engine's own trace (--trace-gc-nvp: global consumed before and after, and the limit) as well as the footprint: the limit's value shows a ratchet that the peak alone only hints at.
5. A mechanism no browser has needs its reason beside it: both browsers leave the wrapper's native half to the collector, so neither meets the problem.

**Takeaway**: **Early frees are not free of consequences: the collector was using that garbage as its clock. Before removing a growth the engine counts, know what paces the collection afterwards - and if the answer is "nothing", report what the engine still holds.**
