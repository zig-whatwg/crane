# Testing: A test may assume only what the process start makes, and must leave the process as it found it

**Date**: 2026-11-01
**Lesson**: A test helper that caches "started" in a once-flag, enters an isolate for the process, keeps a realm for the process, starts V8 with a bare isolate, or swaps a hook before the process starts makes every later test of its process depend on it; start the process once, as the host does, give each test its own agent, and undo everything else before the test ends.

**Why**: tools/test_launcher runs a suite's tests in any order - a process per test, ten to a process, or the whole suite in one shuffled process. tests-v8 had run in one index-order process for its whole life, so a test could lean on whatever the tests before it left behind, and nothing said so. Process-level state in tests/v8 is the V8 platform and its flags (frozen when V8 starts), the src/dom hooks, the standalone runtime scope (`runtime.initializeRuntime`), each thread's entered isolate, and what the V8 adapter keeps per thread - the context manager, which holds every realm registered on the thread, of every isolate.

**What Happened**: Lane tlaunch2's shuffled whole-suite runs found 162 ORDER-DEPENDENT tests and 22 that failed alone (docs/testing/tests-v8-order-findings-2026-11-01.tsv). Lane v8order1 found five mechanisms, each proven by running the same tests in two orders:

1. **The standalone runtime ended under a once-flag.** 65 helpers kept `var pools_ready` and called `runtime.initializeRuntime` only the first time; 31 tests paired `initializeRuntime(std.testing.allocator)` with `deinitializeRuntime()`, which ends the process's one standalone scope. `urlpattern_protocol_component`, then `om1_numeric_bindings`, then `urlpattern_canonicalization_regression` panicked "a platform object made in a realm no Browser owns, with no standalone runtime"; with `om1_numeric_bindings` first, all six passed.
2. **V8 started without the runtime's flags.** A helper whose first act was `ffi.v8_Isolate_New()` started V8's platform lazily, without `RUNTIME_V8_FLAGS` (ShadowRealm, Float16Array, JSPI), and `initializeEngine` after it cannot add them: wj1_wasm_constructor's JSPI tests failed after `dom_string_to_v8_test`.
3. **An isolate left entered.** 56 files entered a file-level isolate in a once-helper and never exited it, so it was the current isolate of every later test: engine_agent_test's `expectEqual(page, v8_Isolate_GetCurrent())` and engine_runtime_impls_operations' `currentRealm()` failed after them, and contexts were used under another isolate's handle scopes (misaligned reads, TRAPs).
4. **A hook swapped before the process started.** refcount_wrapper_link_test swapped `runtime.lifetime`'s hooks, then its helper's first call installed dom.refcount's over them (the tally saw nothing alone), and the test's end restored "no hooks" over the real ones for every later test.
5. **A realm kept for the process, freed by another test's agent.** Fixing 3 left nothing entered between tests, so every test that made an agent of its own (`urlpattern_realm.Page.open`, `engine.createAgent` with no isolate current) made its thread's HOST agent - and a host agent's end takes down what the adapter keeps per thread (`protocol_agents.endAgent` -> `isolate_lifecycle.cleanupAll` -> `context_manager.deinit()`): every realm registered on the main thread, including the realms 56 files kept there for the process. The next test of such a file read a freed ContextData (segfaults at page-aligned addresses in `getV8WrapperCacheStorage`, `page_realm.contextOf`, "Failed to get runtime context"). Proof: a realm registered, nothing current, `createAgent` + `destroyAgent` - the manager no longer has the realm; with the realm's isolate entered while the agent lives (so it is not the host agent), it does. Before 3's fix a file isolate left entered had hidden this: no per-test agent was a host agent.

The same once-flag mistake survived in four snapshot files after these fixes: each ran only "where this file is the first in its process to start V8", decided by the file's first test and cached in `first_in_process`. In a shuffled process (seed 0x47d641a3) a pattern_attribute_snapshot test ran at position 0, and the file's test at position 583, after other files' isolates, restored the snapshot on the cached "first" and crashed in V8's StringTable::InsertForIsolateDeserialization. Each test now reads `v8_Platform_IsInitialized()` before it starts anything.

Separately, three handle-counting tests failed alone because their measured loop was the isolate's first to tier up: V8 13.1 makes its baseline batch compiler's queue, one 32-byte global handle, on the first Sparkplug enqueue. And context_counter's "an abort inside a listener" left 136-408 bytes of its realm's allocator alone and shuffled, never in index order: a probe recording each live allocation with its return address found one 296-byte block, `HashMap(*Instance, *CacheEntry).allocate` - the realm's wrapper cache growing its map once to hold a window's eight Events until their collection (a map never shrinks; in index order an earlier test had grown it). Every later window left +0, and forty rounds each followed by a collection left 0, so it was one-time, not a leak per aborted dispatch: the test's warm-up was two rounds, not a window of the measured shape.

**Fix**: tests/v8/test_process.zig, which every tests/v8 helper now goes through:

- `start()` starts the process as crane.Process does - `engine.initializeEngine(.{})`, then every hook, claimed through `dom.process_start` - and the standalone runtime when none is running (it reads the real state, never a flag). Call it before anything that starts V8 and before swapping a hook.
- `OwnRuntime.begin(allocator)` / `end()` gives a test a standalone scope of its own and puts the process's back.
- `TestAgent`: every test that needs a realm gets its own agent, made by `engine.createAgent` on its helper's first call (`open`) and ended at the test's end (`close`, through `engine.destroyAgent`) - Blink's fresh isolate per test, through the engine's own path, as a Browser makes and ends its page agent. Made with nothing current, it is its thread's host agent, so its end also takes its realms out of the thread's context manager; what the test made besides (Window realms, contexts, a worker's agent, ContextData) ends before it (`endWith`). Every test of such a file starts with `defer test_agent.close();`, and the file's `reset` clears what it cached of the agent.
- A handle-counting realm tiers up an unrelated loop before any test measures, and a measured window is warmed up by one of the same shape.

A host agent owning the thread's context manager is per-thread engine state with no owner but a thread - global-state debt (docs/instances.md), queued for an engine lane that moves it onto the agent that owns it; the tests do not depend on it either way, because no realm outlives its test.

**Takeaway**: **A test may assume only what the process start makes. Read process state, never cache it in a once-flag; give each test its own agent and end it with the test; give back what you take (a scope, an entered isolate, a swapped hook) before the test ends; and start V8 the way the host does, before anything else touches it.**
