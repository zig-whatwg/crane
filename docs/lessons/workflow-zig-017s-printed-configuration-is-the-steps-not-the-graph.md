# Workflow: Zig 0.17's printed configuration is the steps, not the graph - compare the binary, under one environment, less the option records' padding

**Date**: 2026-11-13
**Lesson**: `zig build --print-configuration` prints every step but not what a compile step compiles; the binary behind `--print-configuration-path` holds all of it, and two configures of one graph differ in that binary only in the environment it records and in three bytes of uninitialized padding per declared option.

**Why**: A change to build.zig that is meant to move code and change no output is proved cheapest by comparing the step graph before and after: seconds, the whole graph, every flag set. The pinned Zig (0.17.1-dev+77c319a0f0) serializes the graph (std/Build/Configuration.zig) and offers two views of it. The text view (compiler/Maker/ScannedConfig.zig `print`) walks the steps and prints each step's own fields - but a compile step's module is printed as an index into the binary's `extra` array (`.root_module = 19001`), and an options step's contents as an offset and a length into its string bytes. The module's import table, its C sources and their flags, its include paths and link inputs, and the text of every options module are not in the text at all. Those are exactly what a build refactor can break: swap two fields of an options module and the text is identical, while every compile that imports the module recompiles.

**What Happened**: The build migration's design (tmp/plans/build-protocol-design.md 5.1) made "the configuration text is equal" its per-commit check, from reading the toolchain's source. Lane build2 ran it first, as the design asked, on main b1c9ba6ae77 and on each of its four commits, on server1 and on chat.local, for six flag sets:
- The text is deterministic (two configures of one tree print identical text), 91,459 lines of steps, under a second - and incomplete, as above. Only the steps a top-level step reaches are serialized: two steps build() created and nothing depended on were in neither view, and deleting them changed neither.
- The binary is NOT byte-stable between two configures of one tree, for two reasons that are not the graph. (1) Each declared option's record (`AvailableOption`, an extern struct: name u32, description u32, type u8, then a u32) has three bytes of padding the configurer never writes: on server1 two configures with any `-D` on the command line differed in exactly 3 x 47 bytes; with no `-D`, and on chat.local, in none. (2) The binary holds the configure process's environment variables (a Run step carries an `environ_map`): two pool jobs' binaries of one graph differed in 6 bytes - the ssh client's port in SSH_CLIENT and SSH_CONNECTION, and XDG_SESSION_ID. The lane's first job required byte identity, took the padding for a failure and skipped its builds ([a job chained with &&](workflow-a-job-chained-with-and-runs-only-as-far-as-its-first-failure.md)).
- With the configure run under a fixed environment (`env -i` plus HOME, PATH and the cache directories) and the padding ignored, a commit that deleted 119 lines of unreachable build code gave a binary byte-identical to its parent's: the complete proof, for free.
- A commit that reordered six option declarations and made one an enum (no step changed) shifted numbers through the text: 441 lines of 92,378, every one a field holding an index or an offset (`.root_module`, `.index`, `.target`, `.owner`, `.include_extensions`, `.environ_map`), by +4 (the enum's list of values is four words written to `extra` before any step) or +34 (the string bytes the option texts grew by). With those fields masked the text was identical. Strings are interned as build() runs, so anything that changes which strings exist, or an option's type, moves offsets everywhere after it.
- A commit that added steps renumbered the rest: 4,438 lines removed and 5,357 added in a plain diff for 7 new steps, because step indices are assigned by a walk from the top-level steps. With the index-holding fields and the dependency-list entries masked, the diff was the 7 new step blocks, 9 dependency entries, and the 14 top-level step names after the new one, each one index later - nothing else.

**Fix**: The check, per flag set the gates build with (lane build2's `config.sh`):
1. Capture both views under a fixed environment: `env -i HOME=$HOME PATH=$PATH ZIG_LOCAL_CACHE_DIR=... zig build --print-configuration <flags> > x.zon`, and `cp "$(... zig build --print-configuration-path <flags>)" x.bin`.
2. Compare the binaries, ignoring the three padding bytes of each option record and nothing else. The header's eleven u32s give the sections' lengths - string bytes, steps (20 bytes each), path deps (12), unlazy deps (4), system integrations (8), available options (16), search prefixes (4), extra (4) - so the option records begin at `44 + string_bytes + 20*steps + 12*path_deps + 4*unlazy + 8*system_integrations`, and the padding is bytes 9-11 of each 16. Equal: the whole graph is equal - strings, modules, flags, link inputs. That is the proof for a commit that keeps the builder calls and their order.
3. Where the binaries differ because the commit says so (an option list that changed, a step that was added), the text narrows it: split it at `.path_deps` into the steps and the declared options; compare the step names as a multiset; diff the steps with the index-holding fields and the dependency entries masked, and name every line that is left. That shows which steps exist and that no field of another kind changed - it cannot show that a module's contents did not change, so such a commit's proof is the build itself: every compile step a cache hit in a cache warmed at the base commit, and the outputs' sha256 equal to that warm base's.

**Takeaway**: **The printed configuration shows which steps exist, not what they compile: prove a no-output build change with the binary configuration (one environment, the option records' padding ignored), and where the option list or the step list changes on purpose, with cache hits and output hashes against a cache warmed at the base - never with the text alone.**
