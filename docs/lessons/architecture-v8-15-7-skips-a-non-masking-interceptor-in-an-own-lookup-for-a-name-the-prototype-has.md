# Architecture: V8 15.7 skips a non-masking interceptor in an own lookup for a name the prototype chain has

**Date**: 2026-11-11
**Lesson**: Since V8 fa6c1824b06 (in 15.7.112.43), an OWN property lookup on an object with a non-masking named interceptor walks the prototype chain first and answers NOT_FOUND when the name is there. The interceptor's definer, descriptor and query callbacks are no longer called for such a name, so anything that reaches a named setter through an own lookup (DefineProperty, [[DefineOwnProperty]]) skips it.

**Why**: The change ("[lookup] Support own property lookup in non-masking interceptors", bug 483413086) adds `kSkipNonMaskingOwnProperty` to LookupIterator (src/objects/lookup.cc, NextInternal): a non-masking interceptor means WebIDL's named property visibility, where a name the prototype chain has is invisible. That is right for [[GetOwnProperty]]. But WebIDL's [[Set]] (3.9.2 step 1.2) and [[DefineOwnProperty]] (3.9.3 step 2.2) send a String to the named SETTER whatever the prototype chain has. 13.1.203 restarted an own lookup into the non-masking interceptor at the end of the holder, so the definer ran.

**What Happened**: In lane v8up's port, tests/html/storage_named_properties_test failed: after `localStorage.key = 'key'`, getItem('key') was null and an own data property shadowed Storage.prototype.key. Crane's legacy platform object proxy implements [[Set]] by `target->DefineProperty`, an own lookup. V8's ordinary [[Set]] path is unchanged between the versions (SetPropertyInternal / AddDataProperty never call a non-masking setter for a prototype name). That is why the regression looked like an interceptor-contract change and not a lookup change. wpt.fyi shows Chrome 157 has the same bug: webstorage/set.window.html is 8/20 there, and the "data property on prototype" subtests fail with the own property's value. Firefox 159 and Safari 27.2 pass them (16/20).

**Fix**: An interface with a named setter registers its named interceptor MASKING (interface.zig `named_setter_masks`), so V8 consults it in every lookup. Its getter then runs the whole visibility algorithm (isVisible, steps 1-3), as a [LegacyOverrideBuiltIns] interceptor's does; query, descriptor and deleter already did (lane v8up 4c156cf1db8). Storage was the only interface it changed: DOMStringMap masks already, and the CSS declarations' named properties are Crane's CSS attributes.

**Takeaway**: **On V8 >= 15.7 a non-masking interceptor is invisible to own lookups for any name the prototype chain has. A special operation that must run regardless of visibility (a named setter, a definer) needs a masking interceptor that asks visibility itself.** When an engine update breaks one interceptor behaviour, read the LookupIterator diff before the callback contract.
