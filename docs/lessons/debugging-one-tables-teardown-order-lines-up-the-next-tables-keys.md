# Debugging: One table's teardown order lines up the next table's keys

**Date**: 2026-11-02
**Lesson**: Every `std.AutoHashMap` hashes an address with Wyhash under seed 0 and probes linearly from `hash & (capacity - 1)`, so a given address has the same home slot in every std map of a capacity. A teardown that frees objects by walking one map frees them in home order, the slab's LIFO free list issues them again in that order, and the next map keyed by them clusters: its keys, and the tombstones they leave, fill one run of contiguous slots.

**Why**: Linear probing places a set of keys the same way whatever order they come in, so a single walked table cannot hurt the next one on its own - it is at most 80% full, so a window of its home slots never holds more keys than slots. But two tables that end one after the other (a page and its frame, whose wrapper cache kept the size it grew to after the collector emptied it) hand the next table the frame's keys over every home and the page's last keys over the top of the table: more keys than slots there. Each such end leaves the slab's free list a little more sorted, and a long process stacks many. TombstoneGuard bounds how MANY tombstones a table keeps, not WHERE they are, so it does not help: the side map in the failure below had half its unused slots free on every page.

**What Happened**: Lane v8order1, making tests/v8 hermetic, found `engine_pending_activity_test` "edges traced from owners script has not seen ... page after page" passing alone and failing on every replay of tests-v8 batch 0 seed 0x02e77638 (position 1304): worst mean miss 138-446 slots, 0 pages starved. Its instrumented replay printed the side map's home slots: alone, consecutive owners had scattered homes (198, 2697, 690, 1431...) and probe 1; in the replay, 1,000 consecutive owners had homes 3580, 3580, 3581, 3580 ... 3092 - 488 homes, issued by the slab at generation 134,254, i.e. after the 1,303 tests before it had torn their realms down by walking their wrapper caches. Once v8init1's tests reshuffled the seeds, seed 0x0807690a showed two victims on main 86bb62929d9: the same file's "pending activity kept before the wrapper exists" (pending_before_wrap, position 1280) and wrapper_cache_tombstones_test's "wrappers put and taken out, round after round" (position 834) - the wrapper cache's own map. Lane hashclust1 reproduced it without the prefix (tests/dom/instance_map_clustering_test.zig): a page's table of 3,200 objects and its frame's table of 1,000 (grown to 4,096 by 3,000) end in turn, and the next side map's worst mean miss is 85 slots with std's maps, within 8 with seeded ones. With the fix, tests-v8 batch 0 at seed 0x0807690a passes 1,639 tests with none order-dependent.

**Fix**: `infra.address_map` (src/infra/address_map.zig): `AddressHashMap` / `AddressHashMapUnmanaged`, std's HashMap with a seed per table - Abseil's per-table seed (raw_hash_set.cc `RandomSeed`, a counter advanced per table, and `generate_new_seed` at every resize) and Rust's per-map `RandomState` (rust-lang/rust#36481). WebKit's WTF avoids it differently, by probing quadratically; std's probe is linear and not ours to change.
1. The seed comes from a process-wide atomic counter mixed by SplitMix64: deterministic, no clock or OS entropy (a seeded test run replays its seeds).
2. A table draws one when it is first allocated (and after `clearAndFree`), at `clearRetainingCapacity`, and at `rehash`, which re-places every entry under the new seed.
3. The hash is exactly `Wyhash.hash(seed, asBytes(&key))`, with the seed's mixing done once per table, so it costs what std's seed-0 hash does.
4. The types keep std's method names and a field named `unmanaged`, so call sites change only their type, and `infra.tombstones` (TombstoneGuard, `slotCounts`, `meanMissProbe`) reads them unchanged; `zig build lint-tombstones` reads `address_map.AddressHashMap(...)` fields as maps.
5. Every map keyed by an instance's address uses it - the wrapper cache's three, the InstanceRegistry tables, internal_state, EventTarget's registry, instance_bridge, instance_state_map and the DOM's and HTML's side tables - including the ones keyed by the address as a `usize` or `*anyopaque`: the same 8 bytes hash the same.

**Takeaway**: **A hash map keyed by addresses must not share its hash with every other one: give each table its own seed (infra.address_map), or a teardown that walks one table hands the next one its keys sorted by home slot.**
