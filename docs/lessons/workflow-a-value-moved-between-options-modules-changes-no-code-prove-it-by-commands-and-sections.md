# Workflow: A value moved between options modules changes no code - prove it by sections and commands, not by hash

**Date**: 2026-11-16
**Lesson**: Moving compile-time values from one Zig options module to another (the build migration's batch E5: V8's three values from the shared `build_options` to the adapter's `adapter_options`) recompiles every artifact that imports either module and changes every hash, yet changes no code: the proof is the compile commands, the sections and the symbols.

**Why**: Zig caches a compile on its command line and the contents of every input, and an options module is a generated file whose path holds a digest of its text. So a commit that changes an options module's text, or which modules import it, makes every compile that takes the module run again, and every output it feeds is a new file - on Linux its DWARF names the new path, on macOS its debug map, UUID and signature change, and in a Debug build Zig's anonymous constants are numbered by the module that holds them. None of that is the program. A hash comparison cannot tell the two apart, and the design's fallback - a WPT A/B for every binary whose hash differs - measures behaviour, not identity.

**What Happened**: Lane build5's c5 (37117fe001c) moved jitless, v8_compilation_cache and v8_extra_flags to `adapter_options`, deleted three unread facts, removed `applyTransitional` and stopped handing `build_options` to runtime, namespaces and impls. On chat.local, against a warm control of the commit before it: `zig build --verbose` of the 11-artifact set showed 100 compile commands of which exactly 10 differed, each by the three `-Mbuild_optionsN=...options.zig` modules and their `--dep` (digests masked); the configuration differed only in the two options steps' lengths (346 -> 90, 184 -> 306 bytes) and the dropped dependency entries; tools/section_diff.zig found wpt_runner, the bug-finding runner, repl, the release console, gc_bench and wpt_build_compare the SAME PROGRAM (every __TEXT/__DATA section and every symbol outside the debug map equal); `zig build code-size --base` found 0 of ~19,000 families changed; the snapshot blobs and repl.modes were identical. Two things differed beyond the debug map: the Debug crane renamed two anonymous constants (`___anon_268435817` -> `___anon_134218089`, same address, same bytes - the high bits are the module's number), and libwhatwg_full.a's Zig object differed only in its __DWARF sections and the header bytes that place them. On server1 (Linux) the same comparison gave the same answer for every ReleaseSafe executable - SAME PROGRAM, only .debug_* sections differing - while the Debug crane and libwhatwg_full.a's Zig object differed in code; two fresh builds of ONE tree's crane differ the same way (workflow-zig-017s-self-hosted-debug-backend-is-not-reproducible-prove-a-debug-artifact-by-its-gates.md), so for those the commands and the gates are the proof.

**Fix**: For a commit that may change a compile input but not the program: (1) capture every compile command of the artifact set with `--verbose` before and after (cached builds print them too), mask the cache digests, and require the differences to be exactly the declared ones; (2) build the after-side cold, then again, and compare each executable with the control by `zig build section-diff -- <a> <b>` (verdict SAME PROGRAM) and `zig build code-size -- <b> --base=<a>` (0 families changed); (3) compare data artifacts (the snapshot) by hash; (4) attribute anything else by name. Then the gates and the A/B the brief asks for.

**Takeaway**: **A hash says two builds differ, never that the program did: compare the compile commands with digests masked, then the sections and symbols, and only what is left is a change to explain.**
