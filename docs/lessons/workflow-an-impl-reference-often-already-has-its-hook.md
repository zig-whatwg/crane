# Workflow: An impl reference often already has its hook - read the owner's installHooks before designing one

**Date**: 2026-11-16
**Lesson**: Before designing a hook, a construction argument or a state move for a reference into another type's impl, read the owner impl's `installHooks` and grep src/dom for a function with the same body: the step is often installed already, under another name.

**Why**: Hooks were added one caller at a time, so a hook module's Implementation installs the owner's existing impl functions (`.set_document = &setDocument`), while older callers kept calling the impl function directly. The hook and the direct call then run the SAME function, and the conversion is a one-line swap with no behaviour question at all. State types moved out of impls the same way (impls7: Document's state in dom.document_state), leaving dom accessors (`document_internals.setDocumentElement`) whose bodies equal the impl's copies.

**What Happened**: Lane impls8, the last 28 impls-boundary references. Of HTMLIFrameElement's 14, five were already covered by hooks installing exactly the impl function they called: `Window.setDocument` x2 (`dom.window_globals.setDocument`, installed as `.set_document = &setDocument`), `Document.setDefaultView` x2 (`dom.document_browsing_context.setWindow`, `.set_window = &setDefaultView`) and `Window.replaceBrowsingContext` (`window_globals.adoptBrowsingContext`, `.adopt_browsing_context = &replaceBrowsingContext`). Two more had dom steps with identical bodies: `Node.setLocalName` (`dom.node_creation.setNodeLocalName`, impls7's) and `Document.setDocumentElement` (`dom.document_internals.setDocumentElement`, the same registry write). The wrapper cache's `Document.getInternalState(...).default_view` was the same registry read `dom.document_internals` already does. And Window's named getter, which the adapter reached as `WindowImpl.getNamedProperty`, is IDL: the generated Window already declared `call_getter` and `isSupportedPropertyName` and named them in Meta.special_operations - the impl only had to implement them (a [Global]'s named handlers are never installed by the binding, so binding them changes nothing else). Only Location (its Window, navigable and URL), History's Window and the Window's existing Location needed new steps. They first went into a new hook module, which added a variable to lint-global-state's total (206 -> 207, a Hook slot, so no inventory entry); the integrator asked for the total to stay flat, and they moved into window_globals' slot as Location's and History's fields of one multi-owner `Hooks` struct (`installLocation`, `installHistory`; node_creation's shape).

**Fix**: For each reference `XImpl.f` from outside X:
1. `grep -n 'install(' src/webidl/impls/X.zig` and read the Implementation structs it fills: is `&f` (or a thin wrapper of it) already installed? Call the hook.
2. grep src/dom (and src/html) for a function whose body equals `f`'s - especially accessors of a state type that already moved (`dom.document_state`, `dom.element_data`, `dom.event_dispatch`).
3. Is `f` the impl of an IDL member under another name (a special operation, an attribute's getter)? Check the generated interface and its `Meta.special_operations` before adding anything.
4. Only then design a new hook step or construction argument - and put a new owner's steps into the nearest existing hook slot as a field of its `Hooks` struct (`installField`), not a new module: every new module is one more variable in the global-state total.

**Takeaway**: **Most of the boundary's last debt was a call to a function some hook already installs: read the owner's installHooks and the generated interface first, and design a new step only for what neither has.**
