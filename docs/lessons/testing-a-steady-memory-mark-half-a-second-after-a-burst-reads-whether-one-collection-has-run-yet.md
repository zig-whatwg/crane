# Testing: A steady-memory mark half a second after a burst reads whether one collection has run yet

**Date**: 2026-11-16
**Lesson**: The perf suite's steady figure is the footprint 500 ms after a row ends. When the row ends with its garbage uncollected and V8's heap within a few megabytes of its limit, that figure has two levels - "the collection ran while the page was idle" or "it runs at the next allocation" - and a change that moves nothing V8 counts can still move which level a run reports.

**Why**: V8 schedules a marking task when the space left under its limit falls to the young generation's capacity (15.7.112.43 src/heap/heap.cc `Heap::IncrementalMarkingLimitReached`, :5635-5745; `job->ScheduleTask()`, :1978-1981). A task runs when the page is idle, and its collection finishes "via task" about 0.3 s later. With a little more space left, nothing is scheduled: the collection starts when the page allocates again and finishes "via stack guard" - after the mark. The limit is whatever the last collection inside the row left (size times a growing factor), so 1.3 MB more survivors at that collection (86.9 against 88.2 MB of V8 heap) moved the limit from 282 to 286 MB and the row's steady figure from about 312 to about 400 MB.

**What Happened**: Lane wrap2's cost window read streams.reader's steady memory at 1.273 of main on the judged pass (three runs: 394.8, 398.1, 409.6 against 312.7, 440.7, 312.1 MB) while the row's peak was 0.914 and every later row 0.95. The lane's change is malloc that V8 never counts. First explanation, from three runs a side of the footprint sampled every 20 ms: "the collection falls at 3.5 s on the page's clock on both sides, and the lane's row is 0.27 s shorter, so its mark comes first". It fitted every run - and a test with a 1,500 ms settle disproved it (the lane stayed flat for 1.6 s and fell only after the mark). V8's trace then named the rule above: three runs with the limit at 282 MB collected while idle ("Start (task)" 134-226 ms after the row's end), the run at 286 MB did not. What the trace did not name is why the lane lands on the high side more often (17 of 19 runs against 8 of 19); the row went to the user as a scheduling effect, with the fact that once the collection has run the lane holds less.

**Fix**:
1. For a row whose steady figure moves and whose peak does not, sample the footprint every 20 ms through the mark before reading anything into the figure: a fall of the row's garbage just before or just after the mark is this case.
2. An explanation that fits the runs you have is a hypothesis. State a prediction it makes about a run you have NOT made (a longer settle, a different order), run it, and report the result either way - before the explanation goes into a message as the cause.
3. Then read V8's own trace (`--trace-gc --trace-gc-verbose --trace-incremental-marking`, a diagnosis console): the start reason of the first marking after the row ("task" or "allocation limit"), the size and limit on that line, and how the collection was finalized.
4. Report such a row by level and by count (how many runs at each level, a side), never by a median of three.

**Takeaway**: **A steady mark that sits a fraction of a second from a collection measures V8's schedule, not what the engine holds. Sample through the mark, test your first explanation with a prediction, and let V8's trace name the rule.**
