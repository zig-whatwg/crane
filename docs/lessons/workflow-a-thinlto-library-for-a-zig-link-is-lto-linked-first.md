# Workflow: A ThinLTO library for a Zig link is LTO-linked first, its native objects kept

**Date**: 2026-11-04
**Lesson**: Zig's Mach-O linker reads no LLVM bitcode, so a library built with ThinLTO (V8 as Chrome's official build compiles it) reaches Crane's link as native objects only if the ThinLTO link is run over the library alone first: ld64.lld with `-object_path_lto <dir>` keeps the objects its backends write, and `-u` for every external symbol keeps the API the later link needs.

**Why**: ThinLTO splits optimization in two: the compile writes bitcode with a summary, and the link imports functions across modules and generates code for each. The second half needs a linker that reads bitcode; Zig 0.17.1-dev+77c319a0f0's Mach-O linker reads a bitcode object as a TBD file ("failed to parse TBD file: UnexpectedToken") and one inside an archive as a Mach-O of "unknown cpu architecture: 0". An embedder that links a static V8 with its own linker gets no ThinLTO unless something else runs that half: rusty_v8 ships its static V8 without LTO (its .gn default_args set no is_official_build, use_thin_lto or chrome_pgo_phase); Node can use LTO because one toolchain compiles and links V8.

**What Happened**: Lane v8opt1 built V8 13.1.203 with Chrome's official flags (is_official_build: ThinLTO, Chrome 131's mac-arm64 PGO profile, V8's builtins PGO). Chrome's own mac link already does what was needed: ld64.lld runs the ThinLTO backends inside the link and writes their native objects where `-object_path_lto` says (Chrome passes it through `-Wcrl,object_path_lto` for dsymutil). Running that link over V8's objects alone, as a throwaway `-dylib -undefined dynamic_lookup`, took 14 s at --thinlto-jobs=14 and left native arm64 objects. The traps on the way:
- An LTO link keeps only what it sees used or exported, and a hidden symbol is never exported. ld64.lld treats `-u <sym>` as a reference from a regular object (`SymbolTable::insert`: `isUsedInRegularObj |= !file`), so each of the 72,206 external symbols of V8's bitcode went in as `-u`. llvm-nm prints a blank line and an `<object>:` header per input: filter them out, or a bare `-u` swallows the next `-u` and lld reads a symbol as a file name.
- The objects are not one per input in order. Task 0 is the regular-LTO partition, which holds the split-LTO-unit parts (vtables and what they reference) of every module (`-fsplit-lto-unit`); a module can be all regular-LTO and get no task of its own. Name each object after the module that alone defines one of its symbols, and archive the partition too.
- `use_thin_lto` also compiles `-fwhole-program-vtables`, which would let the LTO link bind a call through a class of hidden LTO visibility to the one subclass it sees, and Crane subclasses v8::Platform, TaskRunner, Task, the serializer delegates and V8InspectorClient outside that link. V8's monolith compiles `-fvisibility=default`, so its classes are public to LTO anyway; GN's `cc_wrapper` (scripts/v8-official-cc.sh) appends `-fno-whole-program-vtables` so soundness does not rest on that (no `llvm.type.test` left at call sites).
- 13.1.203's DEPS put a Linux x86-64 `llvm-nm` in the Mac clang package; Xcode's `llvm-nm` reads the bitcode.

**Fix**: scripts/build-v8-official.sh (`official` step: the GN compile to bitcode, then `lto_native`), and `-Dv8-build=official` (tools/v8_archives.zig) to link the result. The script checks that every archive member is arm64 Mach-O and that each module's strong symbols are defined by its object or by the regular partition; `verify` counts the cross-module calls inlined away (12,991 over 1,084 modules) and the locals ThinLTO promoted (8,862).

**Takeaway**: **When the final link cannot read bitcode, run the library's ThinLTO link yourself and archive every native object it writes - the regular-LTO partition included - keeping each external symbol with `-u`.**
