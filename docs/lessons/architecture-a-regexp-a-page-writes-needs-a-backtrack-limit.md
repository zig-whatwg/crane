# Architecture: A regexp a page writes, run by the engine, needs a backtrack limit

**Date**: 2026-10-10
**Lesson**: A regular expression whose source a page controls and which the engine runs natively (no script on the stack, nothing the page can interrupt) must be compiled with a backtrack limit, or one catastrophic pattern freezes the agent.

**Why**: V8's irregexp backtracks. A nested quantifier such as `(\d+)*$` against a long run of digits ending in a letter tries every way of splitting the digits, about 2^n backtracks, before it fails. In script, a slow regexp is the page's own problem and the page can be stopped like any long script. When the engine itself runs the regexp - the `pattern` attribute's constraint check, run from `validity`, from `:invalid` matching, from form submission - it holds the agent's thread inside a native call the page did not make. Nothing in the spec bounds it; the browsers do.

**What Happened**: engine.matchesPatternAttribute (lane cxsupport) compiled the anchored pattern with plain `RegExp::New`. Once HTMLInputElement used it (lane smallfix), html/semantics/forms/constraints/infinite_backtracking.tentative.html went from OK to TIMEOUT: its input's `pattern="(\d+)*$"` against 38 digits and a `z` never finished, and the page hit the runner's 10 s ceiling.

**Fix**: Do what Blink does. ScriptRegexp compiles every regexp with `v8::RegExp::NewWithBacktrackLimit(context, pattern, flags, 1'000'000)` (third_party/blink/renderer/platform/bindings/script_regexp.cc, `kBacktrackLimit`). Past the limit V8 returns a match failure (null), ScriptRegexp::Match answers -1, and BaseTextInputType::PatternMismatchPerValue reads that as a mismatch. Crane's CompilePatternAttribute now compiles the anchored regexp the same way (`kPatternAttributeBacktrackLimit`), so a runaway pattern is a pattern mismatch. wpt.fyi agrees: Chrome and Safari pass the WPT file (the input is `:invalid`), Firefox times out. tests/v8/pattern_backtrack_limit_test.zig pins it with a semantic case first - `(a+)+$|.*c` against 26 a's and a `c`, which without the limit matches through its second alternative after ~2^26 backtracks and with it does not match - so an engine without the limit fails that test in about a second instead of hanging on the catastrophic cases after it.

**Takeaway**: **When the engine runs a page's regexp on its own initiative, compile it with a backtrack limit (Blink's 1,000,000) and treat "limit exceeded" as the browsers do. Test it with a case whose answer the limit changes, placed before any case that would hang without it.**
