# Architecture: A WebSocket over HTTP/2 needs the transport to own the WebSocket protocol

**Date**: 2026-11-19
**Lesson**: libcurl's WebSocket is HTTP/1.1 only and its CONNECT_ONLY connection got curl's HTTP/2 layer when ALPN said h2, so RFC 8441 meant curl makes the connection raw and Crane speaks the handshake, the framing and HTTP/2 itself.

**Why**: lib/ws.c forces `http_neg.wanted = CURL_HTTP_V1x` for ws:/wss:, and lib/http2.c never sends `:protocol` nor reads SETTINGS_ENABLE_CONNECT_PROTOCOL. A CONNECT_ONLY (1) https connection whose ALPN chose h2 still had cf-https-connect insert the HTTP/2 filter (Curl_http2_switch_at), so curl_easy_send/recv bytes went into nghttp2's session. Every browser frames its WebSockets itself; only Crane leaned on a library's.

**What Happened**: websockets/*.any.js carry a `?wpt_flags=h2` variant (115 files, ~138 majority-pass subtests). They failed for two reasons stacked: the runner loaded them from the plain listener (it read only `wpt_flags=https`; wptrunner's server_protocol reads h2 first), and the transport could not open a WebSocket on wpt serve's h2-only port. libcurl had also been passing a 101 whose Sec-WebSocket-Accept was wrong (Curl_ws_accept only comments on the check).

**Fix**: (1) the runner maps `wpt_flags=h2` to the 9000 listener ahead of https (tests/wpt_runner/wpt_server.zig, tools/console_parity.zig). (2) The zig-whatwg/curl fork leaves a CONNECT_ONLY connection raw on h2 (reviewed for upstream). (3) kit/curl's WebSocket transport: curl connects (DNS, proxy CONNECT tunnel, TLS with the Browser's trust store, ALPN h2+http/1.1 for wss:); ALPN h2 and the server's SETTINGS enabling the extended CONNECT -> an nghttp2 client session with one CONNECT stream (websocket_h2.zig, nghttp2 declared by hand in nghttp2.zig because build.zig may not name the library); h2 without it -> a fresh HTTP/1.1 connection (Firefox's model); ALPN http/1.1 -> Crane's own RFC 6455 4.1 handshake (websocket_handshake.zig) on the same connection; one RFC 6455 codec for both (websocket_frames.zig). Chrome's model (WS over h2 only on an EXISTING h2 session) was out of reach: the page's h2 session lives in libcurl's pool.

Two traps on the way, both found by the WPT h2 variants: (a) a CONNECT_ONLY transfer that is done keeps its connection only for curl_easy_send/recv - CURLINFO_TLS_SSL_PTR reads data->conn (lib/getinfo.c), which is gone, so ALPN must be read in CURLOPT_PREREQFUNCTION, which curl calls for a CONNECT_ONLY transfer too (multi.c state_do); (b) wpt serve's h2 server never calls h2's acknowledge_received_data, so it never sends WINDOW_UPDATE and a client can put only 65,535 bytes of DATA on the connection: binary/002, binary/004 and extended-payload-length pass in the browsers only because they compress with permessage-deflate (RFC 7692), which every browser offers and libcurl never had - so the transport implements it too (websocket_deflate.zig); send-many-64K's h2 variants TIMEOUT in all three browsers.

**Takeaway**: **When a library implements a protocol for one transport only, own the protocol and use the library for the connection; and check which model each browser follows (Chrome reuses an existing session, Firefox offers h2 on a fresh connection and falls back) before choosing the one you can reach.**
