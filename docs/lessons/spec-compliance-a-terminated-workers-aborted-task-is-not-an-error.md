# Spec Compliance: A terminated worker's aborted task is not an error - run no failure steps for it

**Date**: 2026-11-21
**Lesson**: When "terminate a worker" aborts the worker's script in the middle of a task, whatever engine call that task was making fails - and native code that turns such a failure into a spec "error path" (a messageerror, a stream error posted to another realm) makes the abort observable in the page; check the worker's closing flag before running any failure steps.

**Why**: HTML's "terminate a worker" runs in parallel with the worker: 1. set the closing flag, 2. discard the queued tasks without processing them, 3. abort the script currently running. Step 3 is V8's TerminateExecution from the owner's thread, so it lands at any instruction of the task the worker is in - including inside a structured deserialization a port task is doing natively. The deserializer then fails exactly as it would on corrupt data. HTML 10.2.2: once the closing flag is set, no further task runs; Blink checks it at dispatch (message_port.cc MessagePort::DispatchMessageEvent: "if (scope->IsClosing()) return;").

**What Happened**: streams/transferable/worker.html 'terminating a worker should not error the stream' failed once in a FULL A/B on server1 ("Unhandled rejection with value: object TypeError") and 1 in 10 in verify. A Crane test running the upstream scenario 20 times per file (crane/flk3-transfer-worker-terminate.html) failed 8 of 20 runs under --load=10 on chat.local. A diagnostic runner (print lines on every cross-realm error path) showed the order on every failure: on the worker's thread, right after terminate(), the worker's cross-realm writable port took a messageerror (the page's "pull" message failed to deserialize under the abort); Crane ran the messageerror steps natively - CrossRealmTransformSendError posted "error" to the page's readable (its reads rejected with DataCloneError), and the worker's pipe canceled its readable, whose cancelAlgorithm posted "error" to the page's writable; the page's pipe canceled the original stream, so the test's next controller.enqueue() threw a TypeError.

**Fix**: MessagePort's delivery returns without delivering when the port's worker is closing (html.worker_host.scopeClosing, as BroadcastChannel reads it), and checks again after a failed deserialization: a failure while closing is the abort, never a messageerror (src/webidl/impls/MessagePort.zig `deliver`).

**Takeaway**: **A failure inside a worker task can be the termination itself: before native code runs error steps that reach another realm (post a message, error a stream, fire an event), check the closing flag - a closing worker processes nothing, so its aborted task has no error to report.**
