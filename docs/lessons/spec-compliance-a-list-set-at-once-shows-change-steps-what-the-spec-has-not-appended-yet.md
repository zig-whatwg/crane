# Spec compliance: A list set at once shows change steps what the spec has not appended yet

**Date**: 2026-11-11
**Lesson**: Replacing a spec loop that appends one item and runs its steps ("Append each attribute in the given token to element", "clone a single node" step 3) with "set the whole list, then run every step" changes two things the loop gave for free: each step now sees the items that come AFTER it, and the batch needs an answer for a target that is not empty. Copying a browser's batch order means copying what that browser's steps do under it, too.

**Why**: A change step is free to read the element's other attributes. Under the spec's order it reads only those appended so far; under the batch it reads all of them. Steps written to the spec text (Gecko's shape) are only right in the spec's order; Blink and WebKit, which batch, wrote theirs to be right with the whole list in place. Mixing one engine's order with another's steps gives behaviour no browser ships. And a batch that assumes "no attributes yet" meets script sooner than expected: a customized built-in is upgraded synchronously inside "create an element", so its constructor runs before the parser appends the token's attributes.

**What Happened**: Lane nd2 batch 4 shares attribute blocks: the parser and a clone set the element's list at once (Blink's Element::ParserSetAttributes, WebKit's Element::parserSetAttributes) and then run "handle attribute changes" per attribute. Unit tests, the cost rows and the memory rows were all green. The FULL A/B against generation 216 lost two subtests, 3/3:

- `custom-elements/customized-built-in-constructor-exceptions.html`: the batch returned InvalidStateError for an element that already had attributes and its caller logged it at debug and dropped the token's attributes. A constructor's `this.setAttribute('foo', 'bar')` cost `<input id=x is=my-input>` its `id` and `is`.
- `html/semantics/forms/the-input-element/clone.html`: HTMLInputElement's type change step 1 ("if the element's value is not the empty string ... set the element's value content attribute to the element's value") read a clean value from the value attribute, sanitized for the Text state. On main `type` was appended before `value` existed, so the value was empty and nothing happened. With the whole list in place the step rewrote the clone's value attribute ("CHANGED\nCHANGED" became "CHANGEDCHANGED").

The second was wider than its test, and WPT did not see the rest: a PARSED `<input type=hidden value="a&#10;b">` lost its newline, and every parsed or cloned input in a default or default/on state with a value attribute wrote that attribute - which copies its block, so those inputs were never shared and the batch's memory rows were measured with that write in them. Both are pinned by tests/html/nd2_parsed_attributes_order_test.zig. The first loss was fixed in the batch (the fallback of Fix 3; Blink's HTMLConstructionSite::CreateElement, read in source, takes the same two paths). The second was ruled to follow Chrome and Safari - step 1 for a dirty value only - on the condition that Blink's HTMLInputElement::UpdateType and WebKit's updateType are read in source first: when this was written that was a recollection, not a reading.

**Status** (2026-11-11, later the same day): the input fix is in (HTMLInputElement.zig typeChangeSteps, step 1). Reading the two engines in source confirmed the recollection and found more: WebKit's step 2 stores the attribute's value where Blink's does not, so "dirty" is two predicates and the ruling became two cases - a value that only ever came from the attribute is not written (Chrome, Safari), a value an earlier type change took from it is (Safari, Firefox, the spec). See [Two engines' "same" predicate](spec-compliance-two-engines-same-predicate-read-what-sets-the-state-it-tests.md).

**Fix**:
1. Before batching a spec loop, list every step the loop runs per item and grep each for reads of the other items (here: every attribute change step that reads a sibling attribute or state derived from one). The full A/B is the net, not the audit.
2. Write the order tests first: for each element type with such a step, parse and clone it with the attributes in both orders, and assert the attributes read back as written AND that the element still shares its block.
3. A batch path's precondition ("the target is empty") gets a fallback to the spec's literal loop, never an error its caller swallows. Find who can run script before the batch: custom element constructors run inside "create an element".
4. When you copy a browser's order, read that browser's steps for the same elements and take its conditions with it - by golden rule 2, with the evidence - or keep the spec's order.
5. A change step that writes an attribute at parse or clone time undoes copy-on-write sharing silently. Assert sharing on the element types that have such steps, not only on `<p>`.

**Takeaway**: **A batch that sets the whole list first shows every change step the attributes the spec has not appended yet: audit the steps that read siblings, test both attribute orders at parse and clone, and give the batch's "empty target" precondition a fallback to the spec's loop.**
