# Testing: A suppressed sanitizer report still symbolizes - under ThreadSanitizer V8's worker start can deadlock with a test's first stack capture

**Date**: 2026-11-13
**Lesson**: A ThreadSanitizer suppression does not stop the report from being built: the runtime symbolizes it first, under its own locks, by walking the loaded modules with `dl_iterate_phdr` - and a thread that is inside a `dl_iterate_phdr` callback of its own, running instrumented code, holds the loader lock and wants the runtime's. About 1 engine test process in 900 hangs that way since the engine starts before the first test.

**Why**: V8 15.7 locks with `absl::Mutex`, which the sanitizer cannot see (V8 is not instrumented), so what its worker threads do under that lock as they start - each reaches a `vector<WorkerThread*>::emplace_back` of `DefaultWorkerThreadsTaskRunner` from `WorkerThread::Run` - looks like a race between them. tools/test_launcher/tsan_suppressions.txt covers it (`race:v8::`, `race:std::__Cr::`) - but a suppression is matched on function names, so the runtime must symbolize the report before it can drop it: `ReportRace -> OutputReport -> SymbolizeStackElems -> Symbolizer::RefreshModules -> ListOfModules::init -> dl_iterate_phdr`, with the report's locks held. glibc runs `dl_iterate_phdr` callbacks under its loader lock. Zig's `std.debug` loads the process's module list the first time a stack is captured, also through `dl_iterate_phdr` (`debug.SelfInfo.Elf.DlIterContext.callback`), and that callback is instrumented Zig: it appends to a list, the allocation's `memcpy` enters the sanitizer, and the sanitizer wants a mutex the reporting thread holds. Two threads, two locks, opposite orders.

**What Happened**: Lane build3 fixed the build so that a `-Dsanitize-thread` build's test executables are told they link the engine (they had been told they did not: [a predicate that inspects sources](architecture-a-predicate-that-inspects-sources-answers-wrong-when-the-build-compiles-them-apart.md)). The Crane test runner then started the engine before the first test in every engine test process, as it does in every other build - and the sanitizer step, 24 minutes before, took 47: five tests in three suites timed out at 1,200 s on their first run and passed alone.

- Counted, tests/dom under the sanitizer on one tree, arms alternating: with the start before the first test 4 hung processes in 4 runs (about 3,530 processes); with `CRANE_TEST_ENGINE_EARLY=0` and nothing else changed, 0 in 4. With the whole step's pair: 9 in about 8,860 against 0 in about 8,850. The plain build starts the engine the same way and showed 0 timeouts in 7 full runs that day (39,350 engine process starts); generation 219's WPT journal has no timeout before a page loaded. Sanitizer-only.
- A hung process: asleep, 0.02 s of CPU after 150 s, 19 threads, every one in a futex wait. Its stacks, read from /proc by the process that had started the test step ([how](debugging-only-an-ancestor-can-read-a-hung-process-and-age-does-not-make-one.md)), are in tmp/plans/build-migration-proof/build3-logs/hung-process-stacks.txt: a `V8 DefaultWorke` thread in `WorkerThread::Run -> vector::emplace_back -> memcpy -> ReportRace -> OutputReport -> SymbolizeStackElems -> ListOfModules::init -> dl_iterate_phdr -> __pthread_mutex_lock`; a thread the test made in `dl_iterate_phdr -> debug.SelfInfo.Elf.DlIterContext.callback -> ArrayList.append -> __tsan_memcpy -> RestartMemoryAccessRange -> __sanitizer::Mutex::Lock`; the main thread in `pthread_join` for it; the other fifteen workers in `absl::Mutex::LockSlow`.
- Why the early start brings it out: V8's sixteen workers then start, and "race", in the first milliseconds of every engine test process - exactly when the test's first stack capture makes Zig load its module list. Started later, by a test, the two rarely meet.

**Fix**: None in this batch - the build fix landed with the hang listed (the integrator's ruling), owner the V8 lane. What the stacks leave open to that owner, cheapest first:
1. Load Zig's module list before the engine starts: one stack capture (or `std.debug` self-info load) in the runner's process start, before `engine.initializeBeforeThreadCreation`, when no other thread exists - the callback then never runs beside a worker's report.
2. Keep the report from being built: the sanitizer's ignore annotations around the adapter's platform start, or V8's platform told to start its workers lazily, measured against what the sanitizer run is for.
3. Either way, count it the way it was found: N runs of one suite with a short launcher timeout (`-Dlaunch-timeout=60`), hung processes per arm.

Until then a sanitizer run that shows `first run: timeout ... alone: pass pass` with no output, in an engine suite, is this - check that the timed-out process slept (no CPU) before calling it anything else.

**Takeaway**: **Suppressing a sanitizer report hides its text, not its work: the runtime still symbolizes it under its own locks and takes the loader lock to do so. Anything instrumented that runs inside a `dl_iterate_phdr` callback - Zig's first stack capture does - can deadlock with it. Many uninstrumented threads that "race" at process start make a rare interleaving a daily one.**
