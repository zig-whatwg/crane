# Architecture: A bodyless response that announces a body poisons its connection

**Date**: 2026-10-31
**Lesson**: A server that sends bytes after a 204/205/304 whose header block says `Content-Length: N` (N > 0) leaves them on the connection; curl reads none (rightly - the response has no body) and pools the connection, and the next request on it reads `<junk>HTTP/1.1 ...` and fails with "Invalid status line". Browsers parse past the junk; curl cannot, so Crane must not reuse that connection.

**Why**: RFC 9110 15.4.5: a 304 "cannot contain content", whatever its Content-Length says. wpt serve's xhr/resources/redirect.py?code=304 still writes its 4-byte body ("TEST"), in a separate send after the headers. curl decides the transfer is done at the blank line, returns the connection to the pool, and checks a pooled connection only for input already pending when it is reused. If the reuse comes first - more likely once transfers queue for a connection slot and start the moment one is released - the junk arrives ahead of the next response. Chromium tolerates up to 4 bytes before "HTTP" (HttpUtil::LocateStartOfStatusLine, `slop = 4`); Firefox skips up to MAX_INVALID_RESPONSE_BODY_SIZE (128 KiB) in nsHttpTransaction::LocateHttpStart. Neither fails.

**What Happened**: After lane flaky4 capped connections at six per destination, xhr/send-redirect.htm's runs under eight runner processes went from 31/72 failing (connection resets) to 12/72 - every remaining failure a curl error 8 "Invalid status line" on the request after the (304, GET) subtest's. A Python client with no Crane in it showed the same desync against the same server (BadStatusLine on a reused connection, always after a 304).

**Fix**: The header callback (`noteHeaderLine`, src/fetch/network/curl_backend.zig) marks the transfer's connection not reusable (kit/curl `options.forbidReuse`, CURLOPT_FORBID_REUSE, which curl reads in multi_done) when the final block is a 204/205/304 to a non-HEAD request announcing Content-Length > 0. The next request opens a new connection - the one observable difference from a browser, which would reuse and show zero connect times. tests/fetch/network_scheduler_test.zig pins it with the test server's /not-modified-with-body, which sends the junk only after the client's next request arrives on the same connection.

**Takeaway**: **When a peer can break a protocol invariant, find out what the browsers tolerate before blaming the peer: if the library cannot tolerate it the same way, change what the library is asked to do (here: do not reuse), so the outcome matches.**
