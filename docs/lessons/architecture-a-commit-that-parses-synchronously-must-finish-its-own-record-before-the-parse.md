# Architecture: A commit that parses synchronously must finish its own record before the parse

**Date**: 2026-11-14
**Lesson**: A frame's commit that writes navigable state AFTER the parse callback returns can undo whatever the parse's script did to the navigable - a removal of the frame from a load listener or an inline script left a destroyed navigable marked ready, and `contentWindow` answered the removed frame's Window.

**Why**: Crane parses a frame's document inside its navigation's commit (`IFrameIntegration.commitResponse` -> `commitHtmlDocument` -> the parse callback). In the spec and in the browsers the commit is complete before the parser runs: "finalize a cross-document navigation" activates the entry, and the bytes are parsed in later tasks (Blink's DocumentLoader::CommitNavigation installs the document, then the body is parsed as it arrives). So nothing of the commit comes after the page's script there. In Crane every step written after the parse call runs after that script - and since lane nav2 batch 12 ("the end" completes the load in the parser's task, the user's ruling 2026-11-12) after the window's load and the iframe's load event too. A listener there may remove the frame: "destroy a child navigable" sets the integration's state to `.discarded`. The commit's last line was `self.state = .ready`.

**What Happened**: crane/nav1-frame-load-removes-frame.html subtest 1 ("removing the frame from its load listener": contentWindow must be null) went from 20/20 to 1/20 with nav2 batch 12's merge (main 4061acbe96f). It was found in rep1 batch 2's A/B. The bisect on server1's production runners: generation 224 (9a0207b5b4) 20/20, main fb2911d722a (just before the merge) 20/20, 4061acbe96f 1/20. The same bug is OLDER than nav2 batch 12 for a frame whose own inline script removes its container during the parse: the parse was always inside the commit, so `.ready` was always written after that script (tests/html/nav3_frame_removed_in_load_test.zig, "parse-time script"). nav2's audit of the steps after the parse (the lesson below) moved the document setup - type, mode, encoding, form states - but not the integration's own state write, because nothing in the old order could observe it.

**Fix**: `IFrameIntegration.markCommitted` - the committed URL and content type and `state = .ready` - runs BEFORE the parse in `commitResponse` (HTML, text, media, XML and the network error's document) and in `commitHtmlAt` (the javascript: URL's string document). Nothing of the commit follows the parse, so a removal during the parse or at its load is final. The steps of `commitInRealm` after the commit (`attachDocument`, `restorePersistedState`, the forward-history prune) already read the browsing context, which the removal clears, and do nothing for a destroyed navigable.

**Takeaway**: **When the engine runs the page's script inside a call the spec runs long before that script, no line after the call may write state the script can change: move the write before the call, or the script's change is undone. Test it from a load listener AND from an inline script - the second case predates any reordering of the load.** See also [A load moved into the parser's task exposes every step done after the parse](spec-compliance-a-load-moved-into-the-parsers-task-exposes-every-step-done-after-the-parse.md) and [A commit that parses synchronously must record the history entry first](architecture-a-commit-that-parses-synchronously-must-record-history-first.md).
