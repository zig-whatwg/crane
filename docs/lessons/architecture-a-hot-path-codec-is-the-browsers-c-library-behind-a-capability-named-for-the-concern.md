# Architecture: A hot-path codec is the browsers' C library behind a platform capability named for the concern

**Date**: 2026-11-14
**Lesson**: When Crane takes over a decode the browsers do with a C library (zlib for gzip/deflate, Brotli, zstd), measure the Zig replacement against the C one first; on the page-load path, reach the C library through a platform capability named for what it does (`deflate_decoding`), never for the library, and declare its symbols in the kit rather than in build.zig.

**Why**: The user's rule (2026-11-12): no engine-, platform- or library-specific code in build.zig, held by lint-build's per-word counts. A capability named after a library (`zlib_inflate`) also cannot be listed where its siblings are (build.zig's `platform_capability_names`) without adding the library's name there. And a pure-Zig decoder is not automatically as fast as the C one the browsers ship.

**What Happened**: Lane quick1 b3 moved HTTP content decoding out of libcurl into Fetch. gzip/deflate went through Zig's std.compress.flate, and the perf pair measured 1.317x the instructions and 1.068x the time of libcurl's zlib on a 1 MB body. Chromium (net/filter/gzip_source_stream.cc) and Firefox (nsHTTPCompressConv.cpp) both run zlib's raw inflate behind their own gzip header parsing. The fix added a platform capability. Its first name, `zlib_inflate`, was renamed to `deflate_decoding` by the integrator's ruling. zlib's four entry points and `z_stream` are declared as `extern` in kit/inflate/zlib.zig. zlib is already linked through the bundled libcurl, and `inflateInit2_` checks `sizeof(z_stream)` at run time. So no build-graph line names zlib, and a binary that never calls the capability links without it. The capability is reported only where the bundled libcurl is linked; other builds keep the Zig inflater. Afterwards gzip ran at 0.953x main's time.

**Fix**: (1) Perf-pair the new decoder against the code it replaces before the A/B. (2) Use the C library the browsers use, behind a capability that keeps an existing sibling's operation shape (create / decompress / destroy, CodecProgress). (3) Name the capability for the concern. (4) Declare the library's few entry points in the kit, and check the layout with the library's own size argument and a test. (5) Report the capability only where the library really links, and keep the slower pure path for the rest.

**Takeaway**: **A codec on the page-load path is measured against the browsers' C library first. If that library wins, it goes behind a capability named for the concern, with its symbols declared in the kit, so build.zig names nothing new.**
