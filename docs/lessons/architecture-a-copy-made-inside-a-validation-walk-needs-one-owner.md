# Architecture: A copy made inside a validation walk needs one owner, or each early return leaks it

**Date**: 2026-11-15
**Lesson**: When a loop both checks its inputs and allocates as it goes, give what it allocates one owner that frees it on every return but the successful one; a hand-written cleanup loop on each early return is missed by the return written next.

**Why**: The serializer every postMessage and structuredClone uses (v8_wrapper.cpp `serializeWithTransfer`) copies each transferred ArrayBuffer's bytes as it walks the transfer list, and the same walk rejects bad lists: a buffer listed twice, an empty handle, a value that is not an ArrayBuffer, a detached buffer, one that cannot be detached. Each rejection was a `return nullptr`. Four of the later ones freed the copies in a loop of their own; the first three, written above the first copy, never did, and they still ran on the second pass of the loop - after a copy existed. The function also wrote each copy into the caller's out list as it made it, so a failure that did free the copies left freed pointers there.

**What Happened**: Lane rep2's leaks --atExit found 1 leak of 16 bytes over 567 files, and it was queued as "serializeWithTransfer on window.structuredClone of primitives". Lane mem1 ran leaks --atExit with `MallocStackLogging=1` on one file (crane/worker.basic.html): the leaked block's stack was malloc inside serializeWithTransfer, from `call_structuredClone`. The test that made it was not a primitive one: "Phase 6.2: Duplicate transfer throws", `structuredClone(buffer, { transfer: [buffer, buffer] })` with an 8-byte buffer - the first pass copied 8 bytes (a 16-byte block), the second pass hit the duplicate check and returned.

**Fix**: A local struct inside the function owns the copies (a vector and a `handed_out` flag; its destructor frees them unless handed out). The out list is zeroed on entry and written only on success, where the copies move to it. Every early return became a plain `return nullptr`. tests/v8/transfer_failure_copies_test.zig pins it two ways, since std.testing.allocator cannot see C++ allocations: the out list after each kind of failure (all null), and malloc's bytes in use over 64 refused transfers of one 1 MiB buffer through the protocol (macOS `mstats`, glibc `mallinfo2`; the leak was 64 MiB).

**Takeaway**: **Allocation inside a checking loop gets an owner object at its declaration, never a cleanup loop per return - and name a leak from its allocation stack (`MallocStackLogging=1` under leaks --atExit on the one file), not from the description it was queued with.**
