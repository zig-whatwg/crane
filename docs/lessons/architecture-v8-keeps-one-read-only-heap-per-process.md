# Architecture: V8 keeps one read-only heap per process - every live isolate must come from the snapshot that made it

**Date**: 2026-11-02
**Lesson**: With pointer compression in one shared cage, every isolate of a process is in one isolate group, and the group keeps ONE read-only heap, made by the first live isolate from its own snapshot; an isolate restored from a different snapshot while it lives reads objects that heap does not have, and V8 crashes inside Isolate::Initialize.

**Why**: V8 13.1 `ReadOnlyHeap::SetUp` (src/heap/read-only-heap.cc) creates the group's read-only artifacts from the FIRST isolate's read-only snapshot and hands every later isolate the same heap; `ReadOnlyHeap::TearDown` drops it only when the group's isolate count reaches zero. Whether the later isolate's snapshot matches is checked only by `ReadOnlyArtifacts::VerifyChecksum` (src/heap/read-only-spaces.cc:76-104), which is compiled `#ifdef DEBUG`: the release build Crane links trusts it. An isolate made "without a snapshot" is not snapshotless - it restores V8's built-in snapshot, a different read-only snapshot from Crane's blob.

**What Happened**: Lane tsan1's many-Browsers variant ran a busy Browser (snapshot_path "", so V8's built-in snapshot) beside every tests/v8 test. Eight tests that restore agents from Crane's snapshot crashed 2-3/3 with SIGSEGV 0x10488 in `StringTableInsertionKey` <- `StringTable::InsertForIsolateDeserialization` <- `SharedHeapDeserializer::DeserializeStringTable` <- `v8_Isolate_NewFromSnapshot`. The same stack had been seen in October in tests/v8's shared executable ("restoring the snapshot after other files had started V8 crashed"; architecture-a-bare-context-new-in-a-snapshot-agent-deserializes-crane-s-window-context.md) and was worked around by skipping, cause unknown. It was product-reachable: a process started with a snapshot, a Browser with snapshot_path "" made first, then a default Browser. The opposite order - V8's built-in snapshot while Crane's heap is live - is how every worker of a snapshot process is made, and it works only because Crane's read-only snapshot EXTENDS the built-in one (v8_enable_extensible_ro_snapshot = true, 13.1 BUILD.gn:436), keeping the built-in objects where the built-in startup data expects them; a DEBUG V8 would abort there too.

**Fix**: v8_wrapper.cpp records the live isolates' read-only origin under one lock (`g_read_only_heap`, counted in v8_Isolate_New*/NewFromSnapshot*, released after Isolate::Dispose) and refuses a restore from a blob that did not make the live heap. `protocol_agents.createAgent` then makes the agent without the snapshot and says so at warn, naming the origin and the refused blob; `engine.agentRestoredFromSnapshot` answers what the agent really is, so Browser.init and HTMLIFrameElement make realms afresh instead of failing a restore each. Tests: tests/v8/tsanfix1_read_only_heap_test.zig, both orders and the worker cases, run alone under the many-Browsers variant (build.zig `alone`). The end state, queued as its own lane: every isolate of a process from one blob, as Chromium's gin does - which first needs the snapshot's DEFAULT context made plain, because V8's Genesis copies the default global's own properties onto every fresh context (bootstrapper.cc:7056-7062) and Crane's default global is a Window.

**Takeaway**: **An isolate made "without a snapshot" restores V8's built-in one. All the live isolates of a process share the read-only heap of the first: never restore a different blob beside them - and a crash inside Isolate::Initialize that depends on which test ran first is this.**
