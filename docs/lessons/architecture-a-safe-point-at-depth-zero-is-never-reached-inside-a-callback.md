# Architecture: A safe point at DOM-algorithm depth zero is never reached inside a callback

**Date**: 2026-11-12
**Lesson**: "The outermost binding exit" is reached only by script that runs with no native algorithm below it - a top-level script, a module, a promise job. Script inside a timer callback, an event listener or an observer runs at depth one or more for the whole callback, so anything owed to depth zero waits for the task's end there; say which script a safe point covers, and measure the same loop inside a callback before calling a deferral fixed.

**Why**: The V8 adapter counts every binding entry and every native-to-script callback invocation on the agent's `algorithm_depth` (dom_algorithm.zig; protocol.zig invokeCallbackFunction, constructCallbackFunction, callUserObjectOperation), and what the deferred teardown queue owes runs only at the binding exit that brings the depth to zero. The invocation's count stays for the whole callback, so a binding called from a callback's script returns at depth one. Most of a page's script runs inside callbacks.

**What Happened**: Lane v8up b6c made the depth-zero binding exit the safe point for the finalizers of collected wrappers (V8 15.7's second pass may not run them). The proof for the top-level loop was clean: 300,000 dropped Events ended at 162 MB again instead of 392 MB. The design was approved on that shape. Reading where the depth is counted, before the proof, showed the same loop inside `setTimeout(() => {...})` or a listener would never see a depth-zero exit; measured, it ended at 388.6 MB against 167.9 MB, and stayed at 373 MB after two forced collections (the state arena keeps its blocks) - a lasting footprint, not a peak. On main (V8 13.1) the second pass ran those finalizers inside the callback.

**Fix**: A second, narrower safe point inside a callback, decided by construction instead of by type: at a binding's return into the script of the innermost callback invocation (no binding between the two), only the finalizer of an object a script-called constructor made since that invocation began may run. Every DOM algorithm on the stack has been suspended in its call into script since before such an object existed, so none holds a pointer to it. The agent's callback clock ticks at every invocation (`DeferredTeardown.Callbacks`), the constructor trampoline stamps the wrapper cache entry (`WrapperCache.setConstructed`), and everything else - nodes, operation results, older objects, the other finalizer kinds - still waits for depth zero.

**Takeaway**: **Before a design says "at the next safe point", list the kinds of script by the depth they run at - top-level and modules (0), promise jobs (0), script a conversion runs inside a binding (1+), callbacks (1+ for their whole run) - and measure the churn loop in each: the five-mark `event`, `eventpromise`, `eventcb` and `eventlistener` variants (.v8up/gcdiag-b6c.sh). A safe point that needs depth zero covers the first two only.**
