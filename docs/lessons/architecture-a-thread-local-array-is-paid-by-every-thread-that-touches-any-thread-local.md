# Architecture: A thread-local array is paid by every thread that touches any thread-local

**Date**: 2026-11-11
**Lesson**: A large thread-local costs its size on every thread that touches ANY thread-local of the image (macOS) or on every thread at creation (Linux), so a per-thread buffer is mapped explicitly for the threads that need it, never declared `threadlocal`.

**Why**: Thread-local storage is allocated per image, not per variable. On macOS the first touch of any thread-local of an image makes dyld allocate that image's whole thread-local block for the thread and write its initial content over all of it (`dyld::ThreadLocalVariables::instantiateVariable`): the block is footprint in full. On Linux glibc allocates the executable's static TLS block with every thread and clears it. Neither asks which variable the thread wanted.

**What Happened**: Zig std gives its fault handler an alternate signal stack per thread when `std.Options.signal_stack_size` is set (default `1 << 18`): `std.Thread.maybeAttachSignalStack` declares `threadlocal var signal_stack: [size]u8` and runs before `main` and at the start of every `std.Thread.spawn` thread. That put a 262,144-byte array in the thread-local block of every Crane binary: one 278,528-byte malloc block per thread that touched a thread-local. On main only the main thread paid. On the V8 15.7 port V8's worker threads began to touch a thread-local (absl's thread identity), so each of the 13 workers on a 14-core host paid for a signal stack it never registered: +3.6 MB per process, and the port's memory bar failed (lane v8up b4's evidence, tmp/plans/tls1-evidence.md). The array was visible the whole time: `nm -n -m <binary> | grep __thread_bss` names it, `size -m` shows `__thread_bss: 0x400e9`.

**Fix**: (lane tls1)
1. The roots (tools/repl.zig, tests/wpt_runner/main.zig, tools/gc_bench.zig, src/webdriver/main.zig, src/lib_exports.zig) set `std_options.signal_stack_size = null`.
2. The platform maps each thread's alternate stack itself (src/platform/kit/posix/signal_stack.zig; protocol 6.4 `attachSignalStack` / `detachSignalStack`): mmap PROT_NONE with a guard page each side, mprotect the middle, sigaltstack, unmapped when the thread ends - Chromium's design (Crashpad `CrashpadClient::InitializeSignalStackForThread`, crashpad_client_linux.cc). Lazily committed: an unused stack costs no memory. Every `spawnThread` thread has one; a root's `main`, the worker and IndexedDB threads and the hosts' own threads attach in two lines.
3. `tools/thread_local_size.zig` reads a built binary's thread-local block from its headers and names its largest thread-local symbols; build.zig runs it on the production runner, the bug-finding runner and the release console as part of their own steps, against a budget that only goes down (tools/thread_local_size_budget.txt).
4. A fixture process overflows its stack on the main thread and on a spawned thread, in ReleaseSafe and Debug, and the test reads the fault report and its trace from its stderr (tests/platform/tls1_stack_overflow_test.zig).

**Measured** (chat.local, 14 cores, release consoles, an idle console on a blank page): main's image block 262,385 -> 241 bytes, footprint 23.8 -> 23.3 MB, per-thread blocks 2 x 278,528 -> 2 x 256 bytes; the V8 15.7 port's block 262,605 -> 465 bytes, footprint 28.0 -> 24.0 MB, per-thread blocks 15 x 278,528 -> 15 x 512 bytes. Linux: the runner's PT_TLS block 262,400 -> 256 bytes (per-thread resident memory there was not measured).

**A finding about Zig std, not patched and not filed**: std has no hook for a caller-supplied signal stack. `signal_stack_size` is the only setting, `Thread.callFn` calls `maybeAttachSignalStack` unconditionally, and that function's storage is the thread-local array. A program that wants the handler's stack anywhere else must set the option to null and call `sigaltstack` itself on every thread it starts; a thread started with a bare `std.Thread.spawn` then has no alternate stack. The test executables keep std's stack for that reason (their tests call `std.Thread.spawn` directly in 538 places).

**What a thread nobody attached gets**: nothing, before and after. V8's worker threads are not std threads; they never had an alternate stack, they only paid for the array. A stack overflow on one ends the process with the fault's signal and no report.

**Takeaway**: **Before declaring anything `threadlocal` (or linking a library that does), ask what every OTHER thread pays for it: the answer is its full size. Per-thread memory that only some threads use is mapped for those threads, and the linked binary's thread-local block is held to a budget by a check that reads the binary.**
