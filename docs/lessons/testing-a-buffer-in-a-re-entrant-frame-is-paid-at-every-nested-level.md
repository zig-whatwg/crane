# Testing: A buffer in a re-entrant frame is paid at every nested level - measure the depth it leaves

**Date**: 2026-11-15
**Lesson**: A stack buffer in a function script can re-enter (dispatchEvent from a listener) costs its size again at every nested level, so its price is how many levels fit before the engine's stack check - measure that depth on the production build before and after, and compare it with what the browsers reach.

**Why**: V8 keeps script inside a stack limit about 1 MB below where it was entered and checks it on every entry to a function, so a larger native frame between two script frames cannot overflow the stack: it lowers the depth at which script gets a RangeError. That depth is invisible to every other gate - no test nests a hundred dispatches - and it differs by build: the Debug test build's frames are several times the production build's.

**What Happened**: Lane ev1 put an event's path in the dispatch's frame, 32 items inline as WebKit's EventPath has. The integrator asked what that does to re-entrant dispatch. Measured with a page that dispatches from its own listener until it cannot (gc_bench, production build, chat2.local): main reached 130 nested levels - about 7.5 KB of native stack per level already - and the first build, with 88-byte items, fewer; the item was cut to 72 bytes (2,400 B per level with the path's header) and the depth is 102. The Debug test build reaches 46 on main and 41 with the path, so a test that nested 100 dispatches would have failed on main too. The browsers, same page: Chrome 157 stops at 43, by an explicit cap on re-entrant script (Blink's V8ScriptRunner, kMaxRecursionDepth = 44), and Firefox 159 reaches 338.

**Fix**: (1) Before adding a buffer to a frame script can re-enter, measure the nested depth on the production build (a page that re-enters until it catches the RangeError; keep 100 objects per level reached and read the count from gc_bench's "instances still live"). (2) Shrink the item before shrinking the count. (3) Declare the buffer `undefined` in a small wrapper with `@setRuntimeSafety(false)`, or ReleaseSafe fills it with 0xaa on every call. (4) Pin the behaviour, not the number: a test that re-enters without bound must end in the engine's RangeError and leave the page working; assert a floor far below the measured depth, because the Debug build's is lower.

**Takeaway**: **A stack buffer in a frame script can re-enter is priced in nesting depth, not bytes: measure the depth on the production build before and after, compare it with the browsers' (Chrome caps re-entrant script at 44), and test that running out ends in a RangeError, never a crash.**
