# Spec Compliance: Trace what the reference does, not what its schema allows

**Date**: 2026-11-24
**Lesson**: Before designing a mechanism to match a reference implementation, follow the value from the schema that lets it in all the way to the code that uses it. A validator that lets something through, or a comment that says why, does not show the feature exists.

**Why**: chrome-devtools-mcp v1.13.0's evaluate_script declares `sourcePath: {local: true, remote: true, allowUrl: true}` in its verifyFilesSchema, and the comment beside it says "sourcePath may be an http(s): URL the server fetches". McpContext.loadResource has an http(s) branch with a network loader. All three suggest the server fetches a script source over HTTP. It does not. resolveScriptSource (src/tools/script.ts) passes every value that does not start with "file:" through `pathToFileURL(value)`, which path.resolve()s it under the server's working directory. "https://a.test/x.js" becomes file:///<cwd>/https:/a.test/x.js, and loadResource then takes its file: branch. The http(s) branch serves only overrideDevToolsGlobals (the DevTools frontend's own loads for the performance tools).

**What Happened**: Lane mcp1's batch 3 design planned a batch 3b for http(s) sourcePath. It covered an event-loop port owned by the MCP server, transfers through the platform HTTP client, Google's blocked and allowed URL patterns, and 20-hop manual redirects, each checked. That design rested on the schema, the comment and loadResource's branch. While translating resolveScriptSource statement by statement, the lane saw that the value never reaches the http(s) branch. One line of Node confirmed it: `pathToFileURL("https://a.test/x.js").href` from /private/tmp is `file:///private/tmp/https:/a.test/x.js`. The answer Google's server gives is "Unable to read script source from https://a.test/x.js: Access denied: path \"<cwd>/https:/a.test/x.js\" ... is not within any of the configured workspace roots." (or ENOENT when the working directory is inside a root). Batch 3b would have been an invented path: behaviour the reference does not have, which no differential case could ever confirm.

**Fix**: Crane reproduces v1.13.0 exactly. Policy.loadScriptSource (src/devtools/mcp/paths.zig) makes a non-file: value a cwd-relative path, checks it against the roots, then reads it. Its comment cites resolveScriptSource and loadResource with the pin. The https: value is a must-be-equal case in the differential suite ("files: script sources", tools/mcp_diff/cases.json). A later chrome-devtools-mcp that starts fetching fails that case when the pin is bumped. Batch 3b was dropped (main, 2026-11-24).

**Takeaway**: **Conform to what the reference executes, not to what its schema admits or its comments promise: trace the parameter from validation to its last use, confirm the answer against the running reference, and pin that answer in a differential case so a later version's change is caught.**
