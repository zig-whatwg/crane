# Architecture: A live set iterator needs only the sequence of the entry it last yielded

**Date**: 2026-10-17
**Lesson**: Give each set entry the sequence number it was appended with, increasing, and let an iterator remember only the sequence it yielded last: its next step is "the first entry after that sequence". That is a JavaScript Set's iteration exactly, and nothing in the set points at an iterator.

**Why**: WebIDL 3.7.12 makes a setlike's iterators live ("the size of set, and the order of its entries, might have changed while execution ... was paused"), and custom-elements/state/ElementInternals-states.html checks it the way a Set behaves: an entry deleted before the iterator reaches it is skipped, a deletion behind it shifts nothing, an append is visited, a cleared set's later appends are visited. An index into the list breaks on the first deletion behind it. The two designs the browsers use both point from the set to its iterators or keep a second object in step with it: Blink's CustomStateSet keeps its iteration sources in a set that delete() walks to adjust their indices; Gecko and WebKit forward every member to a JavaScript Set kept beside the object. Either way something must unlink or mirror on every change, and an iterator abandoned half-way must be found when it dies - a finalizer, ordered against the set's own teardown, which is the engine lifetime question this codebase keeps getting wrong.

**What Happened**: CustomStateSet's setlike members were codegen-synthesised operations (`call_has`, `call_add`, ... implemented by the impl), and values, keys, entries and %Symbol.iterator% did not exist: `[...internals.states]` threw, and two of the file's four subtests failed in Crane while all three browsers pass them. The impl's own backing (`States`) kept tombstones and compacted only while no forEach was running - a scheme that cannot know when a script-held iterator is done.

**Fix**: `webidl.setlike.SetEntries(T)`: entries in append order, each with its sequence; `after(sequence)` is a binary search. The binding defines the setlike members (codegen emits `Meta.setlike` and a `setlikeEntries` delegate, no operation); an iterator object holds the set's wrapper, its kind and the last sequence in private properties, so the set lives while an iterator can reach it and a finished iterator lets it go. tests/webidl/set_entries_test.zig pins the Set semantics; crane/b4-setlike-members.html the members through the binding.

**Takeaway**: **When an iterator must survive changes to what it iterates, make its position a value the collection can always answer for (a sequence number), not a place inside the collection (an index) - then the collection never needs to know its iterators exist.**
