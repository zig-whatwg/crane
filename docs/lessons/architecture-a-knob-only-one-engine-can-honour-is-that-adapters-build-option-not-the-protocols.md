# Architecture: A knob only one engine can honour is that adapter's build option, not an option of the protocol

**Date**: 2026-11-12
**Lesson**: Before adding an option to the engine protocol, ask whether a second engine could honour it through its public API. If none can, it is not a protocol option: it is a build option of the one adapter that has the knob.

**Why**: The engine protocol is the seam every adapter implements (V8 today, JavaScriptCore on iOS, QuickJS, the test adapter). An option on it costs every adapter a capability line and an operation, costs every host a configuration field and its plumbing to each agent it makes (the Browser, the worker registry, both worker creation sites), and promises hosts something the other engines will silently ignore. JavaScriptCore's public API has no heap sizing at all - JSBase.h offers JSGarbageCollect and nothing else about the heap; JSContextRef.h and JSVirtualMachine.h nothing - so a young-generation limit on the protocol would have been `.unsupported` on every adapter but one, forever.

**What Happened**: Lane v8up b7 found that V8 15.7's larger young generation (32 MB semispaces, 13.1 capped the scavenger at 8 MB) was most of the port's memory gap, and that the size was a product decision. The first build made it a protocol option: `AgentOptions.young_generation_limit`, a capability, `engine.youngGenerationLimitOf`, a `BrowserConfig` field, a `WorkerRegistry` field, two worker creation hunks, a line in three other adapters, tests in three directories, a console flag half written - 19 files. The user's one question undid it: "will this be necessary for javascript core? If not then it should just be a v8 build flag". The second build is `-Dv8-young-generation-mb=<n>`, read at compile time by the adapter (src/runtime/engines/v8/young_generation.zig) and applied where the adapter makes an isolate: build.zig, three adapter files and one test file, and every agent of the build - workers included - gets it with no plumbing.

**Fix**: (1) For a proposed protocol option, name the public API of at least one OTHER engine that would implement it; read that engine's public headers before designing, as for any capability. (2) If only one engine has the knob, make it that adapter's build option (`-D<engine>-...`, passed in `build_options`, one default constant in the adapter), documented with the adapter's build options (docs/engine-protocol.md, 7b). (3) A build-time value is tested through the adapter's one creation function with the value given (a seam the product calls with the build's constant), plus one test that the protocol's own entry point has the build's value - run in a second build to see a command-line value arrive.

**Takeaway**: **The protocol holds what engines have in common. A setting only one engine's public API can honour belongs to that engine's adapter as a build option - ask "which other engine implements this?" before adding a protocol option, a capability or host plumbing for it.**
