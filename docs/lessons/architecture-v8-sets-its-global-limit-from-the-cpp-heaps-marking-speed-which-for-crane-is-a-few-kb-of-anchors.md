# Architecture: V8 sets its global limit from the C++ heap's marking speed, which for Crane is a few KB of anchors - a smaller anchor reads as a slower collector and a page collects later

**Date**: 2026-11-15
**Status** (2026-11-15, lane dm3, the same evening): three corrections, and the outcome. (1) The line numbers below for `heap.cc` (`UpdateAllocationLimits`, :2609-2670) and `heap-controller.cc` (:113-132) are the Mac's source checkout's, an older V8 main; in the linked 15.7.112.43 (read it on server1, `~/v8-15.7.112.43/v8`) the computation is `HeapLimits::UpdateAllocationLimits`, `src/heap/heap-controller.cc:241-392`, and `DynamicGrowingFactor` is :165-182. The `cpp-heap.cc` lines are right. (2) On main 2bdfc95a348, with the 16-byte anchor merged, the factor no longer swings on these pages: the ratio is 10 to 43 and the global factor reads 4.0, its ceiling, in almost every collection (`parser.document-write` 103 MB in 6 of 6 runs, chat2.local). V8's own factor on the same collections is 1.1 to 1.7: Crane gives V8 no `ResourceConstraints`, so V8's default 1.4 GB old generation puts its own factor under the "small device" ceiling (`MaxGrowingFactor`, :97-123) while the global one, sized from twice that, gets 4.0. (3) Fix step 3's repair does not exist in V8's public API: the size is written only from the C++ heap's marked bytes (`cpp-heap.cc:1016`), the speed is recorded only there (:1022), and no header of `include/` sets either; upstream main is the same. What an embedder can set are three flags that change V8's own factor too, measured on the same pages (tmp/plans/lane-dm3-handoff.md): `--heap-growing-percent=70` lowers `parser.document-write` to 85 MB and runs 25% to 50% more full collections elsewhere for nothing; `--sqrt-allocation-limits` raises it to 125 MB; `--memory-saver-mode` lowers five rows by 15% to 37% with 1.3 to 2.3 times the collections. The integrator ruled no change to the default build (2026-11-15, 7:06 PM ET); the row stays as the user ruled it.
**Lesson**: After every full collection V8 picks the growing factor of its global limit from two speeds of the C++ heap: bytes marked per millisecond and bytes allocated per millisecond. Crane's C++ heap holds only wrapper anchors, so both are a few KB over tens of microseconds, their ratio sits next to the formula's pole, and the factor moves between 2.3 and 4.0 on an 8-byte change of an anchor or 26 microseconds of timing. A memory row that moved with no change in what is kept or freed may be this factor: read V8's own line for it before looking for a leak.

**Why**: V8 15.7.112.43 `src/heap/heap.cc` `Heap::UpdateAllocationLimits` (:2609-2670) computes a factor for its own heap (old-generation speeds) and one for the embedder (`GCTracer::EmbedderSpeedInBytesPerMillisecond`, `EmbedderAllocationThroughputInBytesPerMillisecond`), takes the larger, and multiplies the sizes by it. The embedder's marking speed is recorded in `src/heap/cppgc-js/cpp-heap.cc` `CppHeap::FinishMarkingAndProcessWeakness` (:992-999): the C++ heap's marked bytes over its marking time, averaged over the recent collections. The factor (`src/heap/heap-controller.cc` `DynamicGrowingFactor`, :113-132) is `F = R x 0.03 / (R x 0.03 - 0.97)` with `R` the ratio of the two speeds, bounded to 1.1-4.0: it is 4.0 for every `R` under 43, 2.5 at 54, 1.8 at 73, and it has a pole at 32. In Blink the nodes are objects of that heap (Chromium 157.0.8103.50 `core/dom/node.h:165`), so the speed is megabytes per millisecond of real marking and `R` says something. In Crane a node is Zig memory; the C++ heap holds one anchor per wrapper (16 to 24 bytes) while the marking time holds the walk over every kept tree. The numerator is a count of anchors, the denominator is DOM work.

**What Happened**: Lane wrap1 batch 3's cost window read `parser.document-write` 20% higher in steady memory on the lane (103.4 against 86.0 MB, three of three runs, macOS malloc's deferred reclamation off). It had been equal that morning, before lane dm2's change that takes dying trees out of the figure V8 is told. Both sides freed the same memory. V8's trace (`--trace-gc-verbose`, 16 runs a side on chat2.local) showed the full collection inside the previous row, `parser.dom-parser`, ending with `[GlobalMemoryController] factor 2.3-2.9` on main in 15 runs (next limit 55-59 MB) and `3.0-4.0` on the lane in 15 runs (60-66 MB). With the limit at 59 MB or lower the page reaches V8's soft limit as that row ends, a marking task runs in the gap between the rows, and `document-write` starts clean and settles at 85 MB; otherwise marking starts 0.1 s into the row and it settles at 95-103 MB. A print of each cycle's phases from V8's metrics recorder (6 more runs a side) gave the inputs. The C++ heap's marking time was the same on both sides: 18 against 21 microseconds in the first collection, 63 against 60 in the second (medians). Its marked bytes were not: 616 and 3,776 on main, 584 and 3,072 on the lane - 704 bytes less in the second collection, because the batch made the anchor of a non-node wrapper 16 bytes where it was 24. The figures V8 printed are exactly those sums: main (616 + 3,776) bytes / (15 + 63) us = 56,308 bytes per millisecond, the lane (584 + 3,072) / (25 + 56) = 45,136. With the allocation speed equal (1,013 to 1,020), `R` is 55 on main and 45 on the lane, and `F` 2.5 and 3.5. Main is exposed to the same swing: in one of its six runs the first collection's marking took 44 microseconds instead of 18, the factor came out 4.0, and the row read 103 MB. The user accepted the row for this batch; the design fix belongs to the owner of the figure.

**Fix**:
1. For a memory row that moved while frees and kept bytes did not: build both sides with `-Dv8-extra-flags="--trace-gc --trace-gc-verbose --trace-incremental-marking"` and compare the `[GlobalMemoryController] factor ... (gc=..., mutator=...)` line after each full collection, then the `[IncrementalMarking] Start (...)` lines' `global: size / waste / limit`. A different limit after the same collection is V8's schedule, not the change's memory.
2. Get the factor's inputs from V8, not from arithmetic: `v8::metrics::Recorder::AddMainThreadEvent(GarbageCollectionFullCycle)` gives `main_thread_atomic_cpp.mark_wall_clock_duration_in_us` and `objects_cpp.bytes_after` for each cycle (the adapter's `GCPhaseRecorder`, in gc_bench's build). Check that they reproduce the `gc=` figure V8 printed.
3. Do not tune the anchors to move the ratio (padding them back would have "fixed" the row): the ratio measures nothing for Crane. The repair is to give V8 a marking speed and a size that mean what its formula assumes - the bytes the walk keeps alive, where it reads the C++ heap's marked bytes - or to bound the embedder's factor; that is a change to how Crane's figure meets V8's limits (tmp/plans/dom-memory-figure-design.md), with its own measurements.
4. Until then, expect any change to what lives on the C++ heap (an anchor's size, how many wrappers a page makes) to move rows that sit near a limit, in either direction, on main as well.

**Takeaway**: **V8 schedules Crane's full collections with a ratio built from the C++ heap, and Crane keeps almost nothing there. When a row moves and the memory did not, print V8's growing factor after each collection on both sides before anything else.**
