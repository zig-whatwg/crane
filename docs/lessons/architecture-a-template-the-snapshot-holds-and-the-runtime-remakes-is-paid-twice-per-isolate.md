# Architecture: a template the snapshot holds and the runtime remakes is paid twice per isolate

**Date**: 2026-11-19
**Lesson**: Every TemplateInfo (and Name) a V8 context snapshot reaches goes into the STARTUP object cache, which every isolate restored from the blob deserializes and keeps; when Crane's runtime makes the same templates again (interface_bindings.registerAllTemplatesOnly), the snapshot's copy is dead weight in every isolate and its interface objects in every realm.

**Why**: V8's ContextSerializer::ShouldBeInTheStartupObjectCache (src/snapshot/context-serializer.cc) sends `IsTemplateInfo`, `IsName`, `IsSharedFunctionInfo` objects to the startup snapshot's object cache, a root list of the isolate. Crane's snapshot generator builds every interface object in its contexts, but a restored realm reinstalls its interface objects from templates the runtime makes at the isolate's first realm, so the snapshot's templates are never used again - yet they stay. The blob itself is read into anonymous memory (browser/process.zig), so its growth is footprint 1:1, and every realm's context deserialization rebuilds the snapshot's (stale) interface objects.

**What Happened**: Lane css2 put CSSStyleProperties' ~1,000 CSS property accessors (~2,000 FunctionTemplates with "get x"/"set x" names) on its prototype template: +1.2 MB per isolate, +50-90 KB per realm, blob 2.68 -> 2.94 MB; reverted. Lane css3 measured the split with diagnosis consoles (--trace-gc-object-stats in the runtime's V8 flags only, perf_bench memory passes with --collected and MallocLargeCache=0, vmmap -summary on a repl held open by a FIFO): the snapshot copy was +309 KB of live heap at start plus +272 KB of blob, and ~47 KB of unreachable prototype in every realm whether it used style or not; the runtime copy +304 KB of V8 heap; each realm that used style ~51 KB for its own prototype; and the tip binary showed ~300 KB more malloc FRAGMENTATION with identical live malloc (vmmap's MALLOC ZONE table: same ALLOCATED bytes and block counts) - placement, not memory held. A base-vs-itself pass read 0.000 MB, so the remaining differences were real.

**Fix**: (1) Costly templates stay out of the snapshot: the C++ installer returns under g_snapshot_mode (the generator's process-wide flag). (2) The runtime makes such a template on first use per isolate, as Blink makes every interface's (V8PerIsolateData::FindV8Template / WrapperTypeInfo::GetV8ClassTemplate): interface_bindings.madeOnFirstUse lists it; registerAllTemplatesOnly gives every realm, the page's too, a lazy interface object (global_constructor_handler.installLazy) and makes no template; the wrap path builds the interface object before the first wrapper (ensureInterfaceObjectBuilt), so the prototype is whole.

**Takeaway**: **Before adding templates, ask where each copy lives: the snapshot's copy lives in every isolate even when the runtime remakes it, the runtime's lives from the first realm unless it is made on first use - measure V8 heap (vmmap's App-Specific Tag 16, object stats), the blob, and malloc's ALLOCATED vs FRAG separately, never footprint alone.**
