# Architecture: Eager slot assignment stays off trees without shadow roots, by its own invariant

**Date**: 2026-10-09
**Lesson**: DOM's slot assignment can run exactly as the standard writes it - recomputing assignments at every insert, remove and attribute change - without costing a tree that has no shadow root anything but a field test and a walk to the parent's root, because the algorithm's own invariant says when a step can change nothing.

**Why**: The standard's steps look expensive: insert step 7.6 and remove step 10 run "assign slottables for a tree" over the whole tree, on every insertion and removal. But a slot's assigned nodes depend only on (a) the slots of its shadow tree, in tree order, with their names or manually assigned nodes, and (b) the children of that tree's host. And a slot outside a shadow tree always has none: the remove steps empty a slot as it leaves one. So "assign slottables for a tree" can change something only when the tree is a shadow tree and the inserted or removed subtree holds a slot; in every other case each slot already has exactly the assigned nodes it would get, and the run would neither change nor signal anything. Blink and WebKit go lazy instead (SlotAssignment::RecalcAssignment, NamedSlotAssignment::assignSlots) and need extra bookkeeping to signal slotchange at the steps the standard names; eager needs none, and slotchange timing is exact by construction.

**What Happened**: Lane slots implemented DOM 4.2.2.3-4.2.2.5 (find a slot, find slottables, find flattened slottables, assign slottables, assign slottables for a tree, assign a slot, signal a slot change and notify step 7) and their callers. The 21 slot files went from 8 to 148 of 185 subtests. On a no-shadow tree, gc_bench's interleaved append/remove cost moved by the price of the guards only. Two more things the standard leaves out, which every engine does:
- A slottable's assigned slot is never reset by the standard - a removed node, or one whose slot left the tree, keeps naming it, and "get the parent" would route its events through that slot. Assign slottables clears the old ones that still name the slot (Blink ClearFlatTreeNodeData, Gecko RemoveAssignedNode, WebKit assignSlots).
- The agent's signal slots is an ordered set, and a page that builds a thousand components signals thousands of slots in one task, before any microtask checkpoint. A linear membership test made the shadow-heavy timing page quadratic (samples rising 716 -> 931 ms within one run); a membership map beside the list made it flat.

**Fix**: shadow_dom_algorithms.runInsertionSlotSteps / runRemovingSlotSteps: a parent-is-host guard, a vtable test for "parent is a slot", and the root walk; "assign slottables for a tree" only for a shadow tree that gains or loses a slot. Every node reference the slot state keeps is weak (slot_helpers.NodeRef: node, Instance, slab generation); the eager clearing keeps them true and the generation keeps a teardown's leftovers from being read. A signaled slot has pending activity (engine.keepPlatformObjectAlive) until its slotchange fires, so a collection between the mutation and the microtask cannot lose the event.

**Takeaway**: **Before making a spec algorithm lazy for speed, find the invariant that says when each step is a no-op: an eager implementation guarded by it can be as cheap on the common path, and stays exact at every observation point.**
