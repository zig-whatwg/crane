# Architecture: A weak list walked across an engine call loses entries mid-walk - walk it through a cursor its removals move

**Date**: 2026-10-18
**Lesson**: A list whose entries are platform objects the engine collects (a document's live ranges, its NodeIterators) changes inside any engine call that allocates, because that call can start a collection whose prologue runs the previous collection's teardowns. A walk that holds a slice of the list reads freed or vacated slots.

**Why**: V8 runs every pending second-pass callback at the start of the next collection (`Heap::CollectGarbage`: "Ensure that all pending phantom callbacks are invoked"), before marking. Crane tears a collected wrapper's instance down in the second pass (`wrapper_cache.finalizeCollected`). So `engine.traceChild`, a wrap or a new string can tear down any object whose wrapper died earlier, and each teardown runs its deinit, which leaves the lists it joined. engine_protocol 4.12 said only "a point where engine calls are allowed"; the JSC note said "a turn of the host's event loop - the rule V8's second pass keeps". Both were wrong about V8. The node side already knew this (see [A collected tree is freed between tasks](architecture-a-collected-tree-is-freed-between-tasks-a-slice-at-a-time.md)); the weak lists did not.

**What Happened**: Codex row 73's `crane/sl2-cost-selection.html` makes 100,000 selection ranges and then removes their paragraph. It crashed main every run with SIGSEGV at 0xaaaaaaaaaaaaaaaa in `Range.livePoints` <- `mutation.runLiveRangePreRemoveSteps`. The brief's guess was a freed Range left on the list, but `Range.deinit` unregisters correctly. A walk-gated trace showed what happened instead:
- the walk iterated `for (internal.ranges.items) |range|`, a slice captured once;
- step 5's `set_end` redrew the range's edge (`keepContainers` -> `traceChild`), and that started a collection;
- the collection's prologue tore down 21,843 of the walk's 37,733 ranges (`unregisterRange` <- `Range.deinit` <- `finalizeEntry` <- `WeakCallbackSecondPass` <- `InvokeSecondPassPhantomCallbacks`);
- `orderedRemove` fills each vacated tail slot with undefined, and the walk read one at i=26,306.

Probes split the cause from its triggers. Ranges script kept: no crash. Ranges outside the removed node, so no `traceChild` in the walk: no crash. `TestUtils.gc()` before the removal: no crash. The removal in a later task: no crash. `splitText` and `normalize()` crashed the same way.

**Fix**: `dom.live_range_list.LiveList`, the shape of Gecko's nsTObserverArray (xpcom/ds/nsTObserverArray.h, `RemoveElementAt` -> `AdjustIterators`). Each walk in progress is a cursor on the walker's stack. `remove` moves every cursor that had passed the removed entry, and a walk reads one entry at a time and never holds a slice. Every walk of the document's live ranges and NodeIterators in mutation.zig goes through it: pre-remove, insert, split, replace data, normalize, adoption (which also drops its copy; a copy holds entries a teardown frees) and the NodeIterator pre-removing steps. Its tests remove entries before, at, adjacent to and after the cursor, and inside a nested walk; 4 of 8 fail without the adjustment. A cursor does not keep the entry it is on, though: a collected range whose new boundary node has no wrapper yet allocates in its own step (traceChild wraps the child), and the collection that starts can free that range mid-step. So the second part is an engine operation, `engine.holdTeardowns(realm)` / `release()` (`deferTeardowns` / `resumeTeardowns`, engine_protocol 4.12), held around every walk. Collections still run inside a hold, but `wrapper_cache.finalizeCollected` lists the entry instead of tearing it down. The release that ends the outermost hold tears the listed entries down one at a time, taking each next one afresh, because a teardown may start a collection of its own. In Debug builds the adapter's script-running operations panic while a hold lasts (Blink's ScriptForbiddenScope). V8's DisallowJavascriptExecutionScope was tried first and fired on a legitimate wrap inside a walk: V8 counts the builtin behind v8::Set::Add, which a new wrapper's tree edges use, as script.

**Takeaway**: **Any engine call that can allocate can run teardowns: a list of objects the collector frees must survive a removal at every engine call in its walk - walk it through a cursor the list moves, never through a slice or a copy of raw pointers - and hold the agent's teardowns for the walk, so the entry being stepped is not freed under its own step.** Before calling a crash "a freed object left on a list", log every register and unregister while the walk runs: here every free unregistered, and the list shrank under the walk.
