# Spec Compliance: A timestamp taken after the time origin must not coarsen to the zero that means "never taken"

**Date**: 2026-11-27
**Lesson**: When a browser passes a "greater than 0" timing test that Crane fails by the tick, look for a conversion rule before assuming the browser's speed is the reason. WebKit raises a fetch timestamp that lies after the time origin but coarsens to 0 up to one tick. That is a mechanism Crane can implement. A process hop is not.

**Why**: Resource Timing uses 0 to mean "not set": "convert fetch timestamp" step 1 returns 0 for a zero timestamp, and a redirectStart of 0 means "no redirect". The spec's relative coarse time also gives 0 for a moment in the origin's own tick. On one thread, with a 125 us grid, a navigation's first fetch starts 25-120 us after its time origin, so the real mark and the missing mark often read the same. WebKit's networkLoadTimeToDOMHighResTimeStamp (PerformanceResourceTiming.cpp; 306074@main, bug 306010, shipping in Safari 27.2) returns 0 at or before the origin. After the origin it returns the reduced delta, or one tick when that delta reduces to 0. Chrome passes the same tests only through its renderer-to-browser hop: its navigation_start is taken in the renderer and its fetch_start in NavigationRequest::OnStartChecksComplete, and a headless Chrome 157 probe measured redirectStart at 6.7-39.4 ms. Like Gecko, Chrome reports the clamped clock as it is.

**What Happened**: navigation-timing/nav2-test-redirect-server.html, secure-connection-start-non-zero.https.html, nav2-test-timing-persistent.html and test-timing-attributes-dependent-on-document-load.html each passed or failed according to whether Crane's navigate()-to-fetch gap crossed a tick. Lane crane-red1 found 60 of 60 runs agreed with that model. Two of the files carried follows-majority exemptions and the others carried timing-bound dispositions, until the user ruled on 2026-11-27 that a file two browsers pass blocks 0.1. An earlier reading of the same failures (lane flaky6, and the lesson that a relative time is zero when it shares a tick with its origin) found the gap but no browser rule, and concluded that only an artificial delay could help. Lane tbfix1 read all three engines' conversion functions. WebKit's rule had landed in January 2026, after that reading.

**Fix**: hr_time.TimeOrigin keeps its unsafe moment beside the coarse one and converts a fetch timing info's moments with WebKit's rule (`relativeFetchTime`). Performance installs the rule as performance_timeline's `fetch_timestamp` hook, which FetchTimestampConverter calls. The rule does not touch unload, DOM and load marks (WebKit's millisecondsSinceOrigin), coarsenTime, performance.now() or timeOrigin. tests/html/tbfix1_fetch_timestamp_test.zig injects moments 49 us and 33 us after an origin that sits 10 us into a tick. It was red at main, with "expected 0.125, found 0".

**Takeaway**: **Before calling a sub-tick result "engine speed, only a delay would fix it", read each engine's timestamp conversion function, not only where its marks are taken. A browser may define the result (here "after the origin is never 0"), and a rule can be reproduced where a process hop cannot.**
