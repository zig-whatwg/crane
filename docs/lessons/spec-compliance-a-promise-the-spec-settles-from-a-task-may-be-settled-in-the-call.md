# Spec Compliance: A promise the spec settles from a task may be settled in the call by the browsers

**Date**: 2026-11-15
**Lesson**: When a test stops passing after an event-ordering change, first measure WHEN each browser settles the promise the test waits on: a spec's "in parallel, then queue a task" is often done inside the call, and the test passes in browsers because of that, not because of the ordering.

**Why**: WebCrypto 14.3 gives every SubtleCrypto method one shape: return the promise, work in parallel, settle from a task on the crypto task source. Chrome computes on the calling thread and completes before returning for everything but RSA key generation and PBKDF2. Safari does importKey, exportKey, non-RSA generateKey and AES-KW wrapping synchronously and the rest on a work queue. Firefox goes to a background thread unless the task completed early. A page - or a WPT - that reacts to importKey in a microtask of its last script therefore has its keys before DOMContentLoaded in two of three browsers. Crane followed the spec's shape with two tasks (compute, then settle), so the keys arrived two turns later.

**What Happened**: Generation 225 lost WebCryptoAPI/derive_bits_keys/derive_key_and_encrypt.https.any.js (6 subtests -> 2). The file defines its four tests from importKey()'s reaction; testharness completes at the load event's 0 ms timer when every defined test is done. Lane nav2 batch 12 had moved load to the end of the parse (as Chrome and Safari fire it), so the timer ran between Crane's compute task and its settle task. The loss looked like a load-ordering bug. A three-browser probe showed otherwise: with `p.then(A); Promise.resolve().then(B)`, A runs first only when `p` was settled inside the call - and it does for importKey in Chrome and Safari. Firefox settles later and passes only because its load event is a later task still.

**Fix**: `webcrypto.tasks.Settles` and `operations.Request.settles`: importKey, exportKey, generateKey unless RSA, and wrapKey / unwrapKey by AES-KW settle in the call; the others keep their task. Each row is what two of the three browsers do (golden rule 2), and together the rows are Safari's behaviour. tests/wpt/crane/wc1-subtle-settles-in-the-call.https.html is the probe as a test (Safari 44 of 44, Chrome 30, Firefox 25, every row passing in two).

**Takeaway**: **Probe when a promise settles - a reaction registered on it against a microtask queued after it - in all three browsers before touching the event order a test seems to depend on; "in parallel" in a spec does not tell you a task ever runs.**
