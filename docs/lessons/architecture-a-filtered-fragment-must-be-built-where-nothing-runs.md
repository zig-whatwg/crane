# Architecture: A fragment that will be filtered must be built where nothing runs

**Date**: 2026-10-16
**Lesson**: Creating an element is when it schedules its work - an img's load, a compiled `on*` handler, a custom element upgrade - so a sanitizer that filters a parsed fragment cannot undo what the parse already started; the fragment has to be built in a document with no browsing context, and insertion adopts what survives.

**Why**: Crane's fragment conversion (src/html/dom_parser.zig) created every node in the context element's live document and appended its attributes through the normal change hooks. `<img src onerror>` queued "update the image data" (with a keep on the element) and compiled its handler there and then; a custom element was looked up in the registry and queued for upgrade. Removing the element afterwards left all of it scheduled: Codex row 41's safe setHTML ran stripped handlers and fetched removed images (sanitizer-inert-document.html 1/4; Chrome and Firefox 4/4).

**What Happened**: The HTML fragment parsing algorithm's own text builds in the target's document (its root insertion target is a fragment of that document), which is what innerHTML does in every engine - so the default path was right. The sanitizing entry points are where the engines differ from it: Blink's FragmentParser parses into `GetDocument().EnsureTemplateDocument()` with a null registry whenever a streaming sanitizer runs, Gecko's `SetAndFilterHTML` into `CreateInertHTMLDocument` ("We MUST NOT cause any requests during parsing"), and both insert the result with an ordinary append. Making the template contents owner document actually inert in Crane needed four things beyond the parser: update-the-image-data step 1 for a document with no browsing context, the img's adopting steps (a relevant mutation), media and track loads refused there (Blink: "document has no frame"), and the spec's internal raw uncompiled handler for `on*` attributes set there, compiled on first use. A `<template>`'s own contents had been fetching images and losing their handlers on adoption all along.

**Fix**: `FragmentOptions.inert_document` (and `html.custom_elements.parseFragmentToFilter`) builds in the context document's template contents owner document with no registry; template contexts build there too; `src/dom/adopting_steps.zig` runs HTML's adopting steps from DOM adopt; EventTarget keeps a raw handler as an activated listener marked `raw_uncompiled`, compiled by Element's `compileRawEventHandler` at getter or dispatch time.

**Takeaway**: **When code must filter a tree before anything in it acts, build the tree in a document that cannot act (no browsing context) and let insertion's adoption bring the survivors to life - never filter after creating in the live document, and never compile or fetch from an adopting step (it runs mid-insertion; defer to first use).**
