# Architecture: Fresh inside a callback is allocation order, not how the object was made

**Date**: 2026-11-22
**Lesson**: Whether an object may be torn down at a binding's return into a callback's script depends only on whether it was made after that callback began. Prove that from allocation order: the slab generation against the generation the slab would issue next when the invocation began. Do not prove it from the code path that made the object.

**Why**: The frames below the innermost callback (the native algorithm that invoked it, and everything under that) were suspended when it began, so none of them can hold anything made after that point. Lane v8up b6c's rule (9bb4cd3d2) proved "made after" with a stamp that only the constructor trampoline wrote, so only `new X()` objects were ever fresh. Most of the garbage a long callback makes comes from elsewhere: factory methods (`document.createRange()`) and the DOM's own algorithms (the Ranges, InputEvents and trees that editing makes). None of it was fresh, so all of it waited for the callback to end.

**What Happened**: Lane mem1 measured 8,000 delete-joins in one timer callback at 56.6 MB Zig-side, against 5.8 MB for the same joins spread over 80 callbacks (gc_bench, chat2). At the callback's end, 56,000 Ranges (56,000 of 56,002 made inside the callback) and 57,000 queued nodes were waiting. In the html test (3,000 joins, slab objects, server1), adding the trees' rule (min slab generation per queued tree) only moved the peak from 42,075 to 40,290 against 12,750 spread. Adding the same rule to the finalizers' stamp (a wrapper record with no constructor stamp asks `DeferredTeardown.freshSerialOf` with its recorded generation) brought it to 24,225 (1.9x).

**Fix**: `SlabAllocator.generationNow()` (an atomic read of the next generation) is recorded at each callback entry, together with the slab it came from: the innermost invocation's entry, and the outermost's. A queued tree carries its lowest node generation (`Measure.min_generation`, 0 when the walk could not vouch for every node). A wrapper record's finalizer earns the innermost serial when its generation is at or above the innermost entry, and the outermost serial (wait) when it is only above the outermost entry. Everything else gets 0. It is an allowlist: an unknown generation, another slab's object (generations of two slabs do not compare), no callback on the stack, or a stopped clock are all OLD.

**Takeaway**: **When a safety argument is "nothing below the callback can hold an object made after it began", test exactly that: allocation order against the entry point. Do not use a stamp written by one creation path, because the objects that path misses are the ones that pile up.** What a fresh finalizer releases is no wider than before: a constructor-made object was already fresh and already released its references to old objects there. The remaining gap is node wrappers, whose releases still wait for depth zero and keep their deleted trees alive inside the callback.
