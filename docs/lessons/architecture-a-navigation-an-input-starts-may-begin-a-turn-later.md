# Architecture: A navigation an input starts may begin a turn later, and a host page's realm is entered for its life

**Date**: 2026-11-04
**Lesson**: A host that waits for "the navigation this input started" must look again a full turn after the input's last task: a form's submission "plans to navigate" in a task, so at the end of the input nothing is navigating yet. And a host page's Window realm is entered for its life, so a second host page cannot end before a later one - a tab the host opens needs a realm entered per call, like a popup's.

**Why**: HTML's form submission ends in "plan to navigate" - queue a task on the DOM manipulation task source that navigates - while `location.href = ..` and a link's activation navigate at once. An input that arrives as a task itself (the console's terminal posts each line to the loop's TaskSink) settles in the checkpoint after that task, and what it queued runs in the NEXT turn ("one event loop turn runs the tasks queued before it, and no more"). Separately, the V8 adapter enters a parentless Window realm for its whole life (protocol_realms.zig createWindowRealm, `context_entered = true`), and V8 exits contexts only in reverse order: a frame's or a popup's realm, made while its parent's script runs, is entered per call instead.

**What Happened**: Lane console2 made the browser console a live headless browser (tools/repl.zig: the line editor on a thread of its own, the main thread running the Browser's loop for the console's life). Scripted input waits for the navigation an input started, so `location.href = u` then `document.title` reads the new page. The first design looked once, when the input's result printed: right for location.href and a link's click, and - as reading "plan to navigate" before the test ran showed - wrong for `form.submit()`, where nothing is navigating yet and the next line would read the old document. The wait takes two looks between turns before it decides nothing is coming (`NavigationWait.after_input`, tests/repl/live_page_test.zig's form case). Opening a second host tab (a second Context) was designed and dropped: closing the first tab, or navigating it to a new Window, while the second's context is entered above it takes the adapter's "a Window realm ended under another entered context; its context stays entered" path - an entered context left behind until the Browser's end. It is its own batch (HOST-OPENED TABS: a parentless realm entered per call, made like a noopener popup's).

**Fix**: tools/repl.zig `Console.evaluationEnded` -> a navigation wait with `after_input`, settled after two polls with nothing under way, or once a navigation seen has loaded; the console prints "Navigating to <url>" (dom.navigables' navigation_url hook, the record's URL) and "Navigated to <url> (<status>)" (the navigation timing entry's responseStatus). Tabs: Browser lists, selects and closes the host page and its popups; `.newtab` says why it is not there.

**Takeaway**: **"What my input started" is what the input's task queued too: decide that nothing started only after the turn that runs it. Before a host makes a second page, ask whether its realm is entered for life - LIFO entry makes the first page outlive the second.**
